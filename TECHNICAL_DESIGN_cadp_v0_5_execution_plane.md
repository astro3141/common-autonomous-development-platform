### A.2 The cross-plane surface — exact pointers

This plane **produces** envelopes; it never decides what an envelope satisfies, and it holds no Kernel API authority beyond submitting evidence as its registered producers. Four contracts cross the boundary, all of them the Authority Plane's under **AP Part A, §9 row** (evidence ingress and provenance: producer stamping, Ingress-set integrity, adapter-registry-checked `source_relation`, untouched `claim`, source-time-authority derivation, non-policy `received_at`, derived `identity_class`, K4 completeness):

1. **Envelope subject bindings.** The `work_run` / `step` / `surface-role` bindings this plane's evidence carries (`cadp/product/backendExecution.ts`) are ordinary `SubjectBinding`s under Spec v0.5 K2/§2.4; their shape, uniqueness and kernel-namespace rules are AP's (AP B3(4) for declared kernel namespaces; AP B2(3.4) for projected pairs). This document adds exactly one binding, in B1, and adds no namespace to any kernel lookup.
2. **`produced_at` sourcing.** Per-producer, from `adapter_registry.produced_at_source`: `{kind: NONE}` for `backend-scan:*`, `{kind: SOURCE, claim_pointer: /completed_at}` for `verifier:github-actions` (`referencePolicy.ts`). A producer here never chooses its own time authority.
3. **Locator rules.** Every `PRESENT` observed field must carry a locator; the Ingress refuses `OBSERVED_WITHOUT_LOCATOR` otherwise (`cadp/kernel/ingress.ts` `assertBackendObservedLocators`; TD v0.4 C13). This plane supplies locators; it does not enforce them.
4. **Producer registration.** Which `producer_ref` may submit which `evidence_kind` under which `source_relation` lives in `adapter_registry` and changes only by `POLICY_ACTIVATE` (TD v0.4 §9.4; WP §3.2). A surface cannot acquire an evidence kind by being an execution surface.

## PART B — NEW v0.5 CONTRACTS

Exactly three. None is a constitutional record; all three are product-service contracts of an **optional** plane.

### B1. The symmetric execution contract (Spec v0.5 §6)

**Seam today.** The broker transport carries per-operation bodies with no digest discipline: `brokerImplement({repo_full_name, base_sha, work_item, worker_product})`, `brokerReview({repo_full_name, candidate_sha, work_item, review_product?})`, `brokerPlan({repo_full_name, base_sha, intent, plan_product?})` (`cadp/product/surfaceBroker.ts`, dispatched through `BROKER_OPERATIONS` / `cadp/product/brokerTransport.ts`). The result side is likewise asymmetric: `brokerImplement` returns `{candidate_sha, bundle_b64, backend_provider, backend_model?, backend_locator?, backend_effort?, …}` — an artifact and observed facts, but **no digest of the artifact**. The contract below is therefore contract-new on both sides; it describes no measured mechanism.

1. **`ExecutionRequest` — a product API contract, not a K-record.** `cadp.execution-request.v1` = `{ schema, surface_role, provider, executor_profile_digest, repo_id, base_revision, input_digests: [{ input_role, digest }] }`.
   - `provider` is the closed-union name the resolvers admit; an unknown name fails closed with no side effect (§17.1, unchanged).
   - `executor_profile_digest` is a digest over the **resolved provider profile entry** — argv template, auth descriptor, scan fields, `identity_class_product` — i.e. the argv identity of §17.1. It does **not** exist today and is **not** `workerProfileDigest` (`cadp/product/workerProfile.ts`), which digests the constructed auth sandbox; the two are distinct objects and must not be conflated.
   - `repo_id` and `base_revision` are exactly the `repo_full_name` and `base_sha` the broker already receives — `base_revision` is the same exact base revision the boundary calls `candidate_base_sha` (WP §3.4), carried unchanged. It binds provenance, never target state; this document redefines neither.
   - `input_digests` covers the exact inputs the surface is given: at minimum the work item (`work_item` / `intent`) by digest, and for the review surface the `candidate_sha` under review. Today those arrive as plain strings and the broker digests none of them.
   - **Relation to the sealed work item and base revision.** The Execution Plane digests **what it was handed** and re-derives nothing: `base_revision` MUST equal the base revision the sealing composition already pinned for that run (the worker workspace is materialized at exactly that sha — `brokerImplement` checks it out), and the work-item digest MUST be over the exact work item that run sealed. Whether a sealed effect's material and an execution envelope agree is decided by the evaluator over K4-bound facts (Spec v0.5 §4.3), never here.
2. **`ExecutionResult`.** `cadp.execution-result.v1` = `{ schema, surface_role, provider, output_artifact_digest, observed: { model, effort, provider, run_id, version } }`. `observed.*` is the existing scan payload, unchanged (`backendExecution.ts`). `output_artifact_digest` is the **exact digest of the artifact this execution produced** — for the worker surface, the candidate the broker itself materializes and returns (the candidate commit / `git bundle` bytes). It is computed by the **BROKER as observer over bytes the broker holds**; it is never read from the surface's stdout or session log and never accepted as a value the model states about itself. Exactly one digest per result, or none — never a placeholder.
3. **How it binds into the evidence envelope.** The `BACKEND_EXECUTION`-successor envelope gains exactly one subject binding, constructed exactly as the existing `surface-role` binding is: `{ authority_ref: "cadp-store:k04", namespace: "output-artifact", object_id: <output_artifact_digest> }`, so the produced artifact is a **subject** of the execution evidence rather than a claim field. Everything else about that envelope is unchanged and is the Authority Plane's (§A.2): producer stamping under `backend-scan:<provider>`, `produced_at_source {kind: NONE}`, the locator obligation, and `source_relation` staying `SELF_REPORT` — **no promotion** (Spec v0.5 §4.5). A stronger relation requires a probe establishing it and an `adapter_registry` change under the ordinary activation gate; this document promotes nothing and mints no evidence kind (Design D7-3). Whether any gate consumes the binding is composition policy: the reference policy states no such predicate today, so the binding is **inert until a composition adds one** — and the AP B4 `subject_complete_assembly` declaration set can only name this pair once the binding exists (AP B4(1)–(2): a declared entry whose subject namespace is unbound refuses `ASSEMBLY_SUBJECT_UNBOUND`).
4. **Capture mechanics, marked honestly.** `[UNMEASURED — probe required: v0.4's measured scan captures model/effort/run identity from session logs (TD v0.4 §17.2, §19.3; `scanBackendModel`); no probe has captured an output artifact digest from a live surface, so the capture mechanics of (2) and (3) are unmeasured.]` This is the capture probe that Spec v0.5 §6's marker, WP §4.2's future K2 candidate-provenance contract (which names this probe as its trigger and mints nothing before it), and the AP B4 declaration-set extension above all wait on. **The contract shape is defined NOW so the probe has an exact target.**
5. **What the probe must measure**, in order: (a) that the broker can digest the produced artifact from bytes it already holds at the surface boundary, with the surface supplying no digest and no input to it; (b) **which object is digested**, pinned exactly — a `git bundle`'s bytes are not canonical across producers, while the candidate commit sha is target-canonical, and the probe must fix one and show it stable for the same artifact; (c) the observer chain — which principal seals it, and that the value's locator names a **broker-side observation** (the `broker-response#…` shape) and never a session-file locator, since a session log is the model's own output and an artifact digest read from it would be self-report promoted to observation; (d) that the digest is comparable to the artifact the sealed material names (`candidate_sha` / `bundle_cas_key`), so the evaluator's Spec v0.5 §4.3 comparison has both sides. Until (a)–(d) are measured, no envelope this plane produces satisfies any execution-provenance requirement, and the reference policy asserts none.

### B2. Provider-credential custody (Spec v0.5 §2.3 and §6; Design D1.2)

1. **The rule, as this plane's internal discipline.** In the reference deployment, provider subscriptions are **not mutation credentials for any current governed domain target**. The measured basis is this plane's own posture: exactly one provider's auth is injected into an isolated container, read-only at its provider path, with the host keychain and every other provider unreachable (TD v0.4 §17.3; `surfaceProviderAuth` → `reviewerAuthArgs`, and `buildWorkerSandbox` on the worker path), inside a container whose only egress is the allowlist proxy to provider hosts so governed targets have no route (`isolation.ts`); and the GitHub read credential stays **host-side on the broker**, never inside any surface container (TD v0.4 §18.2; `fetchExternalVerification` shells the operator's `gh` on the broker host).
2. **This is a deployment-policy fact, and it dissolves on reclassification.** It is never a universal exemption and never a credential-**kind** exemption (Spec v0.5 §2.3, §6; Design D1.2, D7-5). A deployment whose policy classifies **provider invocation itself** as a governed effect — spend caps, data-egress control, model-access governance — thereby brings provider credentials under the **full Authority Plane custody rules**: held by the PEP, absent from every Execution Plane process and every surface container, with the invocation passing admission like any other governed effect. Nothing in this document may be read as carving them out, and Spec v0.5 §2.5's classification rule cuts the same way — an operation with no policy-bound classification defaults to **effecting**, so provider invocation is not non-effecting by default anywhere; the reference deployment's explicit classification is what puts it outside, and only there.
3. **Why this plane's isolation is load-bearing and never delegated.** WP §6 states the measured counter-fact (P0, run `24919dde`, 2026-09-07): a Conductor `working_dir` is **not a sandbox**, and `claude-agent-sdk` loads the working directory's settings as a trust boundary. An orchestrator's working directory, settings, or the word "sandbox" in its documentation therefore establish nothing. The enforceable boundary is this plane's container construction — network, mounts, single-provider auth injection, bounded lifetime (`isolation.ts`) — and it is **never delegated to any orchestrator**. The same fact is why B1's observer is the broker: an orchestrator working directory is not a place a digest can be observed from honestly.

### B3. Optionality and the equal-citizen consequence (Design D1.2)

1. **What is lost: nothing constitutional.** A deployment that runs its workers some other way — its own CI, its own harness, a human clone — keeps K1–K7, admission, PEP-only actuation, reconciliation and Kernel Conformance untouched (Spec v0.5 §9.1). What it loses is exactly the **reference execution-evidence producers**: `backend-scan:codex | grok | claude`, the only producers `adapter_registry` authorizes for `BACKEND_EXECUTION` (`REFERENCE_ADAPTERS`, `referencePolicy.ts`), so no other principal can submit that kind (`EVIDENCE_KIND_FORBIDDEN`).
2. **Which reference-policy predicates then become unsatisfiable, exactly** (`cadp/deployment/referencePolicy.ts`): `backend_model_present` — it requires a `PRESENT` `BACKEND_EXECUTION` with a `surface-role = WORKER` binding and `claim.observed.model.availability == "PRESENT"` — unsatisfiable. `backend_effort_present` — the same shape over `observed.effort` — unsatisfiable, so `effort_requirement_met` holds **only** while `params.require_backend_effort` is `false` (its first clause) and becomes unsatisfiable the moment a deployment arms that param. The **`BACKEND_EXECUTION` clause of `implementer_refs`** contributes nothing; the set is then whatever the `WORK_STEP` clause supplies, and a `WORK_STEP` producer names the **orchestrator, not the model that did the work** (WP §3.2), so a non-empty set from that clause proves no implementer product. Consequently `pr_create_ok` — `verification_ok` ∧ `external_verification_ok` ∧ `review_ok` ∧ `backend_model_present` ∧ `effort_requirement_met` — **DENYs, and no PR is created**.
3. **This is the same honest ingress-only posture the WP TD states for external candidates** (WP §3.2, control 12): **fail-closed at admission, never a defect**. An equal citizen at the effect boundary (Spec v0.5 §4.2) is equally subject to the composition's evidence requirements, and being admissible is not part of any plane's boundary contract. A deployment that wants admission without the reference producers needs a **reference-policy delta** — what establishes the implementer identity of its execution surface, how independence is computed over that evidence, and how model/effort provenance applies when the backend sits outside this plane — the same three questions WP §3.2 defers, composition work, out of scope here.

## C. Conformance controls (falsification additions)

In the Spec v0.5 §9 spirit — proven by attempting the violation. Three controls; the plane's existing product controls (TD v0.4 §13.2, P1–P7) are unchanged.

1. **Symmetric contract shape, with the observer leg.** An `ExecutionResult` carrying no `output_artifact_digest` produces an envelope with no `output-artifact` subject binding and **satisfies no execution-provenance requirement** — *vacuously today*, since the reference policy consumes only presence, `surface-role` and `observed.*` on `BACKEND_EXECUTION` and states no artifact comparison, and *normatively* once B1(5) is measured and a composition adds the predicate. Negative leg, runnable when the capture lands: a candidate digest whose locator names the surface's own session file or stdout is **refused, never sealed as observed** — the artifact digest must be the broker's observation of bytes the broker holds, so a model cannot self-report its way into execution provenance.
2. **Custody.** The **F2** control carries forward unchanged — `cadp/tests/conformance-isolation.test.ts`, "F2: the worker sandbox imports ONLY codex auth material; the profile digest is deterministic": exactly the declared auth files are imported, the host `config.toml` (MCP/config mutation surface) is not, and the probe and production constructions digest equal. Its sibling in the same file carries the reviewer posture (the session bind is the only extra writable bind, `/ws` stays `:ro`, host `HOME` is never mounted). A second provider's auth in one surface container, or any governed-target credential in any surface container, falsifies B2(1).
3. **Optionality.** A deployment with this plane removed — no surface broker, no `backend-scan:*` producers — still passes the Spec v0.5 §9.1 kernel-conformance controls unchanged, while `pr_create_ok` **DENYs** for want of `backend_model_present`. The DENY is asserted as the **correct** outcome, exactly as WP control 12 asserts it for external candidates.
