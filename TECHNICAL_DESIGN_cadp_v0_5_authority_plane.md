## PART B — NEW NORMATIVE CONTRACTS

Five contracts. Each names the implemented seam it changes, in this checkout, before it states the change. All five are Authority Plane mechanism: **no new constitutional record is created and no K8 exists** (Spec v0.5 §8-1). New storage below is implementation state in the same store, exactly as `effect_allocation` already is (TD v0.4 §3.2).

### B1. Requester-scoped allocation

**Seam today.** `allocate_effect_id` is the only write API that does **not** receive the authenticated principal: `cadp/kernel/api.ts` resolves `principal` for every call but passes it on only to `seal_effect_request` and `submit_evidence` (`sealEffectRequest(draft, { principal })`, `submitEvidence(draft, { principal })`); the allocation branch calls `deps.ingress.allocateEffectId(tuple)` with the tuple alone. `cadp/kernel/ingress.ts` accepts exactly one tuple schema, `cadp.allocation-key.v1` = `{ schema, work_run_ref, step_ordinal, purpose }`, validates `work_run_ref`'s prefix, `step_ordinal ≥ 1` and `purpose ∈ active.config.allocation_purposes`, and derives `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1(tuple))`. **There is no requester scoping in the key.**

1. **The Ingress allocation entry point takes the stamped principal.** `allocateEffectId(tuple, principal)`; the API layer passes the same `principal` it already resolves. As with `requester_ref` (TD v0.4 §9.1 S3), the principal is **stamped, never accepted from the body**: the tuple carries no requester field, and a tuple containing one is rejected `ALLOCATION_TUPLE_INVALID`. The Ingress resolves it through the active `identity_registry` to a `requester_ref` and refuses an unregistered principal (`FORBIDDEN_FOR_PRINCIPAL`).
2. **The derived key is requester-scoped for every tuple schema.** `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1({ requester_ref, tuple }))`. Consequences, both normative: **retry-convergence per principal** — the same principal resubmitting the same tuple receives the same `effect_id`, so an orchestrator that re-runs a step still creates no second logical effect (TD v0.4 §7.4; control P4) — and **distinct effect identities across principals** — two principals submitting an identical tuple receive different `effect_id`s and neither can conflict the other's request (WP control 2).
3. **Tuple schema `cadp.allocation-key.external.v1` — the wire shape is the Workflow Plane's and is not re-shaped here.** The merged WP TD canonically defines it as `{ schema, repo_id, candidate_base_sha, candidate_sha, purpose }` (WP §3.3, which **owns** it); that IS the public wire shape, and this document restates it only to cite it. The Authority Plane treats every field other than `schema` and `purpose` as an **opaque exact string it does not interpret**: allocation-time validation is exactly that the key set is the schema's, that every value is a non-empty string, and that `purpose ∈ data.cadp.allocation_purposes` (the existing check) — no field's meaning is parsed (Spec v0.5 §7; Design D7-4). `allocation_binding_digest` (B2) is computed over the `cadp-jcs-1` canonical form of the wire tuple **as received**; the tuple is an **object**, so JCS canonicalization fully determines the bytes and **no array-ordering problem exists** to be solved here. A future allocation schema is added by the plane or composition that owns its wire shape, and reaches the Authority core only through B2's bundle-supplied projection; the Authority core never parses its fields. The tuple carries no `work_run_ref` and no `step_ordinal`: it presumes no run-profile enrollment, which is why WP §5 can refuse enrollment and still allocate.
4. `cadp.allocation-key.v1`'s field set, validation and meaning are otherwise unchanged; only the scoping of (2) is added. Because a v0.5 deployment requires a v0.5 genesis in a new store namespace (Spec v0.5 §10; TD v0.4 §10), no existing `effect_allocation` row is re-keyed in place.

### B2. Allocation binding storage and first-seal atomicity

**Seam today.** `effect_allocation (allocation_key PK, effect_id UNIQUE)` (`cadp/kernel/store.ts`), written by `insertAllocation`, read by `allocationByKey` only. `sealEffectRequest` in `cadp/kernel/ingress.ts` **never reads the allocation table**: it stamps `requester_ref`, reads the material CAS object, checks the injected idempotency key, digests, and inserts under `withImmediate`, applying the K3 rule (identical semantic payload → idempotent stored row; different → `REQUEST_DIGEST_CONFLICT` incident + scope hold). An `effect_id` that was never allocated is accepted today.

1. **Storage — one generic shape for every schema.** `effect_allocation` gains exactly `{ requester_ref, allocation_schema, allocation_binding_digest, purpose }`, **all NOT NULL**, plus an index on `effect_id` (already UNIQUE) so a seal resolves the row from the `effect_id` it names. `allocation_binding_digest` = `sha256` over the `cadp-jcs-1` form of the **allocated wire tuple as received, whatever its schema** — an object, so canonicalization alone fixes the bytes (B1(3)). **No domain-named column exists and none is ever added per schema** — a new tuple schema changes no DDL (Spec v0.5 §7; Design D7-4). The row stays non-constitutional: in no K-record, no digest, no `ResolvedAdmissionBundle`.
2. **The projection registry — composition-supplied data, generic equalities.** `cadp.kernel-config.v2` gains exactly one new closed-entry-key registry: `data.cadp.allocation_schemas: [{ schema, binding_projection: [{ tuple_field, authority_ref, namespace }], purpose_relation: [{ purpose, operation_kind }] }]` — required, may be `[]`, exact strings, closed entry keys (B3), gate-controlled at activation exactly like `identity_registry` and `adapter_registry`. **Every value in it is supplied by the policy bundle**; the Authority core stores these strings, compares them, and interprets none of them (Spec v0.5 §7; Design D7-4). B3(1)'s uniqueness rule extends to it — two rows sharing a `schema`, two `binding_projection` entries of one row sharing a `tuple_field`, or two `purpose_relation` entries of one row sharing a `purpose` are refused `REGISTRY_DUPLICATE_KEY` — for the same reason as the other registries: a first-match lookup would otherwise let bundle authoring order decide what a seal is compared against.
3. **First seal verifies material AND purpose, before any K3 record exists.** The first `seal_effect_request` for an `effect_id` (no `effect_request` row yet) MUST resolve the allocation row by `effect_id`; absent ⇒ `ALLOCATION_NOT_FOUND` (closing caller-invented effect identities — Spec v0.5 K3). It then executes exactly these equalities, all of them generic:

   1. **principal** — stamped `requester_ref` == row `requester_ref`, else `ALLOCATION_PRINCIPAL_MISMATCH`;
   2. **tuple integrity** — the caller re-presents the allocated tuple as **transport, never a draft field**; the core recomputes its `cadp-jcs-1` digest and requires equality with `allocation_binding_digest`, else `ALLOCATION_BINDING_MISMATCH`. **Nothing inverts the digest**; the stored digest only confirms what was re-presented;
   3. **material** — for each `binding_projection` entry registered for the row's `allocation_schema`, the sealed request's `work_bindings` MUST contain a binding whose `authority_ref` and `namespace` equal the entry's **and** whose `object_id` equals the re-presented tuple's `tuple_field` value, else `ALLOCATION_BINDING_MISMATCH`;
   4. **purpose** — the sealed `operation_kind` MUST equal the `operation_kind` that the registered `purpose_relation` pairs with the allocated `purpose`; no pair for that `purpose` is itself a refusal. Else `ALLOCATION_PURPOSE_MISMATCH`.

   This is WP §3.3's contract restored as that document states it: a first seal naming a different **candidate, base, purpose or principal** than the allocation is REFUSED BEFORE ANY K3 RECORD EXISTS, never deferred to a composition-level admission predicate that runs after one. It imports no domain vocabulary to do it — every string compared in (3) and (4) is either bundle-authored data or the caller's own tuple, and the core reads none of them for meaning.
4. **Why a projection entry carries `authority_ref`.** `cadp/kernel/records.ts` defines a `SubjectBinding`'s identity as `{ authority_ref, namespace, object_id, revision_or_version?, content_digest? }` with **`authority_ref` required** — a `namespace`/`object_id` pair is not, by itself, a subject identity. Each entry therefore names the full `(authority_ref, namespace)` pair, so an allocation can never be satisfied by an identically-named subject standing under a **different** authority (`github.com` vs `cadp-store:k04` vs a second forge), which a namespace-only match would accept. The optional `revision_or_version` and `content_digest` are not compared: the tuple field is the object identity, and comparing an optional field would make the check satisfiable by omission.
5. **Schema coverage is closed.** A tuple schema with no `allocation_schemas` entry **cannot be allocated** — `allocate_effect_id` refuses `ALLOCATION_SCHEMA_UNREGISTERED` — so no allocation can come to exist that a first seal would have to check against nothing. The single exception is `cadp.allocation-key.v1`, whose projection is **fixed by this document** and needs no bundle entry: the sealed binding in the `work-run` namespace equals the allocated `work_run_ref`. That namespace is Kernel vocabulary, not composition data — the implemented `sealEffectRequest` already selects `work_bindings` by `namespace === "work-run"` and the authority is the constitutional store itself (`cadp/kernel/ingress.ts`) — so the fixed projection inherits exactly the implemented selection and raises no new authority question. Honestly: **`step_ordinal` is allocation-key entropy only** — it names the orchestrator's step slot for key derivation and is **not re-verifiable at seal, because no K3 field carries it**; per-key idempotency and the K3 conflict rule bound it, unchanged. A bundle MAY declare an `allocation_schemas` entry for `cadp.allocation-key.v1` to supply its `purpose_relation`, which is then enforced by (3.4) identically; such an entry's `binding_projection` MUST be `[]`, the projection being this document's. Absent such an entry, `purpose` for the internal schema is bound as it is today — by the allocation-time `allocation_purposes` check and by K3 — which is no regression, and it is the only leg not covered by (3).
6. **Illustrative only — composition data, not a normative table here.** The reference bundle's entry for `cadp.allocation-key.external.v1` — the repository, base-commit and commit namespaces, the GitHub authority, and the three purpose relations — is **composition data, authored where WP §§3.4 (material bindings) and §3.3 (the purpose correspondence) define them**. It is cited, not restated normatively here. One illustrative fragment, marked **composition-supplied data**: `{ schema: "cadp.allocation-key.external.v1", binding_projection: [{ tuple_field: "candidate_sha", authority_ref: "github.com", namespace: "commit" }, …], purpose_relation: [{ purpose: "pr-create", operation_kind: "PR_CREATE" }, …] }`. The test that these are data and not core vocabulary: changing any string in them is a policy change under the ordinary activation gate and requires no Kernel change at all.
7. **Atomicity.** The read of the allocation row, the equality checks of (3) and the `effect_request` insert occur **in one store transaction** with the allocation row locked for the duration (`SELECT … FOR UPDATE` on PostgreSQL; `BEGIN IMMEDIATE` single-writer on the SQLite reference, i.e. the existing `withImmediate`). Consequence, which is the point of the contract: a first seal whose principal, projected material or purpose does not equal the immutable allocation row is **REFUSED deterministically before any K3 record exists**, under every interleaving of concurrent first-seal attempts — the check is against the allocation row, never against a race-visible request row, so no ordering makes a mismatching seal land. Concurrent *matching* first seals resolve by the unchanged §3.3 rule: one inserts, the other returns the stored row. Once a `request_digest` exists, the ordinary K3 conflict rule governs everything after it, unchanged.
8. **Refusal shape.** Reason codes `ALLOCATION_NOT_FOUND`, `ALLOCATION_PRINCIPAL_MISMATCH`, `ALLOCATION_BINDING_MISMATCH` (re-presented tuple digest ≠ `allocation_binding_digest`, or a projection entry unsatisfied) and `ALLOCATION_PURPOSE_MISMATCH` at first seal; `ALLOCATION_SCHEMA_UNREGISTERED` at allocation. On any of them no `EffectRequestV1` is sealed and no effect is performed. **No `KERNEL_INCIDENT` and no scope hold is raised** — deliberately, and this is normative: the allocation is requester-scoped, so a mismatching first seal is a caller error against an effect identity that has no K3/K6/K7 history, and raising a scope hold would let any principal freeze another principal's effect scope by attempting one bad seal. The K3 conflict path (which does raise an incident) is untouched.
9. **Registry drift is fail-closed.** The row stores the `requester_ref` resolved under the policy active at allocation; the first seal compares the `requester_ref` stamped under the policy active at seal time, and applies the `allocation_schemas` projection active at seal time. A policy activation that re-maps the principal, or that changes or withdraws the schema's projection, makes the check unequal or unregistered, the seal is refused, and the proposer re-allocates under the new bundle. This is a refusal, never a fallback to the raw principal string and never a silent re-interpretation of an allocation under a projection it was not made under.
10. **Not a K8.** Nothing above is a constitutional record, a new evidence kind, or a new admission state. It is the pre-K3 window's implementation, delegated to this document by WP §3.3.

### B3. Registry uniqueness and closed entry keys

**Seam today.** `validateKernelConfig` (`cadp/kernel/policyBundle.ts`) enforces the closed top-level key set (`ALLOWED_KEYS`), the exact-string/no-pattern rule on `identity_registry.principal` and `adapter_registry.producer_ref`, entry field types, the `produced_at_source` shape, the governed-writer opt-in vocabularies and the invariant-P reserved-constant rule, bounds and bootstrap-scheme retention. It performs **no duplicate detection**, and the closed-key check is `data.cadp` top level only — an unknown key *inside* an entry validates and activates. Resolution is by first match: `identityEntry`/`adapterEntry` in `cadp/kernel/policyState.ts` are `find()`.

1. **Uniqueness (new activation-time rejection).** A bundle is refused at `POLICY_ACTIVATE` recheck #17 / genesis validation if any of the following holds: two `identity_registry` rows share a `principal`; two `identity_registry` rows share a `producer_ref`; two `adapter_registry` rows share a `producer_ref`. Reason `REGISTRY_DUPLICATE_KEY`. Grounding for each: a duplicate `principal` makes `identityEntry`'s `find()` silently order-dependent, so the caller's `process_class` (and therefore its `METHOD_REACH`) and its stamped `producer_ref` are decided by bundle authoring order; a duplicate `producer_ref` in `identity_registry` makes the reference policy's `registry_entry(producer)` a function with two candidate outputs — in Rego that is a conflicting-output evaluation error, i.e. an `EvaluatorFailure` and **no** decision (fail-closed but opaque), while the PEP computing the same derivation in TypeScript takes the first row (fail-open relative to the evaluator, and the two can disagree about `identity_class.product`, which is exactly the value the independence predicate compares); a duplicate `adapter_registry` row makes the allowed `evidence_kinds`, `source_relation` and `produced_at_source` of one producer order-dependent at the ingress. Rejecting at activation makes all three unconstructible.
2. **Unknown keys inside entries are rejected** — decided here, and decided the same way as the top level, for the same fail-closed reason: **an inert key is not a declared binding.** A key the Kernel does not read is either a future binding activated early (so its meaning is unenforced while it appears authoritative to a reader) or a typo silently disabling the binding it was meant to be (`producer-ref` for `producer_ref`, `evidence_kind` for `evidence_kinds`). Spec v0.5 §2.5's rule — a missing or unverifiable required fact never satisfies a requirement — makes silent acceptance the wrong default for the one document that declares who may say what. Reason `REGISTRY_UNKNOWN_ENTRY_KEY`.
3. **Closed entry key sets** (exact; anything else is refused): `approved_digest_schemes` `{algorithm, canonicalization}`; `root_public_keys` `{key_id, alg, public_key, valid_from, valid_to?}`; `attestation_keys` `{key_id, alg, public_key, purpose, valid_from, valid_to?}`; `identity_registry` `{principal, producer_ref, identity_class{vendor, product, account, process_class}}`; `adapter_registry` `{producer_ref, evidence_kinds, source_relation, produced_at_source{kind, claim_pointer?}, replay_idempotency?, governed_edge?}`; `allocation_schemas` `{schema, binding_projection[{tuple_field, authority_ref, namespace}], purpose_relation[{purpose, operation_kind}]}` (B2(2)). The two optional `adapter_registry` keys are the governed-writer opt-ins that exist in the checked-out schema and in the reference `adapter_registry` row `governed:reclassification`; omitting them from the closed set would refuse the current reference bundle.
4. **Schema identity.** (1)–(3), together with B2(2), B4(1) and B5(3), define **`cadp.kernel-config.v2`**, required exactly by `schema` string. Because activation acceptance is narrowed, this is a generation-boundary change: v0.5 genesis bundles carry v2, and no running v0.4 environment is mutated in place (Spec v0.5 §10).

### B4. Assembly completeness

**Seam today.** `assemble_admission_input(effect_id, evidence_refs[])` takes the caller's list verbatim: `cadp/kernel/api.ts` parses `{ effect_id, evidence_refs }` from the body and `Ingress.assembleAdmissionInput` resolves each id, records `{evidence_id, envelope_digest}`, and seals K4. The store already supports the needed read: `evidence_subject(evidence_id, subject_key)` with `subject_key = "<authority_ref>|<namespace>|<object_id>"` and an index, plus an `evidence_kind` index, joined by `evidenceBySubjectKey`. The reference policy's predicates are existential (`some e in input.evidence`), so **a caller can today withhold an unfavourable sealed envelope of a kind the gate consumes** and the evaluator never learns it exists.

1. **Declaration.** `data.cadp.subject_complete_assembly: [{ evidence_kind, subject_namespace, operation_kinds[] }]` — required, may be `[]`, exact strings, closed entry keys (B3), part of `cadp.kernel-config.v2`. Kernel-read, so it lives under `data.cadp` and not in rego-private `policy_params`. All three components are identity strings the Kernel already handles; **no material field is parsed** — domain material vocabulary stays in the composition (Spec v0.5 §7).
2. **Query contract.** For a declared entry and a sealed `EffectRequestV1` whose `operation_kind` the entry lists, the Platform computes, from that request's own `work_bindings`, every subject key `<authority_ref>|<subject_namespace>|<object_id>` it names, and selects **every** sealed envelope of that `evidence_kind` bound to that exact key — the complete set, not a latest-wins pick. This is the existing `(evidence_kind, subject_key)` join over the sealed store. The `latestEvidenceOfKind` helper in `store.ts` MUST NOT be used for assembly: "latest" is not authority in sealed history (Spec v0.5 §2.6; TD v0.4 §6.6). If the sealed `work_bindings` name **no** binding in `subject_namespace`, assembly REFUSES `ASSEMBLY_SUBJECT_UNBOUND` — the rule is never vacuously satisfied by an unbound subject. Composition consequence, stated because it is a real change and not a kernel one: the reference composition binds only `work-run` into `work_bindings` today (`cadp/product/activities.ts` seals `[{namespace: "work-run", …}, ...extra_bindings]` and nothing populates `extra_bindings`), so declaring `{REVIEW, commit, [PR_CREATE, PR_MERGE]}` requires the composition to bind the candidate through that existing hook — exactly what WP §3.4 already mandates for external candidates.
3. **Where it runs.** Inside `assemble_admission_input`, in the Platform (Ingress), in the same transaction that seals K4. The result is the **union** of the caller's `evidence_refs` and the queried set, deduplicated by `evidence_id` and ordered canonically by `evidence_id` so `input_digest` is deterministic. The caller may add; the caller can never subtract. Assembly is never the caller's evidence-selection choice for a declared kind (Spec v0.5 K4: the PEP never back-fills facts the evaluator did not see — the correction is to put them in front of the evaluator, not behind the PEP).
4. **Fail closed.** If the query cannot be executed, or any matched row fails verify-on-read, assembly **refuses** — `ASSEMBLY_QUERY_FAILED` / `DIGEST_CORRUPTION` (incident per TD v0.4 §2.6) — and **no `AdmissionInputV1` row is written**. A partial set is never sealed.
5. **Completeness is as-of a transaction, so it is re-proven at commit.** A new `§4.4` recheck item **#18**: inside the admission transaction, the PEP re-runs (1) over rows read in that transaction and refuses `ASSEMBLY_INCOMPLETE_AT_COMMIT` if the complete set for any declared pair differs from the set the bound `AdmissionInputV1` carries. Without #18 a producer could seal a contrary envelope after assembly and the decision would be silently stale (Spec v0.5 §2.7). Honest cost: a producer that keeps sealing envelopes for a subject can keep admission failing. That is a liveness cost of a safety rule, and it is fail-closed — a fresh assembly and evaluation resolve it.
6. **What this does not do.** It does not make an existential policy predicate sound; it removes the caller's power to decide what the evaluator sees. Whether the complete set satisfies a gate remains the evaluator's decision over K4-bound facts.

### B5. Run membership mechanism

Spec v0.5 §5.3 locks the invariant — *a requester cannot self-select or borrow another valid run scope* — and delegates the mechanism to the TD. **One mechanism is chosen: a Platform-minted run capability.**

**Seam today.** Nothing implements this: `work_bindings` are caller-supplied content on the seal draft, and `sealEffectRequest` reads `work_run_ref` out of them only to index the request row. `METHOD_REACH` in `cadp/kernel/api.ts` is keyed by `process_class`, not by principal. And `admit_and_dispatch` is the **second** write API that receives no principal: the branch calls `deps.pep.admitAndDispatch(body.effect_id, body.decision_id)` with no caller identity at all (`cadp/kernel/api.ts`), so any principal of the `workflow` class could dispatch any effect.

1. **Minting at dispatch, delivered only to the sealed requester.** `admit_and_dispatch` takes the authenticated principal — `admitAndDispatch(effect_id, decision_id, { principal })`, the same pattern the API layer already uses for `seal_effect_request` and `submit_evidence`. For an effect whose **sealed request is run-capability-minting** (its `operation_kind` is the run profile's `WORK_START`), the PEP **REFUSES the dispatch** unless the caller's stamped `requester_ref` equals the sealed request's `requester_ref` — reason `WORK_START_DISPATCH_REQUESTER_MISMATCH`. That is a generic stamped-vs-sealed `requester_ref` equality carrying no domain knowledge, and it is what makes the one-shot secret deliverable **only** to its exact holder-to-be. Without it, the checked-out seam would let any `workflow`-class principal dispatch another's `WORK_START`, receive the capability, and — there being no recovery (7) — strand that run permanently. The alternative (let the dispatch proceed and merely withhold the secret from the wrong caller) was **rejected**: it leaves exactly the same permanent stranding, reachable by any authorized caller who simply races the dispatch. On that refusal nothing is minted and no outcome is written.
   At the **initial** `admit_and_dispatch` of a minting `WORK_START` — before any outcome exists — the Platform mints a run capability of ≥256 bits from a CSPRNG and returns it in **that** result to the verified caller. `H(C)` is stored **in the same transaction as the admission**, in `run_capability(work_run_ref PK, holder_ref, capability_digest, minted_at)`, a non-constitutional implementation table; the secret itself is never stored, never in any K1–K7 record or digest, never in the `ResolvedAdmissionBundle`, and never in workflow args or effect material. `holder_ref` is the stamped `requester_ref` of that `WORK_START` request, which by the paragraph above is also the caller the secret went to. The `work_run_ref` primary key is that `WORK_START`'s own `effect_id` (TD v0.4 §7.4), so minting is once-and-only-once by construction: a repeat `admit_and_dispatch` of the same effect finds the row present, mints nothing, and returns no secret — "exactly once" (7) is enforced by the store, not by caller discipline.
2. **Usability is gated at seal time on a conclusive `COMMITTED` K7 — not on when the capability was minted.** Minting is delivery; **grading is Spec v0.5 §5.2's**, and it is applied on every presentation. The run-membership check of (4) requires, in addition to digest match and holder match, that the `WORK_START`'s `EffectOutcomeV1` be **conclusively `COMMITTED`, read in the sealing transaction** — K7, never K6, per Spec v0.5 §5.2 and the memo-proof rule of TD v0.4 §6.4. Therefore: an `UNKNOWN` `WORK_START` makes **every** presentation refuse `RUN_SCOPE_UNRESOLVED` (Spec v0.5 §5.2's "unusable until reconciliation resolves it" — no blind retry, no optimistic use); when reconciliation returns `COMMITTED`, the **same already-delivered capability becomes usable**, with **no re-delivery and no reconciler secret-handling** — which matters, because `Reconciler.reconcileEffect` writes that outcome with observer `…:reconciler` outside any `admit_and_dispatch` result (`cadp/kernel/reconciler.ts`), reached from the restart scan or from `request_reconcile`, whose reach is not the holder's alone (`cadp/kernel/api.ts`); a `NO_EFFECT_CONFIRMED` `WORK_START` leaves the capability **inert forever** — every presentation refuses `RUN_SCOPE_REFUSED`, and no path ever revives it. This keeps all four properties at once: no recovery, digest-only storage, Spec v0.5 §5.2's reconciliation semantics honoured rather than contradicted, and **no secret in any reconciler path**.
3. **Enrollment, in the `requester_ref` domain.** `data.cadp.run_profile_enrolled_requester_refs: [exact requester_ref]` — required, may be `[]`, part of `cadp.kernel-config.v2`. Spec v0.5 §5.1 declares enrollment over exact requester principals **as stamped** (`requester_ref`), so the enrolled set is in that domain and never in the raw authenticated-principal domain. At seal the chain is: authenticated principal → `identity_registry` → **stamped `requester_ref`** → enrollment membership; the PEP's admission-time identity for (5) is `EffectRequestV1.requester_ref`, the **same domain**, read off the sealed record rather than re-derived. For an enrolled `requester_ref`, `seal_effect_request` REFUSES a request without a `work-run` binding (`RUN_BINDING_REQUIRED`) — refused, not merely uncounted (Spec v0.5 §5.1). A **non-enrolled** `requester_ref`'s request carrying a `work_run_ref` is refused `NOT_RUN_ENROLLED`: enrollment cannot be acquired by presenting a binding (WP §5.2; WP control 5).
4. **Presentation and verification.** An enrolled requester presents the capability on `seal_effect_request` over its authenticated channel — as a transport-level header, never as a draft field, never inside any record. The Ingress refuses unless, in the sealing transaction: the capability's digest matches the `run_capability` row for the request's exact `work_run_ref`; that row's `holder_ref` equals the **stamped** `requester_ref` of this request; and that run's `WORK_START` K7 outcome is conclusively `COMMITTED` (2). Possession never suffices on its own: the row binds one capability to one `work_run_ref` **and** one holder, so presenting run R2's capability on a request bound to R1 fails the first check and a principal holding another's capability fails the second. **Seal-time refusal codes, all distinct from recheck #19's `RUN_MEMBERSHIP_UNPROVEN`** — which is a PEP-time refusal on a missing durable row: `RUN_CAPABILITY_INVALID` (no digest match against the row for this request's `work_run_ref`, including the case where no row exists for it); `RUN_CAPABILITY_HOLDER_MISMATCH` (row `holder_ref` ≠ stamped `requester_ref`); `RUN_SCOPE_UNRESOLVED` (`WORK_START` outcome `UNKNOWN`); `RUN_SCOPE_REFUSED` (`WORK_START` outcome `NO_EFFECT_CONFIRMED`); `RUN_CAPABILITY_REQUIRED` (an enrolled requester's run-bound request presenting none — distinct from `RUN_BINDING_REQUIRED`, which covers only the missing-`work-run`-binding case of (3)). **There is no revocation state in this generation** and no `revoked_at` column: the store contract forbids runtime `UPDATE`/`DELETE` (`cadp/kernel/store.ts`), so a mutable flag would be a field no append-only path could ever set. Revocation, if it is ever wanted, is a future append-only row (`run_capability_revocation { work_run_ref, revoked_at, … }`) consumed by this seal-time check; out of scope here.
5. **Durable proof for the PEP.** The seal inserts `run_membership(effect_id PK, work_run_ref)` in the same transaction as the `effect_request` row. New `§4.4` recheck item **#19**: for a request whose sealed `requester_ref` is enrolled, the PEP requires that row, with a matching `work_run_ref`, read inside the admission transaction — refusing `RUN_MEMBERSHIP_UNPROVEN` otherwise. Authority after restart is reconstructed from rows, never from process memory (TD v0.4 §4.5); the secret is not needed at admission time.
6. **What it is not.** The run capability is **not** a governed-target credential and confers no effect authority: a compromised one lets its holder propose requests bound to a run, which still need evidence, a decision under the active policy and the PEP's fresh recheck (Spec v0.5 §4.3). Its compromise cannot create an effect; it can only mis-attribute an effect to a run's budget — precisely the invariant it exists to protect, so the residual is stated, not hidden. Custody is no new custody class: the holder already holds a Kernel API bearer/workload credential today (`ApiDeps.tokens`, `cadp/kernel/api.ts`).
7. **No recovery.** The capability is returned **exactly once**, in the initial `admit_and_dispatch` result of the minting `WORK_START`, to the caller (1) verified as the sealed requester. That result is the **only** delivery channel this document defines. There is no re-delivery: only `capability_digest` is stored, and a digest cannot be inverted, so no contract here may promise to hand the secret back — and none needs to, because (2) makes a later K7 resolution change only *usability*, never delivery. A holder that loses it **cannot seal further run-bound requests for that run** — fail-closed, a liveness cost only, and consistent with the run remaining governable per-effect (its already-sealed effects admit, reconcile and grade normally). Rotation — mint C2, atomically append a superseding row, return C2 to the exact holder — is a possible future contract needing its own concurrency and replay rules and would be named `rotate_run_capability`; out of scope here. **This document adds no Kernel API method.**
8. **Unmeasured part, marked exactly** (Spec v0.5 §5.3's marker resolved to the one dependency that is actually unmeasured, with the invariant unweakened):
   - Holder-side custody across an orchestrator restart. `[UNMEASURED — probe required: no probe of any orchestrator's durable secret custody exists. The measured counter-fact bounds it: WP §6 (P0) measured that a Conductor `working_dir` is not a sandbox and that its settings are a trust boundary, which is one reason the reference deployment enrolls no Conductor principal (WP §5.2). The reference run profile's holder is the Temporal-backed `requester_ref` `workflow:cadp-work` (stamped from principal `cadp-workflow`, `cadp/deployment/referencePolicy.ts`).]`
9. **Not a K8.** Two implementation tables and two recheck items. No new record, no new evidence kind, no orchestrator lifecycle.

## C. Conformance — one falsification control per new contract

In the Spec v0.5 §9 spirit: proven by attempting the violation, observables counted at the target and read from the store (TD v0.4 §13). Guard-bite applies (TD v0.4 §13.1): each control is re-run with its check removed and must then show the prohibited outcome, or it is reported as defence-in-depth, not as load-bearing.

**Already live in the Workflow Plane TD — referenced, not duplicated:** B1's cross-principal distinctness is WP control 2 (identity-squatting refusal) and its replay convergence is WP control 1; B2's first-seal mismatch legs are WP controls 7 (candidate), 8 (base), 9 (purpose) and 10 (principal). **All four remain executable as the seal refusals WP §3.3 states them to be**, because every check behind them is a generic equality naming no domain field: 7 and 8 reduce to a `binding_projection` entry unsatisfied for the `candidate_sha` and `candidate_base_sha` tuple fields (`ALLOCATION_BINDING_MISMATCH`), 9 to the registered `purpose_relation` not pairing the allocated purpose with the sealed `operation_kind` (`ALLOCATION_PURPOSE_MISMATCH` — a **seal refusal before any K3 record exists**, per B2(3), not a post-K3 evaluator DENY), and 10 to requester inequality (`ALLOCATION_PRINCIPAL_MISMATCH`).
