## 1. Position and thinness rule

The withdrawn Conductor integration (PRs 199–204) failed by constitutionalizing an orchestrator's runtime; every Conductor concept demanded a CADP counterpart (Design D0). This document is its replacement at a fraction of that size, and the size bound is structural, not stylistic: per Spec v0.5 §4.1, mutation intents arriving as `EffectRequestV1` through an effect client is the **whole** mandatory integration between any workflow plane and CADP. Everything below specifies that boundary and nothing behind it. A Conductor workflow, a cron job, and a human at a terminal are equal citizens at this boundary (Spec v0.5 §4.2); nothing here is Conductor-specific except measured facts grounding refusals (§5, §6).

## 2. Scope fence (non-goals)

Per Design D7-2 and D7-3, this document contains, normatively:

- **no orchestrator task states** — how a Conductor (or Temporal, or cron) run represents progress is its business;
- **no retry semantics** — the orchestrator may retry its own steps freely; the *effect* retry discipline is the Authority Plane's (Spec v0.5 §4.4: no blind retry), stated there, not here;
- **no checkpoint model** — orchestrator durability is never authority (Spec v0.5 §4.1);
- **no DAG vocabulary** and **no Conductor YAML schema** — workflow shape never crosses the boundary.

Orchestrator internals appear below **only** as measured facts grounding refusals (Design preamble; §5, §6). If a future revision of this document states any of the above normatively, that is a regression to the withdrawn approach and grounds for REQUEST_CHANGES on its own.

## 3. The external-candidate effect client

### 3.1 Measured gap (P0)

v0.4 exposes no surface for an externally-produced candidate to enter governance. The live surfaces — `cadp/live/mcpServer.ts` (`cadp_work_start`) and `cadp/live/ctl.ts` — only start the internal Temporal pipeline: `cadpWork` (`cadp/product/workflows.ts`) runs its own `implementCandidate` / `verifyCandidate` / `reviewCandidate` activities. A candidate produced anywhere else (a Conductor workflow's working tree, a cron job, a human clone) has no path to the governed effects `GIT_PUSH`, `PR_CREATE`, `PR_MERGE` except by not being governed at all. This section closes that gap with the minimal caller surface.

### 3.2 Caller surface — no new API, no caller-contract delta

The client is the existing Kernel API of TD v0.4 §12, unchanged: `put_blob`, `allocate_effect_id`, `seal_effect_request`, `submit_evidence`, `assemble_admission_input`, `evaluate`, `admit_and_dispatch`, `get_effect_state`, `request_reconcile`, plus the reads. An external effect proposer authenticates as its own registered principal (mTLS/SPIFFE or, for a human terminal, the IdP path) with the **workflow/orchestrator caller class reach** of the TD v0.4 §12 matrix. No new endpoint, no new record kind — and, correcting the prior draft, **no caller-contract (method-reach) delta either**. The implemented method-reach contract (`METHOD_REACH`, `cadp/kernel/api.ts`) is a **static method-to-`process_class` table**: it is code, not registry content — `cadp.kernel-config.v1`'s closed schema carries no method-reach key — and it is **kind-blind**: `submit_evidence` reach already exists for the `worker`, `evidence-adapter`, `human-surface`, and `agent-surface` process classes (alongside `workflow` and `deployment-control`). The per-evidence-kind restriction lives one layer down, enforced by the Ingress on every submission: authenticated principal → `identity_registry` entry (exact string; `process_class`; `producer_ref`) → the `adapter_registry` entry for that exact `producer_ref` → `evidence_kinds.includes(kind)` and the registered `source_relation` (TD v0.4 §9.1; `cadp/kernel/ingress.ts`).

**The boundary guarantee this document makes is INGRESS-ONLY, never admission.** External candidates can enter governance through the effect boundary — allocation, sealing, evidence submission for registered kinds, evaluation — but **ADMISSION remains fail-closed under the active development composition**: a candidate lacking the policy-required execution/implementer provenance may be DENYed before `PR_CREATE`, even with a Human merge decision available. The concrete implemented consequence, stated so that reach is never read as reachability: **under today's reference composition an external candidate is EXPECTED to deny at `PR_CREATE`.** `pr_create_ok` (`cadp/deployment/referencePolicy.ts`) requires `verification_ok`, `external_verification_ok`, `review_ok`, `backend_model_present` and `effort_requirement_met`. `review_ok`'s independence leg is `independent_product`, which requires `count(implementer_refs) > 0`. `implementer_refs` is a two-clause union: `WORK_STEP` producers, and `BACKEND_EXECUTION` evidence carrying a `surface-role` = `WORKER` subject binding. Only the second clause attributes an **implementer identity**: every `WORK_STEP` is submitted by the orchestrator, so the `WORK_STEP` clause names the workflow rather than the model that did the work — which is why the `BACKEND_EXECUTION` clause exists at all (`cadp/deployment/referencePolicy.ts`; the 12th-pilot fix, where independence was being compared only against the workflow's own product class). An external candidate supplies neither clause's evidence — and not merely by omission: in the reference registries `WORK_STEP` is carried only by `workflow:cadp-work` and `BACKEND_EXECUTION` only by the `backend-scan:*` producers of the internal execution surface (`REFERENCE_ADAPTERS`, `cadp/deployment/referencePolicy.ts`), so no external principal is even authorized to submit either kind (`EVIDENCE_KIND_FORBIDDEN`, `cadp/kernel/ingress.ts`). So `implementer_refs` is **empty**, `independent_product` fails, `review_ok` is false, and `pr_create_ok` DENYs — and `backend_model_present` fails on the same missing `BACKEND_EXECUTION` evidence. The Human merge decision is **never even reached**, because no PR is ever created to merge. **This is correct fail-closed behaviour, not a defect.** An equal citizen at the effect boundary (Spec v0.5 §4.2) is equally subject to the composition's evidence requirements; **being admissible is not part of the boundary contract**. Independence that cannot be proved against a known implementer is not independence (TD v0.4 §8.3: the `count(implementer_refs) > 0` rule exists because a vacuous universal quantifier once let a self-implemented candidate auto-merge).

Supporting an external-candidate flow through to a Human merge would be a future **reference-policy delta** — composition, not kernel and not this boundary — and that delta must define three things before it can be written: which evidence establishes the **actual implementer identity** of an externally-produced candidate; how **reviewer independence** is computed over that evidence; and how `backend_model_present` and the `require_backend_effort` effort requirement apply when the implementing backend sits outside the platform's execution surface. All three are **explicitly out of scope for this document**.

Registering an external proposer — its `identity_registry` entry, and the `adapter_registry` entry for its exact `producer_ref` naming the `evidence_kinds` it may submit — is an **ordinary policy-bundle change, gate-controlled like any other registry change** (TD v0.4 §9.4): it rides a `POLICY_ACTIVATE`, never a runtime toggle. So is any future policy delta of the kind §3.2 defers above. **Boundary note:** only a deployment that needs to open `submit_evidence` to a process class that does NOT already hold it would touch the static caller contract — and that is a code-level Authority Plane change, outside `POLICY_ACTIVATE`, out of scope here. This surface remains safe for untrusted callers for exactly the reason TD v0.4 §12 states: no method grants authority — a sealed request still needs evidence, an evaluator decision under the active policy, and the PEP's fresh recheck (Spec v0.5 §4.3 steps 5–7). `requester_ref` is always stamped from the authenticated principal, never accepted from the body (TD v0.4 §9.1 S3).

### 3.3 Effect identity — Platform-sealed, orchestrator-retry-convergent

`effect_id` is allocated by Platform effect ingress before any non-trivial external call; a caller-proposed correlation string is never identity authority (Spec v0.5 K3). Concretely for external proposers:

- The proposer calls `allocate_effect_id` with a versioned canonical tuple (TD v0.4 §7.4 discipline: canonical JSON, closed `purpose` vocabulary, no raw concatenation), schema `cadp.allocation-key.external.v1`: `{ schema, repo_id, candidate_base_sha, candidate_sha, purpose }`. `candidate_base_sha` (§3.4 vocabulary: the exact base revision the candidate was built and reviewed against) is an exact immutable identity component alongside repository identity and `candidate_sha` — without it, two submissions whose candidates sit on materially different base revisions could share an `effect_id`, contradicting K3's binding of one `effect_id` to one `request_digest` over exact material. The Ingress scopes the derived key by the **stamped** requester principal — two principals proposing the same candidate get distinct effect identities; a retry by the same principal converges on the same `effect_id`, so an orchestrator that re-runs a step never creates a second logical effect. (This replaces the internal tuple's `work_run_ref + step_ordinal` scoping, which presumes run-profile enrollment — §5 refuses that here.)
- **Allocation-to-first-seal binding (closes the pre-K3 window).** K3's one-`effect_id`-one-`request_digest` conflict rule presupposes an *existing* sealed `request_digest`; on the first `seal_effect_request` for an allocated `effect_id` there is nothing yet to conflict with, so K3 alone would not stop a first seal naming different material than the allocation — or a first seal by a different principal than the allocator. This document therefore states the **observable cross-plane contract, and only that**: (a) an allocation MUST be scoped to the stamped requester principal and MUST be durable across restart; (b) the FIRST `seal_effect_request` for an `effect_id` MUST verify the allocation binding — stamped principal, `repo_id`, `candidate_base_sha`, `candidate_sha`, and the closed purpose-to-`operation_kind` correspondence (purpose `git-push` ↔ `operation_kind` `GIT_PUSH`, `pr-create` ↔ `PR_CREATE`, `pr-merge` ↔ `PR_MERGE`, the purpose literals coming from the policy bundle's closed `allocation_purposes` vocabulary — `cadp.kernel-config.v1`, TD v0.4 §5.4 — never invented by the caller) — **atomically with respect to the allocation**, so that a mismatch is REFUSED deterministically BEFORE any K3 record exists, including under concurrent first-seal attempts, never degenerating into a post-hoc K3 conflict whose semantics vary by implementation. On refusal, no `EffectRequestV1` is sealed and no effect is performed. The binding is explicitly **not** a new constitutional record — no K8 is created. **The storage schema, transaction, and locking that realize this contract are owned by the Authority Plane TD**, to which this document delegates them (per its own Non-scope; §2). Measured seam, marked as an Authority Plane TD work item: today `allocate_effect_id` does not pass the authenticated principal to the Ingress — `cadp/kernel/api.ts` passes the principal only for `seal_effect_request` and `submit_evidence` — so requester-scoped allocation is not yet realized at that seam. Once the first sealed `request_digest` exists, the ordinary K3 conflict rule remains the guard for everything after it — same material converges, different material conflicts and performs no effect (Spec v0.5 K3). The binding closes the pre-K3 window; K3 governs everything after it.
- A Conductor run identifier is doubly disqualified as an identity component: constitutionally, because K3 forbids caller identity authority; and factually, because P0 measured that `CONDUCTOR_RUN_ID` is not exported to script-step environments despite the documentation saying it is. It may travel as opaque diagnostic content inside `source_ref`/claim payloads; it never keys anything.

### 3.4 The three governed effects and their material bindings

All three re-use the v0.4 GitHub adapter contract of TD v0.4 §6.4 **byte-for-byte** — same materials, same idempotency/precondition rules, same COMMITTED / NO_EFFECT_CONFIRMED proofs. What is new is only who seals the request.

**Vocabulary split — two different "bases".** `candidate_base_sha` is the immutable provenance/input binding: it records which base revision the candidate was built and reviewed against, and it is what the §3.3 allocation tuple and the sealed `work_bindings` carry. `base_ref` is the mutable PR/merge target branch at the target. No existing adapter proves that `base_ref`'s current revision equals `candidate_base_sha` at effect time: `PR_CREATE`'s `base_ref` is a mutable branch that can move between seal and call, and the GitHub merge API's `sha` precondition is a CAS on the PR HEAD, never on the base branch.

| Effect | Material (TD v0.4 §6.4) | External-candidate binding rule |
|---|---|---|
| `GIT_PUSH` | `{repo_id, ref = refs/heads/cadp/candidate/<candidate_sha>, new_sha = candidate_sha, expected_old_sha = 0000…, bundle_cas_key}` | The proposer `put_blob`s a `git bundle` of the candidate; the PEP verifies the bundle reproduces **exactly** `candidate_sha` before pushing (TD v0.4 §6.6, §8.1). An external bundle is exactly as untrusted as a worker bundle was; the same verification makes it safe. The sealed request also binds `candidate_base_sha` as exact immutable input (rule below); the PEP's ancestry check runs against exactly that admitted `candidate_base_sha` (TD v0.4 §6.4) — bundle ancestry against the admitted base is target-state-independent and enforceable, so this effect's base discipline is complete as stated. |
| `PR_CREATE` | `{repo_id, base_ref, head_ref = refs/heads/cadp/candidate/<head_sha>, head_sha, title_cas_key, body_cas_key}` | `head_sha = candidate_sha`; write-once candidate ref shape enforced at admission (TD v0.4 §4.4 #14). The sealed request also binds `candidate_base_sha` as provenance (rule below). `base_ref` is the mutable target branch; this effect does not prove what revision it names at call time. |
| `PR_MERGE` | `{repo_id, pr_number, expected_head_sha, merge_method}` | `expected_head_sha = candidate_sha`; the target-native CAS rejects **head** drift only — GitHub's `sha` precondition is on the PR HEAD, never on the base branch. The sealed request also binds `candidate_base_sha` as provenance (rule below). |

For each of the three effects, `candidate_base_sha` and repository identity enter the sealed `EffectRequestV1` alongside `candidate_sha` as exact immutable bindings: `work_bindings` carries them as exact input identity + revision, covered by `request_digest` (Spec v0.5 K3), and equal by the §3.3 allocation-to-first-seal binding to the allocated values. This is the same exact-input discipline TD v0.4 §8.3 applies to the candidate subject in the development composition — equality over K4-bound sealed facts, decided by the evaluator; inequality = requirement unsatisfied, no K6 — extended to the base revision that composition already pins (worker workspace materialized at exactly `candidate_base_sha`, bundle ancestry checked against the admitted base; TD v0.4 §8.1, §6.4). What this binding proves is **provenance, not target state**: policy and reviewers evaluate against the pinned base the candidate was built and reviewed on; the binding does not — and no measured adapter can — pin the target branch's current revision at effect time. A policy that cares about the target's *current* base takes a fresh target observation (`base_ref` → current sha) into K4 as evidence and applies its drift rule there, evaluator-side (Spec v0.5 §2.4). Atomic exact-base-at-merge enforcement is a target adapter contract gap: `[UNMEASURED — probe required: no GitHub-native atomic base-branch CAS exists in the measured v0.4 adapter contract]`. Any ancestry rule (candidate descends from `candidate_base_sha`) is development-composition semantics per Spec v0.5 §7, evaluated by the evaluator over K4-bound facts — never new kernel vocabulary.

### 3.5 Re-homed unchanged

- **Broker push/PR actuation:** the credential-less bounded broker and PEP-held GitHub credential (TD v0.4 §4, §18.2) actuate; the proposer never touches a governed-target credential (§6).
- **Gate-file routing:** `touchesGateMachinery` (`cadp/product/gateFiles.ts`) applies to external candidates identically — a candidate touching kernel/policy/surface/conformance/constitutional-document paths routes to a `HUMAN_DECISION`, never a delegated agent merge.
- **Agent vs HUMAN merge decision:** the TD v0.4 §12 r9 `agent-surface` contract carries over — `AGENT_DECISION` satisfies only the merge gate, only for producers named in `delegated_merge_producers`, formed by a fresh isolated reviewer, honestly attributed. For an external candidate the carried-over r9 predicate is, and claims only, **proposer/reviewer separation**: a delegate that is, or shares an identity class with, the proposing `requester_ref` is refused. **Proposer/reviewer separation is not implementer independence** — and absent implementer evidence the independence requirement is simply **unsatisfied**, so machine merge fails closed. That is exactly the implemented `review_ok` / `agent_merge_ok` behaviour, and it needs **no new evidence kind** to enforce: both gates carry the `independent_product` leg, which requires `count(implementer_refs) > 0` (`cadp/deployment/referencePolicy.ts`), and under the reference composition an external candidate carries no `WORK_STEP` and no `surface-role` = `WORKER` `BACKEND_EXECUTION` evidence — neither kind being registered to any external producer (§3.2) — so the set is empty and the requirement is unsatisfiable by any reviewer or delegate. It needs **no new policy parameter** either: external machine merge is already closed by the implemented policy — empty `implementer_refs` fails `review_ok` closed, and `delegated_merge_producers` (`[]` in the reference parameters) independently gates the delegate list. The reference `policy_params` carries exactly `verification_max_age_s`, `max_effects_cap`, `max_steps_cap`, `require_backend_effort`, `require_external_verification`, `extra_plain_allow_operations` and `delegated_merge_producers` — nothing else — and nothing in this document adds to that set. Where an independence comparison is reached at all it is the implemented one: non-membership in `implementer_refs`, **AND** `identity_class.product` inequality against every member — the `product` component, never whole-object `identity_class` inequality, since a delegate sharing the implementer's `product` under a different `account` is exactly the self-merge the live self-approval fix closed.
### 3.6 The run-origin allocation schema

§3.3's external schema presumes **no** run-profile enrollment. This section owns the wire shape for the opposite case: the `WORK_START` that **originates** a run scope for an **enrolled** principal (Spec v0.5 §5.3; the seal-time adjudication is the Authority Plane TD's B5(10)). It changes nothing in §5 — a non-enrolled principal, which in the reference deployment is every Conductor principal (§5.2), allocates no run-origin tuple and acquires no run-profile semantics by presenting one.

<!-- RUN-ORIGIN BLOCK v1 — BYTE-IDENTICAL IN AP B1(5) AND WP §3.6; A DIVERGENCE BETWEEN THE TWO COPIES IS A CROSS-PLANE CONTRACT DEFECT -->

**`cadp.allocation-key.run-origin.v1` — the run-origin allocation schema.** Canonically owned by **WP §3.6**; **AP B1(5)** cites and consumes it and does not re-shape it, exactly as both documents already treat `cadp.allocation-key.external.v1` (WP §3.3 owns that wire shape; AP B1(3) restates it only to cite it). This block is **byte-identical in both documents by contract**.

**Wire shape — exactly three keys.** `cadp.allocation-key.run-origin.v1` = `{ schema, origin_key, purpose }`, and nothing else.

- `schema` and `purpose` are the **two reserved fields**, the only kernel vocabulary any tuple carries (AP B2(5)).
- `origin_key` is the schema's **single non-reserved field**, declared by the Workflow-Plane-authored descriptor entry `{ field: "origin_key", role: "ENTROPY", value_contract: "NONEMPTY_STRING" }` (AP B2(2)(i)).
- The schema's `allocation_schemas` entry carries **`binding_projection: []`** — it projects nothing onto any subject — and exactly **one** `purpose_relation` pair, composition-supplied and cited here as bundle data rather than enumerated as kernel vocabulary: `{ purpose: "work-start", operation_kind: "WORK_START" }` (Spec v0.5 §7; Design D7-4). The empty projection is the case AP B2(5) already provides for: it binds no material, and it weakens no other schema, being a **different, visibly-named schema id** whose tuples are its own contract. It is also not a bundle author's choice to make differently: `origin_key` is `ENTROPY`, so AP B2(2)(iii)'s descriptor-vs-mapping validation **refuses** at activation (`ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE`) any bundle that gives it a `binding_projection` entry. This block introduces **no new registry key, no new kernel field name and no new reason code**.
- The tuple carries **no `work_run_ref` and no `step_ordinal`**. Self-binding is deliberately **not** an allocation-time projection and cannot be one: the value the origin must bind is the `effect_id` the Platform derives *from this very tuple*, which does not exist while the tuple is being formed. Self-binding is verified **at seal**, by `is_run_origin` (AP B5(10)), against the request's own `effect_id` — a value no caller can propose (AP B1(2)).

**`origin_key` is a WORKFLOW-OWNED OPAQUE IDEMPOTENCY DISCRIMINATOR.** The Workflow side decides it **once**, when it creates a logical run origin, and preserves it **VERBATIM** across every retry of that origin. It identifies **one logical origin**, never the work's content:

- two **distinct** origins carry **distinct** `origin_key`s even when their work is byte-identical — the same repository, base revision and work item, or on the record path the same tenant and the same payloads — and therefore receive **distinct `effect_id`s**;
- a **retry** of one origin carries the **same** `origin_key` and therefore converges on the **same `effect_id`**, so a re-run creates no second logical run (AP B1(2)'s retry convergence; WP control 13).

**Why the discriminator is the ORIGIN and never the work's CONTENT.** A content fingerprint — `{repo_id, base_sha, work_item_digest}` or any variant of it — fails on both axes, and is rejected here for stated reasons rather than by preference. **(a) Collision.** Two genuinely distinct runs may legitimately share identical work content (the same work item re-run against the same base of the same repository), so a content tuple collapses them onto **one** `effect_id`; their differing sealed `WORK_START` material then makes the second seal a **`REQUEST_DIGEST_CONFLICT`** — an incident and a scope hold — rather than two runs. The differing material is not hypothetical: `bounds`, `worker_product`, `review_product` and `external_verification` on the development path, and `resource_prefix` and `payloads` on the record path, are all sealed args (`cadp/live/ops.ts`). **(b) Vertical non-generality.** The record vertical has **no** `repo_id`, no `base_sha` and no work item at all — its `WORK_START` args are exactly `{ tenant, resource_prefix, payloads }` (`cadp/live/ops.ts`, the record branch) — so a repository-shaped tuple is unfillable there, and the schema would be a development-vertical schema wearing a generic name. `origin_key` is product-generic: it applies unchanged to the development path, the record path and any future vertical, because it names the origin and reads none of the work. `work_item_digest` is therefore **dropped entirely**, and with it the question of which digest scheme would canonicalize a work item.

**Opaque to the Authority core; no effect-identity authority.** The core compares `origin_key` as a `NONEMPTY_STRING` and **never parses it** (AP B2(2)(i)); no kernel path reads its structure, and AP B2's generic projection machinery gains no operation-kind, vertical or domain knowledge from it. Nor does choosing one confer identity: the Platform derives the allocation key from `{ requester_ref, tuple, allocation_contract_digest }` (AP B1(2)), so a caller can neither self-select an `effect_id` nor land on another principal's identity — a different `requester_ref` derives a different key (WP control 2) — and gains nothing by choosing its `origin_key` adversarially.

**Derivation in the checked-out product — named, without over-constraining implementations.** The contract is only that the value is decided once per origin and reproduced verbatim; how it is formed is the Workflow side's.

- On the **workPlan** path the stable pair is already present: `workPlan` iterates a sealed `WORK_PROPOSAL`'s items with its `proposal_evidence_id` and the item's index in hand at each start (`cadp/live/ops.ts`), and that pair is canonically derivable into an `origin_key` by a collision-resistant or injective stable encoding as appropriate. It is stable across retries by construction — the proposal is sealed evidence and the index is positional.
- On a **direct CLI or MCP start** (`work-dev`, `work-record`, `cadp_work_start` — `cadp/live/ctl.ts`, `cadp/live/mcpServer.ts`) no such pair pre-exists: the caller **mints** an `origin_key` once at invocation and preserves it across every retry of that invocation, again by a collision-resistant or injective stable encoding as appropriate.

**LIFETIME-STABLE IDENTITY — the run-origin allocation contract is IMMUTABLE, so this schema is NOT contract-scoped.**

1. **The entry is frozen once first activated.** AP B2(2)(ii)'s cross-activation descriptor immutability — refusal `SCHEMA_DESCRIPTOR_CHANGED`, compared against the **sealed store** rather than against the currently active bundle, so nothing can be laundered by withdrawing it in one activation and re-adding it in the next — is extended, **for this schema id only**, to its `allocation_schemas` **mapping entry**: once any activation has carried `cadp.allocation-key.run-origin.v1`'s descriptor entry and mapping entry, **every later bundle MUST carry both byte-identically**. Changing either, or dropping either, is refused at genesis validation and at `POLICY_ACTIVATE` recheck #17 under **the existing refusal shape and the existing reason code**; no new code is added. The justification is exact and does not generalize: this entry has **no repointable projection** (`binding_projection: []`) and **one fixed purpose relation**, so it holds no content that could ever legitimately drift, and freezing it forecloses nothing a deployment could want. Honest consequence, stated rather than implied: once activated, this schema is a permanent fixture of that store, and a different run-origin contract requires a **different, visibly-named schema id**, gate-controlled, exactly as AP B2(2)(ii) already requires for a different wire shape.
2. **Therefore one `origin_key` maps to exactly one `effect_id` for the store's lifetime.** `allocation_contract_digest` is `sha256(cadp-jcs-1(allocation_contract_payload.v1))` over precisely those two entries (AP B2(1)); with both immutable it is **constant for the store's lifetime**, so AP B1(2)'s derivation over `{ requester_ref, tuple, allocation_contract_digest }` yields, for a given `requester_ref` and a given `origin_key`, **exactly ONE allocation key and therefore exactly ONE `effect_id`, permanently, under ANY activation sequence**. In particular the oscillation `C1 → C2 → C1` cannot fork an origin: for this schema there is no `C2` to reach, because the entry that would have to change cannot change, so no second first-sealable allocation for one `origin_key` — sealed or unsealed — can be brought into existence at all. This is not an exception to AP B1(2) and modifies nothing in it: B1(2)'s convergence qualifier — *under an unchanged active allocation contract* — is satisfied **by construction and permanently** for this one schema.
3. **No contract-drift recovery exists for this schema, because there is no drift to recover from.** The fresh-`effect_id`-on-contract-drift recovery of AP B1(2) / B2(3.3) / B2(9), and WP control 1's versioning-boundary leg, are properties of schemas whose allocation contract is legitimately **MUTABLE**: `cadp.allocation-key.external.v1`'s entry carries repointable `binding_projection` targets whose drift is a feature, and **that text is untouched by this block and remains exactly as it stands**. The asymmetry is the point — a mutable allocation contract buys retargetability at the price of a versioning boundary at which one logical request re-allocates; run-origin has nothing to retarget, so it buys nothing, pays nothing, and keeps a single lifetime-stable identity per origin instead. Correspondingly **no conformance leg of either document presents run-origin contract drift, or a run-origin re-allocation under a changed contract, as a correct observable**: the only run-origin activation leg is the immutability refusal (AP A4 leg o4; WP control 14).

**GENERAL REPLAY INVARIANT — for one logical origin, the sealed `WORK_START` MATERIAL must itself be byte-reproducible across retries.** Broader than the allocation key, and normative on the **Workflow side**: converging on the same `effect_id` is necessary and **not** sufficient. A re-seal of an existing `effect_id` is judged by K3 semantic equality over the sealed payload — `requester_ref`, `work_bindings`, `target_ref`, `operation_kind`, `material_schema`, `material_digest`, `material_ref`, `prior_effect_refs` (`cadp/kernel/ingress.ts`) — so a retry that converges on the right `effect_id` while re-deriving **different** material does not re-seal idempotently: it is `REQUEST_DIGEST_CONFLICT`, a `KERNEL_INCIDENT` and a scope hold (Spec v0.5 K3, §4.4). The origin path therefore **MUST fix the `WORK_START` args at first origin creation and reproduce them VERBATIM on every retry of that origin** — the bounds, the provider selections, and every vertical-specific field — and **MUST NOT derive any sealed-material field from the wall clock**, nor from any other value that varies between retries of one origin.

**Checked-out consequences, named as consequences: the implementation lane is later work and this block states the contract only.**

- `cadp/live/ops.ts`'s record branch derives its `resource_prefix` from the wall clock (`live-${Date.now() % 100000}`). That value enters the sealed `WORK_START` args, hence `args_digest` and the CAS'd material, hence `material_digest` — so it is **replay-unstable sealed material and is FORBIDDEN on the v0.5 origin path**: it must become a function of `origin_key`, or of another input that is stable across retries of one origin.
- The same file's development branch resolves `base_sha` freshly per invocation (`resolveBaseSha`, an `ls-remote` of the base ref). That is stable *within* one invocation and not *across* retries of one origin: if the base moves between retries the sealed material drifts and the same conflict follows. Under this invariant the base resolved at first origin creation is part of the origin's fixed args and is re-presented verbatim rather than re-resolved.
- The same file's wall-clock `step_ordinal` default (`Math.floor(Date.now() / 1000) % 1000000`) is **allocation-tuple** input rather than sealed material; on the origin path it is superseded outright, this tuple carrying no ordinal at all.

## 4. Evidence submission

### 4.1 Ingress and provenance honesty

External evidence enters as `EvidenceEnvelopeV1` through `submit_evidence`, under the full TD v0.4 §9.1 ingress discipline: `producer_ref` stamped from the authenticated principal; `provenance.integrity` set by the Ingress; `source_relation` checked against the policy-bound adapter registry. The consequence for orchestrator-relayed evidence is mechanical: **when an orchestrator submits a review it ran (the P0 case: a codex review executed inside the Conductor loop), the envelope's producer is the orchestrator's principal and its relation is at most `SELF_REPORT` of the orchestrator** — unless the platform can independently verify the actual producer (a signature the Ingress verifies against `data.cadp.attestation_keys`, sealing integrity `SIGNED_ATTESTATION` under the true producer, or the producer submitting directly as its own registered principal). Self-report is never promoted (Spec v0.5 §4.5); an honest `SELF_REPORT` review is recorded, and simply does not satisfy a gate requiring independence.

### 4.2 What the reference policy accepts for external candidates

The candidate-sha subject-equality rules of TD v0.4 §8.3 (C41 leg 1) apply unchanged — they are composition semantics now (Spec v0.5 §2.4, §7): a required `REVIEW`/`VERIFICATION` envelope satisfies the requirement only if its bound `repo_id + candidate_sha` equals the exact candidate the sealed material names; inequality is requirement-unsatisfied, no K6.

**Candidate-producer self-report is AUDIT TELEMETRY here, not a K2 evidence kind.** Proving reviewer ≠ proposer does not prove reviewer ≠ actual implementer (§3.5), but in this generation that gap is not closed by minting an evidence kind for it. A candidate producer's self-report of what produced the candidate MAY be recorded as **workflow/product audit telemetry** — orchestrator logs, the PR body, product records — and is **NOT a K2 evidence kind in this generation**. Design D7-3 is the fence: no evidence kinds whose only consumer is a workflow engine's internals; if no gate consumes it, it is orchestrator telemetry, not evidence. Today no effect requires such a kind, no independence gate consumes it, and the source that could prove producer-set completeness is `[UNMEASURED]` — zero current gate consumers, so pre-minting the K2 contract would violate the thinness fence. A K2 candidate-provenance contract is introduced **only** when a measured completeness-proving source — the Execution Plane `output_artifact_digest` binding chain (Spec v0.5 §6), `[UNMEASURED — probe required: the Execution Plane capture probe]` — creates an actual gate consumer. That future contract must then resolve, in order, four questions, stated here as **design constraints on it and as no machinery now**: (1) **who submits**, under which `producer_ref` and which registered `source_relation`; (2) how **producer-set completeness is proven rather than asserted** — no provenance label proves set completeness, strength and completeness being independent axes (a claim labelled `INDEPENDENT_OBSERVATION`, or carried under verified `SIGNED_ATTESTATION` integrity, that names `[P1]` for a candidate co-produced by P1 and P2 is strongly labelled and still incomplete); (3) how the **claim's author is excluded from the separation basis** that claim establishes, so the party authoring the basis is never the party it clears; (4) how **multiple or conflicting claims** are consumed deterministically, sealed history having no "latest" authority (Spec v0.5 §2.6).

**Per-effect evidence prerequisite matrix (normative).** Evidence can gate an effect only if it can exist before that effect: a GitHub Actions verification exists only after the candidate ref is pushed, so it cannot gate `GIT_PUSH`; a GitHub-native PR review exists only after the PR exists, so it cannot gate `PR_CREATE`. The reference policy gates per effect:

| Effect | Evidence the reference policy requires |
|---|---|
| `GIT_PUSH` | Only evidence obtainable pre-push: any policy-required pre-push `REVIEW` by a registered principal over the submitted bundle/candidate content. |
| `PR_CREATE` | May additionally require: the `GIT_PUSH` outcome `COMMITTED`, and a `PRESENT` `VERIFICATION` from `verifier:github-actions` bound to the exact pushed `candidate_sha` with `claim.conclusion == "success"`, `TARGET_AUTHORITY_OBSERVATION`, source-authoritative `produced_at` (TD v0.4 §18.3 fail-closed projection, unchanged; this producer observes the pushed ref at the target, so it is independent of whoever made the candidate by construction). |
| `PR_MERGE` | May additionally require: PR-created facts; a GitHub-native review read via API (subject = `commit_id`, compared by the evaluator) or a platform review of the pushed ref, satisfying the implemented implementer/reviewer independence predicate of §3.5 (an orchestrator-relayed review only under the §4.1 verification paths — as bare relay it is `SELF_REPORT` and does not satisfy); and `HUMAN_DECISION` (TD v0.4 §9.3 path A) or delegated `AGENT_DECISION` per §3.5. |

General rule — a **REFERENCE-POLICY AUTHORING INVARIANT, not a kernel or activation contract**: no machine-readable effect-to-required-evidence or evidence-to-prerequisite dependency graph exists in `cadp.kernel-config.v1`, and policy is Rego, so no current contract can statically decide satisfiability of an arbitrary policy at `POLICY_ACTIVATE` time — the kernel and `POLICY_ACTIVATE` make NO general satisfiability judgment. The invariant is enforced by the reference policy's own unit/conformance tests: no required evidence for effect E has E itself (or a later effect) as its producing precondition, and every required evidence kind has at least one registered `producer_ref` carrying it in `adapter_registry.evidence_kinds` (§3.2). Honest safety note: an unsatisfiable policy is still fail-closed — it admits nothing — so the invariant protects liveness, not safety. If activation-time refusal is ever wanted, it requires machine-readable prerequisite metadata defined in the Authority Plane TD — out of scope here.

### 4.3 Fail-closed default

Absent, stale, subject-mismatched, or `UNKNOWN` required evidence admits nothing (Spec v0.5 §2.5, §4.5). There is no "external candidates get a lighter gate" mode: an external candidate passes the same evaluator, the same fresh recheck, and the same gate-file routing as an internal one, or it does not pass.

## 5. Explicit non-enrollment in the run profile

### 5.1 Measured facts (P0, run `24919dde`, 2026-09-07)

Conductor's run receipts are local-file grade: an `events.jsonl` under `TMPDIR`, keyed by an 8-hex `run_id`; the run record is **deleted on normal completion**; a checkpoint is written only on failure by default.

### 5.2 The refusal

Run-scope validity grades by the K7 outcome of a `WORK_START` effect (Spec v0.5 §5.2): `COMMITTED` requires a target-authoritative receipt binding the exact effect (the measured v0.4 rule: a describe-read returning a memo matching `cadp_effect_id` and `cadp_args_digest` — TD v0.4 §6.4, C34). A TMPDIR file deleted on success, keyed by a local 8-hex identifier, cannot be that receipt: there is no target-authoritative `WORK_START` outcome to grade a Conductor run scope by K7, and after a normal completion there is no receipt at all. **Therefore the reference deployment enrolls no Conductor principal in the run profile. Conductor runs claim per-effect Kernel Conformance only — never the run profile.** This is a measured refusal, not a policy preference, and it is complete governance, not degraded governance: per-effect Kernel Conformance is the whole constitutional guarantee (Spec v0.5 §5).

Non-enrollment is symmetric and policy-bound (Spec v0.5 §5.1): the active policy simply does not name any Conductor principal among the enrolled `requester_ref`s, and the reference policy reserves run-scope binding for enrolled principals — a non-enrolled principal **cannot acquire run-profile semantics by presenting a `work_run_ref`**. What non-enrollment costs is stated, not hidden: no `MAX_EFFECTS_IN_WORK_RUN`, no `WORK_STEP` chain requirements, no bound-stop semantics for these runs.

### 5.3 Revisit conditions

Enrollment could be revisited only on new measurement: `[UNMEASURED — probe required: a target-authoritative run receipt from the orchestrator — durable across normal completion, correlatable to a Platform-sealed WORK_START effect_id by a target-returned binding (memo-equivalent), and readable by the Reconciler after restart. Absent all three properties, K7 grading of a Conductor run scope remains impossible and non-enrollment stands.]`

## 6. Credential custody at the client (measured)

P0 measured that a Conductor `working_dir` is **not a sandbox**, and that `claude-agent-sdk` loads the working directory's settings as a trust boundary. The consequence is the Spec v0.5 §2.3 rule with no softening: **no governed-target credential may exist anywhere an orchestrator's working directory or settings can reach.** Credential custody stays entirely PEP/broker-side (TD v0.4 §4.1, §18.2: the GitHub credential is PEP-held; the broker is credential-less toward the kernel; workers cannot `admit_and_dispatch` — matrix reach notwithstanding, the worker class cannot even seal requests). The only CADP/governed-effect credential an effect-proposer environment holds is its own Kernel API principal identity, which grants no effect authority by §3.2. A deployment that places a governed-target token in a Conductor working directory has left Kernel Conformance for every effect that token can reach, whatever this document says.

## 7. Conformance controls (falsification additions)

In the Spec v0.5 §9 spirit — proven by attempting the violation:

1. **Replay convergence:** the same external principal re-calling `allocate_effect_id` with the same `cadp.allocation-key.external.v1` tuple **under the same active allocation contract** (the schema's `allocation_schemas` entry unchanged — see the Authority Plane TD) receives the same `effect_id`; after an activation that changes that entry, the same call derives a fresh `effect_id` under the new contract, by design, and a replayed `GIT_PUSH` on that `effect_id` produces exactly **one** push/ref effect at the target (counted at the target, TD v0.4 §13 method). The control asserts no PR count, because under the current reference composition there is no PR to count: control 12 establishes that an external candidate is EXPECTED to DENY at `PR_CREATE`, so the target carries **zero** PRs for it and a one-PR assertion would be unsatisfiable — the two controls would contradict. The PR leg is therefore **scoped as a future leg, asserted of no deployment today**: under a future reference-composition delta that makes `PR_CREATE` admissible for external candidates (i.e. one supplying a known implementer basis — see control 3), the same replay must additionally show exactly one PR at the target by the same counting method.
2. **Identity-squatting refusal:** a different principal submitting the same tuple receives a different `effect_id` and cannot conflict the first principal's request.
3. **Relayed-review honesty:** an orchestrator-relayed review seals as `SELF_REPORT` of the orchestrator principal and a gate requiring independent review DENYs; the same review submitted by the reviewer's own registered principal (or attested per §4.1) admits **only with all other gate predicates satisfied, including a known independent implementer basis** (`count(implementer_refs) > 0`, `cadp/deployment/referencePolicy.ts`). The current reference composition provides no such basis for an external candidate (control 12: `implementer_refs` is empty, so `independent_product` and `review_ok` are false however the review arrives), so the **admit leg is likewise scoped to a composition where that basis exists**; the **DENY-on-relay leg is runnable today** and is the leg this control exercises against the reference deployment.
4. **Subject inequality:** review/verification bound to candidate A does not admit an effect naming candidate B (C41 leg 1 rerun against the external client).
5. **Opt-in refusal:** a non-enrolled principal's request carrying a fabricated `work_run_ref` is refused (Spec v0.5 §9.2 negative control, external edition).
6. **Gate-file guard:** an external candidate touching a `GATE_PATH_RULES` path cannot be merged by `AGENT_DECISION`.
7. **First-seal candidate binding:** an `effect_id` allocated for candidate A whose first `seal_effect_request` names candidate B is REFUSED — no `EffectRequestV1` sealed, no effect (§3.3 allocation-to-first-seal binding).
8. **First-seal base binding:** an `effect_id` allocated with `candidate_base_sha` X whose first seal names base Y is REFUSED.
9. **First-seal purpose binding:** an `effect_id` allocated with purpose `pr-create` whose first seal names `operation_kind` `PR_MERGE` is REFUSED (§3.3 closed `allocation_purposes` correspondence).
10. **First-seal principal binding:** principal B first-sealing an `effect_id` allocated to principal A is REFUSED.
11. **Unsatisfiable-authoring refusal (reference-policy tests, not activation):** the reference policy bundle's own authoring/conformance tests reject a requirement that is cyclic — e.g. requiring, for `GIT_PUSH`, the `verifier:github-actions` `VERIFICATION` of the pushed candidate, evidence whose producing precondition is the `GIT_PUSH` itself — and a requirement whose evidence kind no registered `producer_ref` carries in `adapter_registry.evidence_kinds` (§4.2 general rule). The control tests those authoring tests; it does NOT claim an activation-time refusal by the deployment — `POLICY_ACTIVATE` makes no satisfiability judgment.
12. **External-candidate `PR_CREATE` fail-closed (the §3.2 boundary guarantee, falsified):** an external candidate that entered the boundary correctly — allocated, sealed, with a source-authoritative `VERIFICATION` bound to its exact `candidate_sha` and an `APPROVE` `REVIEW` submitted by a registered reviewer principal over that same sha — is nonetheless **DENYed at `PR_CREATE`** under the reference composition, carrying `review_missing_or_wrong_subject` and `required_fact_unknown` among its reason codes: `implementer_refs` is empty (no `WORK_STEP`, no `surface-role` = `WORKER` `BACKEND_EXECUTION`), so `independent_product` and therefore `review_ok` are false, and `backend_model_present` is false (`pr_create_ok`, `cadp/deployment/referencePolicy.ts`). The control asserts this DENY as the CORRECT outcome — the boundary contract promises ingress, never admission — and asserts the negative form of the liveness claim: no `PR_MERGE` becomes reachable for such a candidate, so no `HUMAN_DECISION` merge path is offered to it.
13. **Run-origin replay convergence, identity-not-content, and material reproducibility (§3.6):** the same enrolled principal re-calling `allocate_effect_id` with the same `cadp.allocation-key.run-origin.v1` tuple — the same `origin_key` — receives the **SAME `effect_id`**, **unconditionally and with no active-allocation-contract qualifier**: this schema's allocation contract is immutable (§3.6), so no activation sequence exists under which one `origin_key` derives a second allocation key. Two **distinct** origins over **byte-identical work content** — the same repository, base and work item on the development path, or the same tenant and payloads on the record path, where no repository, base or work item exists at all — carry distinct `origin_key`s and receive **DISTINCT `effect_id`s**, so identical work never collapses two runs onto one identity. The retry re-presents the origin's **fixed** `WORK_START` args verbatim, so its re-seal is idempotent: exactly **one** `effect_request` row, **one** run scope, **one** `WORK_START` effect counted at the target. Negative leg, asserted as the **prohibited** outcome and not a sanctioned one: a retry that re-derives any sealed-material field from the wall clock — the record vertical's `resource_prefix` shape (`cadp/live/ops.ts`) — instead produces `REQUEST_DIGEST_CONFLICT` with an incident and a scope hold, which is exactly what the §3.6 replay invariant forbids the origin path from constructing.
14. **Run-origin allocation-contract immutability (§3.6):** `POLICY_ACTIVATE` a bundle that changes `cadp.allocation-key.run-origin.v1`'s `allocation_schemas` entry — or its descriptor — under the **same** schema id ⇒ **REFUSED `SCHEMA_DESCRIPTOR_CHANGED`**, zero activations, active policy unchanged. Positive control, so the refusal is attributed to the change and not to the bundle: the same bundle carrying both entries byte-identically **activates**. Guard-bite: remove the immutability and that bundle **ACTIVATES**, after which `C1 → C2 → C1` forks one logical origin — an unsealed allocation E1 made under C1, a fresh E2 allocated and first-sealed under C2, then a restore to C1 under which the stale E1 first-seals too: **two** run scopes, both valid origins, for **one** `origin_key`. This control does **not** touch `cadp.allocation-key.external.v1`, whose allocation contract remains legitimately mutable and whose versioning-boundary leg (control 1) is unchanged.
