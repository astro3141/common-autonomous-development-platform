### A.2 The cross-plane surface — exact pointers

This plane **produces** envelopes; it never decides what an envelope satisfies, and it holds no Kernel API authority beyond submitting evidence as its registered producers. Four contracts cross the boundary, all of them the Authority Plane's under **AP Part A, §9 row** (evidence ingress and provenance: producer stamping, Ingress-set integrity, adapter-registry-checked `source_relation`, untouched `claim`, source-time-authority derivation, non-policy `received_at`, derived `identity_class`, K4 completeness):

1. **Envelope subject bindings.** The `work_run` / `step` / `surface-role` bindings this plane's evidence carries (`cadp/product/backendExecution.ts`) are ordinary `SubjectBinding`s under Spec v0.5 K2/§2.4; their shape, uniqueness and kernel-namespace rules are AP's (AP B3(4) for declared kernel namespaces; AP B2(3.4) for projected pairs). This document adds exactly one binding, in B1, and adds no namespace to any kernel lookup.
2. **`produced_at` sourcing.** Per-producer, from `adapter_registry.produced_at_source`: `{kind: NONE}` for `backend-scan:*`, `{kind: SOURCE, claim_pointer: /completed_at}` for `verifier:github-actions` (`referencePolicy.ts`). A producer here never chooses its own time authority.
3. **Locator rules.** Every `PRESENT` observed field must carry a locator; the Ingress refuses `OBSERVED_WITHOUT_LOCATOR` otherwise (`cadp/kernel/ingress.ts` `assertBackendObservedLocators`; TD v0.4 C13). This plane supplies locators; it does not enforce them.
4. **Producer registration.** Which `producer_ref` may submit which `evidence_kind` under which `source_relation` lives in `adapter_registry` and changes only by `POLICY_ACTIVATE` (TD v0.4 §9.4; WP §3.2). A surface cannot acquire an evidence kind by being an execution surface.

## PART B — NEW v0.5 CONTRACTS

Exactly three. None is a constitutional record; all three are product-service contracts of an **optional** plane.

### B1. The symmetric execution contract (Spec v0.5 §6)

**Seam today.** The broker transport carries per-operation bodies with no digest discipline: `brokerImplement({repo_full_name, base_sha, work_item, worker_product})`, `brokerReview({repo_full_name, candidate_sha, work_item, review_product?})`, `brokerPlan({repo_full_name, base_sha, intent, plan_product?})` (`cadp/product/surfaceBroker.ts`, dispatched through `BROKER_OPERATIONS` / `cadp/product/brokerTransport.ts`). The result side is likewise asymmetric: `brokerImplement` returns `{candidate_sha, bundle_b64, backend_provider, backend_model?, backend_locator?, backend_effort?, …}` — an artifact and observed facts, but **no digest of the artifact**. The contract below is therefore contract-new on both sides; it describes no measured mechanism.

1. **`ExecutionRequest` — a product API contract, not a K-record.** `cadp.execution-request.v1` is **a common header plus a role-specific exact-input block**. It is not one flat shape, because the three implemented entry points are **not handed the same revision**: `brokerReview({repo_full_name, candidate_sha, work_item, review_product?})` receives a `candidate_sha` and **no `base_sha` at all** (`cadp/product/surfaceBroker.ts`), so a common `base_revision` field is one the reviewer role could only fill by re-deriving a value it was never given — which the no-re-derivation rule below forbids. Every field below maps to an argument an implemented broker function **already takes**; that mapping, cited per field, is the whole warrant for the field existing.
   - **COMMON HEADER — `{ schema, surface_role, provider, executor_profile_digest, repo_id }`**, well-defined for all three roles:
     - `surface_role` ∈ `WORKER | REVIEWER | PLANNER` — the existing §19.5 vocabulary, already carried as the `surface-role` binding's `object_id` (`submitBackendExecutionEvidence`, `backendExecution.ts`).
     - `provider` is the closed-union name the resolvers admit — the `worker_product` / `review_product` / `plan_product` argument of `brokerImplement` / `brokerReview` / `brokerPlan` after resolution (`resolveReviewProvider`, `resolvePlanProvider`, `surfaceBroker.ts`); an unknown name fails closed with no filesystem, process, docker or network side effect (§17.1, unchanged).
     - `executor_profile_digest` is a digest over the **resolved provider profile entry** — argv template, auth descriptor, scan fields, `identity_class_product` — i.e. the argv identity of §17.1. It does **not** exist today and is **not** `workerProfileDigest` (`cadp/product/workerProfile.ts`), which digests the constructed auth sandbox; the two are distinct objects and must not be conflated.
     - `repo_id` is exactly the `repo_full_name` argument all three functions already receive.
   - **ROLE-SPECIFIC EXACT INPUTS — `WORKER` and `PLANNER`: `{ base_revision, input_digests: [{ input_role, digest }] }`.** `base_revision` is exactly the **`base_sha` argument `brokerImplement` and `brokerPlan` already receive** and materialize the workspace at (`git checkout --quiet <base_sha>`, both functions) — the same exact base revision the boundary calls `candidate_base_sha` (WP §3.4), carried unchanged. It binds provenance, never target state; this document redefines neither, and it stays the declared field it already is rather than dissolving into `input_digests`.
   - **ROLE-SPECIFIC EXACT INPUTS — `REVIEWER`: `{ candidate_revision, input_digests: [{ input_role, digest }] }`.** `candidate_revision` is exactly the **`candidate_sha` argument `brokerReview` already receives** and checks out. The reviewer request carries **no `base_revision`**, because the broker is never handed one — the asymmetry is in the implemented signature and this contract mirrors it rather than papering over it. (`brokerReview` does compute a fork base for its diff — `git merge-base origin/main <candidate_sha>` — but that is a *derived* value built for prompt construction, and it is deliberately **not** promoted into this contract: promoting it would be precisely the re-derivation the sealed-input rule below forbids — though the prompt bytes it feeds are digested, in the surface layer of the next bullet, which is where a derived value belongs.)
   - **`input_digests` — TWO DECLARED LAYERS, because the caller's inputs are NOT the surface's inputs.** No surface is handed the caller's arguments as-is. `brokerReview` **builds** the prompt the reviewer actually receives: `git merge-base origin/main <candidate_sha>` (falling back to `origin/main` when it fails or is empty) → `forkBase`, then `git diff --stat --patch <forkBase> <candidate_sha>` truncated at 60 000 chars, wrapped in the broker's own instruction text (`surfaceBroker.ts`). `brokerPlan` builds it as `buildPlanPrompt(intent, repo_full_name, base_sha)` (`cadp/product/planner.ts`). Byte-identical caller inputs therefore yield **different surface bytes** when `origin/main` moves under the merge-base, when the diff crosses the truncation bound, or when prompt-building code changes — so a caller-inputs-only digest is not the *exact input digests* Design D1.2 requires. `input_digests` is accordingly a list over a **CLOSED** `input_role` literal set — exactly `work-item`, `intent`, `surface-prompt`, `workspace-revision`, and nothing else — declared in two layers:
     - **CALLER INPUTS.** `work-item` — the `work_item` string exactly as handed to `brokerImplement` / `brokerReview` (`WORKER`, `REVIEWER`); or `intent` — the `intent` string exactly as handed to `brokerPlan` (`PLANNER`). Both arrive as plain strings today and the broker digests neither.
     - **SURFACE INPUTS.** `surface-prompt`, **REQUIRED for every role**: the exact final prompt string the broker hands the surface — the reviewer's built prompt, the planner's `buildPlanPrompt` output, and for `WORKER` the `work_item` as substituted at `WORK_ITEM_SENTINEL` into the profile's argv template (`workerArgv`, `cadp/product/workerProviders.ts`), where it equals the caller string at this checkout and the template around it is covered by `executor_profile_digest`, not duplicated here. Plus `workspace-revision` for the roles that materialize a workspace the surface reads: `WORKER` and `PLANNER` mount the tree checked out at `base_sha`, so each declares one, and it MUST equal the role's `base_revision` field — a broker that materialized a tree other than its declared revision is malformed, and the entry is the surface layer's record of what the surface actually read, not a second source for it. `brokerReview` mounts a **fresh empty `review-ws`** and keeps its candidate checkout broker-host-side purely for diff construction (`surfaceBroker.ts`), so `REVIEWER` declares **no** `workspace-revision` entry.
     - **Encoding, pinned so the request's own canonical digest is implementable identically everywhere.** Every entry digests the **UTF-8 raw bytes of the exact string handed over** (the revision entry over its 40-character sha string), under `{sha256, raw-bytes-1}` from `data.cadp.approved_digest_schemes` (`referencePolicy.ts`); entries appear in the literal order of the closed set above; no role emits an `input_role` outside the set, and none omits one the layers above declare for it.
     - **Consequence, stated approvingly.** The `ExecutionRequest`'s own `cadp-jcs-1` canonical digest — and therefore the execution-output `object_id` prefix of (2a) — **changes whenever the surface-visible bytes change**, including a merge-base drift or a prompt-template edit under byte-identical caller arguments. That is what *exact* means: two executions the caller cannot tell apart are two distinct requests when the surfaces saw different bytes.
   - **Relation to the sealed inputs, for every role.** The Execution Plane digests **what it was handed** and, in the caller layer, re-derives nothing: the role's revision field MUST equal the revision the sealing composition already pinned for that run, and the work-item / intent digest MUST be over the exact string that run sealed. Whether a sealed effect's material and an execution envelope agree is decided by the evaluator over K4-bound facts (Spec v0.5 §4.3), never here.
2. **`ExecutionResult` — output-bound for EVERY role.** `cadp.execution-result.v1` = `{ schema, surface_role, provider, output_artifact_subject, output_artifact_digest, output_artifact_locator, observed: { model, effort, provider, run_id, version } }`. `observed.*` is the existing scan payload, unchanged (`backendExecution.ts`). **A success result MUST carry all three output fields — `output_artifact_subject`, `output_artifact_digest` AND `output_artifact_locator`.** Missing any one makes the result **MALFORMED**: the broker refuses to return it, the activity refuses to construct anything from it, and **no `BACKEND_EXECUTION` envelope is sealed at all**. There is no "or none" leg, no placeholder, and no envelope carrying a partial binding. A contract calling itself *symmetric and output-bound* while letting one role return no artifact would be neither, so the per-role artifact is **pinned here, now** — subject, canonical bytes, digest scheme, locator — grounded in what the implemented broker **already holds**, so that the capture probe of (4) measures **MECHANISM only** and decides no design. In all three cases the digest is computed by the **BROKER as observer over bytes the broker already possesses**; it is never read from the surface's session log or from stdout-as-self-description, and never accepted as a value the model states about itself.
   - **`output_artifact_subject` — why the RESULT must transport the finished subject.** The topology forces it. The activity host holds the Kernel tokens and constructs and submits every envelope; the broker holds **no** Kernel token and seals nothing — it "returns raw observed data and the activity submits every evidence envelope here with its Kernel tokens" (`cadp/product/activities.ts` header; `submitBackendExecution` → `submitBackendExecutionEvidence`). But the attempt identity of (2a) exists **only inside the broker**: `runBoundedSurface` mints it and returns it as `RunResult.container` (`isolation.ts`), and **no broker function returns it across the transport at this checkout** (`brokerImplement` / `brokerReview` / `brokerPlan` return types, `surfaceBroker.ts`). The sealing party therefore **cannot derive** this subject from anything it receives. So `output_artifact_subject` = `{ authority_ref, namespace, object_id }` — the **COMPLETED** product-side subject, constructed by the **broker**, which is the one place that holds both components: identity is decided in exactly one place. The activity copies it **VERBATIM** into the envelope's subject binding with `content_digest = output_artifact_digest`; it re-derives nothing and may not alter, normalize, re-order or re-mint any component. Honest delta: this field does not exist at this checkout, and it is the only bridge across the broker/sealer boundary for the identity.
   - **`WORKER` — artifact bytes = the candidate `git bundle` bytes the broker itself generates.** Canonical bytes: the bundle file the broker creates and reads back (`git bundle create <path> cadp-candidate` → `readFileSync(bundlePath)`, surfaced as `bundle_b64`, `surfaceBroker.ts`) — a byte stream in the broker's own hands, which the composition then puts into CAS (`client.putBlob(Buffer.from(impl.bundle_b64, "base64"))` → `bundle_cas_key`, `cadp/product/activities.ts`). Subject: **the execution-output subject of (2a)**, identical in rule to the other two roles. The candidate **commit is not this binding's subject**, and `git rev-parse HEAD` supplies no part of it: a bundle containing commit C is not commit C's bytes, so putting the commit's identity in `object_id` and the bundle's digest in `content_digest` would be exactly the two-object mix this document forbids on the reviewer side. The candidate-commit **RELATION** is carried where it already lives — the sealed `GIT_PUSH` material, which names `new_sha`/`candidate_sha` and `bundle_cas_key` **side by side** (`buildMaterial`, `activities.ts`), plus the existing `github.com|commit` bindings the `REVIEW`, `VERIFICATION` and external-verification envelopes already carry over that same sha (`activities.ts`) — and is compared **explicitly by policy** per Spec v0.5 §2.4, never smuggled into the artifact binding.
   - **`REVIEWER` — artifact = the captured verdict stdout bytes.** Canonical bytes: `review.stdout` exactly as the broker captures it from the surface (`brokerReview` returns it), under the **measured** per-provider output contracts already implemented — `parseReviewVerdict`'s exact `APPROVE` / `REQUEST_CHANGES` first line, and the `--json-schema` path for grok's measured glued-narration case (9th pilot). Identity (`object_id`): **the execution-output identity pinned in (2a) below**, exactly as for the other two roles. It is **NOT** the reviewed candidate. This distinction is stated explicitly because the tempting alternative is false: binding `object_id` to the reviewed `candidate_sha` in the `commit` namespace with the verdict bytes as `content_digest` would assert that those bytes **are the content of that commit**, which they are not. The binding of a verdict to the candidate it reviews **already exists and stays exactly where it is** — the REVIEW evidence's own `commit` subject binding (`cadp/product/activities.ts`) — and the artifact binding does not overload it.
   - **`PLANNER` — artifact = the captured proposal stdout bytes**, whose digest the broker **ALREADY measures**: `stdout_digest: sha256(run.stdout)` in `brokerPlan` (`surfaceBroker.ts`). This is **the one measured output-artifact capture that exists at this checkout**, and it is cited as such; worker and reviewer capture mechanics are the remaining **unmeasured** probe scope (4). Identity (`object_id`): **the execution-output identity pinned in (2a) below**, the identical rule under the identical reason. Honest delta, since the measured value is not yet the contract value: today `stdout_digest` is a bare hex string, not a typed `Digest`; this contract requires it typed.
   - **(2a) THE PINNED OUTPUT-ARTIFACT SUBJECT FOR ALL THREE ROLES — ONE RULE, NO EXCEPTION.** Unifying the worker onto this rule is the **thinner** outcome, not a widening: one subject rule, three roles, no role-specific carve-out, and no binding anywhere in this plane that names one object while digesting another. The output-artifact subject binding for every role's result is exactly `{ authority_ref: "cadp-store:k04", namespace: "execution-output", object_id: "<the ExecutionRequest's cadp-jcs-1 canonical digest>/<the broker-minted execution attempt identity>" }`, with `content_digest` = the `output_artifact_digest` as already specified. Each part is fixed, not offered: **`authority_ref`** is `cadp-store:k04`, the broker-minted authority this plane's evidence **already carries** on its own `surface-role` binding (`submitBackendExecutionEvidence`, `backendExecution.ts`) — never a target-served authority like `github.com`, because no target serves these bytes. **`namespace`** is `execution-output`, a product-side subject namespace this plane mints for exactly the artifacts that have no native identity; it enters no kernel lookup (the kernel constrains no namespace in `validSubjectBindings`, and `assertBackendSurfaceRole` filters on `surface-role` alone — `records.ts`, `ingress.ts`), and it is declarable under AP B4 only if and when a composition names it. **`object_id`** is a **two-component identity**, both components broker-held before any seal:
     - **The request-digest prefix** is the **`cadp-jcs-1` digest of the role-specific `ExecutionRequest` of (1)** (`jcsDigest`, `cadp/kernel/canonical.ts`; `{sha256, cadp-jcs-1}` is an approved scheme in the reference config, `referencePolicy.ts`). It carries the **reference semantics**: it names *which execution request* this artifact answers.
     - **The attempt suffix** is the **container identity the broker already mints per surface execution**: `runBoundedSurface` constructs `cadp-surface-<kind>-<randomUUID()>` **before** it creates the surface and returns it as `RunResult.container` (`cadp/product/isolation.ts`) — for **every** surface this plane runs, since `runWorker` and `runReviewer` both delegate to it (`kind: "worker"` / `"reviewer"`), so `brokerImplement`, `brokerReview` and `brokerPlan` alike hold it from surface start through capture (`surfaceBroker.ts`). Nothing is invented for this slot: the identity exists in this checkout, is minted **by the broker at the moment it starts that execution**, is v4-UUID-unique per attempt, and no byte of it is ever supplied or echoed by the surface. **Honest delta**, since the field is not yet load-bearing: `container` is typed **optional** on `RunResult` (`isolation.ts`), so this contract requires the broker to treat a result lacking it as **not well-formed** — no artifact binding is constructed and nothing is sealed — the same fail-closed discipline (2) already applies to a digest without its locator.
     - Together the subject reads **"the output of attempt A of execution request R"**: the prefix preserves the reference semantics the request digest alone carried, and the suffix supplies the per-execution uniqueness (2b) now claims outright. `/` is the separator because the store's subject key is `<authority_ref>|<namespace>|<object_id>` (AP B4(2)), so it cannot collide with that key's own delimiter, and `object_id` is an unconstrained non-empty string in the kernel (`validSubjectBindings`, `records.ts`).

     **The same rule serves any future role too**; nothing in it is role-specific, which is precisely why the worker needs no exception from it. **An evidence id could not have served the attempt slot at all**, which is why no such option survives: `evidence_id` is allocated by the Ingress at submission (`newId("evidence", …)`, `cadp/kernel/ingress.ts`), so it does not exist at the moment the envelope's **own** subject bindings are constructed — an identity that cannot be derived before the seal is not an identity this binding can carry, whereas the container identity is derivable at surface start.
   - **(2b) The digest-as-name objection, answered — the distinction is load-bearing.** (3) forbids carrying **an artifact's own content digest as its name**, because such a subject passes exact-subject equality on a string comparison while engaging no content binding at all. The pinned `object_id` is not that object: its prefix is the digest **of the request**, and the request is a **different object** from the artifact whose bytes `content_digest` binds; its suffix is not a digest of anything. The artifact's own digest therefore appears in **`content_digest` and nowhere else**, so the content binding is not collapsed into the name — the binding still carries both an identity to match on and a typed digest to verify with, identically for all three roles. The identity is further (i) **derivable BEFORE any seal in both components**: the broker holds the very request it is executing and canonicalizes it with no allocation round-trip and no target read, and it mints the attempt identity at surface start and holds it through capture, so the whole `object_id` exists before a byte is sealed; (ii) **broker-assigned, never surface-asserted** — no byte of either component comes from the model's stdout or session log; and (iii) **COLLISION-FREE PER EXECUTION.** Two executions differing in any canonicalized request field (role, provider, `executor_profile_digest`, `repo_id`, revision, input digests) differ in the **prefix**. Two executions of a **byte-identical** request — an ordinary retry of the same work item at the same revision through the same profile, the case the prefix alone could not separate — differ in the **suffix**, because each attempt mints its own container identity. **No two executions ever share this `object_id`**, so no `object_id` this plane produces can carry two different `content_digest`s: one identity claiming two contents is exactly the ambiguity the identity/content split exists to prevent, and the attempt component is what makes the claim TRUE rather than disclaimed.
   - **(2c) Retry semantics, stated rather than implied.** Two attempts of one logical request are **two DISTINCT artifacts with distinct identities and their own content bindings**. They are **append-only observations that never contradict each other**, because no identity is shared: a nondeterministic surface emitting different verdict or proposal bytes on a retry produces a **second subject**, not a second and conflicting claim about the first. Each such subject names a completed attempt whose bytes are fixed at capture and never re-observed under that name, and the binding carries its `content_digest` regardless, so the Spec v0.5 K2/§2.4 rule — a mutable subject cannot be claimed exact without its content binding — is satisfied on either reading of the subject's mutability. The retry question therefore moves to where it belongs: **a consumer that wants "the" output of a logical request MUST select an attempt through the envelope it trusts**, never by matching the request-digest prefix alone and never by taking the most recent. That is no new burden — it is the same discipline sealed history already imposes everywhere else: **"latest" is not authority** (Spec v0.5 §2.6; TD v0.4 §6.6), which is exactly why AP B4(2) forbids `latestEvidenceOfKind` for assembly and requires the complete set for a subject key. Envelopes stay independently distinguishable besides: each carries a distinct Ingress-allocated `evidence_id` and `received_at` (`cadp/kernel/ingress.ts`), with the caller's per-run bindings riding alongside (`work-run` / `step` on the worker/reviewer path, `cadp/product/activities.ts`; `work-intent` / `repo-base` on the planner path, `cadp/live/ops.ts`). The attempt component **imports no other plane's identity domain**: it is the Execution Plane's **own product-side container identity**, not the orchestrator's run or step reference — which the broker is still handed none of (`brokerImplement` / `brokerReview` / `brokerPlan` take no run or step argument, `surfaceBroker.ts`) and now demonstrably does not need.
   - **All three:** `algorithm` / `canonicalization` come from `data.cadp.approved_digest_schemes` — at this checkout `{sha256, raw-bytes-1}` for all three, each artifact being a raw byte stream and `raw-bytes-1` being an approved scheme in the reference config (`referencePolicy.ts`). `output_artifact_locator` is the **broker-side observation locator** for that digest, of the `broker-response#…` shape the broker already uses for the one field it observes rather than scans (`observed.provider.locator = "broker-response#backend_provider"`, `backendExecution.ts`), satisfying the existing OBSERVED_WITHOUT_LOCATOR rule (§A.2(3)) without any ingress change. Subject, digest and locator are **all three REQUIRED on success**, per (2): any one missing is a malformed result that seals nothing.
3. **How it binds into the evidence envelope — two halves, no new kernel field.** `SubjectBinding` at this checkout is `{ authority_ref, namespace, object_id, revision_or_version?, content_digest? }` (`cadp/kernel/records.ts`), where `object_id` is the subject's **identity** (*which* artifact) and `content_digest` is its **content binding** (*which exact bytes*, as a typed `Digest {algorithm, canonicalization, value}`). It carries **no locator slot**, and this document adds none. The digest and its provenance therefore land in the two carriers that already exist:
   - **Subject identity and content, each in its own field.** Exactly one added binding, appended alongside the existing `surface-role` binding by the same activity that already constructs these envelopes (`submitBackendExecutionEvidence`, `backendExecution.ts`). Its `object_id` is never a value the surface states **and never a value the sealer derives**: the activity copies `output_artifact_subject` **verbatim** per (2), so for **all three roles, with no exception**, the binding is `{ authority_ref: "cadp-store:k04", namespace: "execution-output", object_id: "<the cadp-jcs-1 digest of that role's ExecutionRequest>/<that execution's broker-minted attempt identity>", content_digest: <the output_artifact_digest> }`. **No role's artifact binding is `github.com|commit`.** The reviewer's and planner's bytes are the content of no commit; and the worker's bundle bytes are not the content of the candidate commit either — a bundle containing commit C is not commit C's bytes, so naming the commit while digesting the bundle would mix two objects in one binding exactly as the reviewer case does. Each role's tie to the candidate stays **where it already lives and is untouched here**: the sealed `GIT_PUSH` material naming `new_sha`/`candidate_sha` and `bundle_cas_key` side by side (`buildMaterial`, `cadp/product/activities.ts`), and the `github.com|commit` bindings the `REVIEW` and `VERIFICATION` envelopes already carry over that sha (`activities.ts`, `cadp/live/intakeDriver.ts`) — with any relation between artifact and commit decided **explicitly by policy** over K4-bound facts (Spec v0.5 §2.4, §4.3), never inferred from a shared `object_id`. `content_digest` is the **`output_artifact_digest` itself**, typed, under a scheme in `data.cadp.approved_digest_schemes` (TD v0.4 §2 — approved schemes govern every new write and must keep verify-on-read computable; AP Part A §2 row, which owns the canonicalization set and the write/read-validation and verify-on-read discipline). **The digest is never an `object_id`**, in this binding or any other this plane produces: a digest carried as a *name* would pass exact-subject equality on a string comparison while engaging neither the approved-scheme discipline nor verify-on-read, so a subject with no content binding at all would satisfy the Spec v0.5 K2/§2.4 rule that a mutable subject without its required digest cannot be claimed exact — the content binding defeated by putting it in the identity field. **Two layers, both obligatory — and an implementation gap NAMED, not absorbed.** (i) The Execution Plane MUST **construct** every `content_digest` it produces under an approved scheme — this plane's own obligation and control C1's falsification target. (ii) The Authority ingress MUST **independently reject** a `SubjectBinding.content_digest` carrying an unapproved scheme, under the **inherited** TD v0.4 §2.1 rule the Authority Plane re-homes verbatim (AP Part A, §2 row): `data.cadp.approved_digest_schemes` in the active policy content **governs every new write**, and *"a digest with an unapproved scheme is invalid input, never a different-but-equal identity."* At this checkout that second layer is **not implemented**: `validSubjectBindings` (`records.ts`) validates `content_digest`'s typed **shape** only (`isDigestShape`), and `assertSchemesApproved` (`cadp/kernel/ingress.ts`) is invoked over **K3 digests alone** — `[sealed.material_digest, sealed.request_digest]` — never over evidence subject bindings. That is an **IMPLEMENTATION GAP in the Authority Plane's own inherited contract**, named here as required implementation work before v0.5 conformance. It is **not re-assigned to this plane**: a product-side construction discipline binds only well-behaved producers, whereas §2.1 governs *every new write by any producer*, so this plane's obligation cannot discharge the kernel-wide rule and does not purport to. **No Authority Plane TD amendment is needed** — the rule already exists there in re-homed §2.1; only its enforcement over this field is missing. **Required-ness of the digest is owned elsewhere, deliberately.** The Authority ingress is generic: it enforces that digests which **exist** carry an approved scheme, and it is **not** asked to know that an `execution-output` binding must have one — an ingress carrying that knowledge would re-import product namespace semantics into the kernel. The two layers that do own it are **product construction** (the broker refuses to return, and the activity refuses to build, a binding without its `content_digest` — (2)'s malformed-result rule) and the **composition gate** (a policy that consumes the binding verifies the relation it needs explicitly). The consequence of the identity being the identity then lands where B1(5)(d) needs it: the comparison against the sealed material has a subject to select on and a typed digest to verify with — the bundle bytes against the material's `bundle_cas_key`, the candidate commit against the material's `candidate_sha` — rather than one string doing both jobs and neither well.
   - **Observation provenance.** The same digest also rides as an ordinary observed field — `claim.observed.output_artifact = { availability: "PRESENT", value: <output_artifact_digest>, locator: <output_artifact_locator> }` — so the §A.2(3) locator obligation applies to it under the **already-implemented** rule with no ingress change: `assertBackendObservedLocators` (`cadp/kernel/ingress.ts`) refuses `OBSERVED_WITHOUT_LOCATOR` for any `PRESENT` observed field lacking a locator, this one included. The binding's `content_digest` and the observed field carry the same digest under the same scheme: the binding is the content-verified subject record, the observed field is the provenance-bearing carrier that names where the broker observed it.

   That rule enforces locator **presence** only. It cannot distinguish a broker-side locator from a session-file one — `observed.model`'s locator is legitimately a session file — so *which* locator this field carries is this plane's construction obligation (the broker populates `observed.output_artifact` only from bytes it holds, never from `scanBackendModel` output) and control C1's falsification target, not a kernel guarantee. Everything else about that envelope is unchanged and is the Authority Plane's (§A.2): producer stamping under `backend-scan:<provider>`, `produced_at_source {kind: NONE}`, the locator obligation, and `source_relation` staying `SELF_REPORT` — **no promotion** (Spec v0.5 §4.5). A stronger relation requires a probe establishing it and an `adapter_registry` change under the ordinary activation gate; this document promotes nothing and mints no evidence kind (Design D7-3). Whether any gate consumes the binding is composition policy: the reference policy states no such predicate today, so the binding is **inert until a composition adds one** — and the AP B4 `subject_complete_assembly` declaration set can only name this pair once the binding exists (AP B4(1)–(2): a declared entry whose subject namespace is unbound refuses `ASSEMBLY_SUBJECT_UNBOUND`).
4. **Capture MECHANICS, marked honestly — the WHAT is decided above, not here.** `[UNMEASURED — probe required: the PLANNER artifact digest is measured today (`stdout_digest`, (2)); no probe has captured a WORKER bundle digest or a REVIEWER verdict-stdout digest at the surface boundary, so the capture MECHANICS of those two roles in (2)–(3) are unmeasured. Which object is digested, and under which identity, is settled for all three roles by (2) and is **not the probe's to choose**; the probe measures only that the broker can perform that capture, and it must capture **both** halves of (3)'s binding — the artifact identity destined for `object_id` and the digest destined for `content_digest` — each broker-side and neither self-reported. For **all three** roles the identity is **derived and minted** broker-side per (2a) — the canonical digest of the request the broker already holds, joined to the container identity the broker already mints at surface start — so the probe measures the **digest capture only**, for every role: no identity component needs measurement, because none needs observation.]` This is the capture probe that Spec v0.5 §6's marker, WP §4.2's future K2 candidate-provenance contract (which names this probe as its trigger and mints nothing before it), and the AP B4 declaration-set extension above all wait on. **The contract shape and the artifact identity are defined NOW so the probe has an exact target.**
5. **What the probe must measure**, in order: (a) that the broker can digest the produced artifact from bytes it already holds at the surface boundary, with the surface supplying no digest and no input to it; (b) that the object **already pinned in (2)** digests **stably** — the same worker run's bundle bytes re-digest equal on re-read, and the same reviewer stdout capture re-digests equal; this is a stability measurement over an object this document has fixed, **not** a choice among candidate objects; (c) the observer chain — which principal seals it, and that `output_artifact_locator`, landing in `claim.observed.output_artifact.locator` per (3), names a **broker-side observation** (the `broker-response#…` shape) and never a session-file locator, since a session log is the model's own output and an artifact digest read from it would be self-report promoted to observation; (d) that the WORKER artifact digest is comparable to the bundle the sealed `GIT_PUSH` material names by `bundle_cas_key`, and that the material's own `candidate_sha` remains comparable to the candidate the existing `commit` bindings name, so the evaluator's Spec v0.5 §4.3 comparison has both sides of each relation and policy states each one explicitly (§2.4). Until (a)–(d) are measured, no envelope this plane produces satisfies any execution-provenance requirement, and the reference policy asserts none.

### B2. Provider-credential custody (Spec v0.5 §2.3 and §6; Design D1.2)

1. **The rule, as this plane's internal discipline.** In the reference deployment, provider subscriptions are **not mutation credentials for any current governed domain target**. The measured basis is this plane's own posture: exactly one provider's auth is injected into an isolated container, read-only at its provider path, with the host keychain and every other provider unreachable (TD v0.4 §17.3; `surfaceProviderAuth` → `reviewerAuthArgs`, and `buildWorkerSandbox` on the worker path), inside a container whose only egress is the allowlist proxy to provider hosts so governed targets have no route (`isolation.ts`); and the GitHub read credential stays **host-side on the broker**, never inside any surface container (TD v0.4 §18.2; `fetchExternalVerification` shells the operator's `gh` on the broker host).
2. **This is a deployment-policy fact, and it dissolves on reclassification.** It is never a universal exemption and never a credential-**kind** exemption (Spec v0.5 §2.3, §6; Design D1.2, D7-5). A deployment whose policy classifies **provider invocation itself** as a governed effect — spend caps, data-egress control, model-access governance — thereby brings provider credentials under the **full Authority Plane custody rules**: held by the PEP, absent from every Execution Plane process and every surface container, with the invocation passing admission like any other governed effect. Nothing in this document may be read as carving them out, and Spec v0.5 §2.5's classification rule cuts the same way — an operation with no policy-bound classification defaults to **effecting**, so provider invocation is not non-effecting by default anywhere.
3. **Provider-invocation classification — the honest gap, stated rather than argued around.** The v0.5 reference deployment does **NOT** yet carry a policy-bound classification of provider invocation. No such datum exists in the active policy content: the reference bundle's params are `{verification_max_age_s, max_effects_cap, max_steps_cap, require_backend_effort, require_external_verification, extra_plain_allow_operations, delegated_merge_producers}` (`cadp/deployment/referencePolicy.ts`), and **`extra_plain_allow_operations` is not an effect classification** — it is a plain-**ALLOW** list over `operation_kind`s that still arrive as `input.effect_request` and still pass through admission and PEP dispatch (`op in params.extra_plain_allow_operations`, `REFERENCE_REGO`; default `[]`, and `FINDING_SEAL` is excluded from it whatever a deployment puts there). Plain-allowed is *governed with a trivial gate*, the opposite of *outside effect admission*; it could not supply the missing declaration and is not cited as if it could. **Two inferences this document explicitly does NOT make.** (i) That provider invocation is absent from the closed adapter-declared operation vocabulary — the PEP resolves `adapters.byTarget(request.target_ref)` (else `NO_ADAPTER_FOR_TARGET`) and then `adapter.describe().operations` (else `OPERATION_UNAVAILABLE`, `cadp/kernel/pep.ts`), and the declared set is `GIT_PUSH`, `PR_CREATE`, `PR_MERGE`, `WORK_START`, `POLICY_ACTIVATE`, `RECORD_WRITE`, `DEPLOY`, `FINDING_PROJECT`, `FINDING_SEAL` (`cadp/kernel/adapters/*.ts`) — establishes **nothing** about its purity. Inferring non-effecting from a vocabulary's shape is the same move as inferring it from a tool name or a mode label: purity by vocabulary shape is exactly what §2.5 exists to forbid, and Design D1.2 already treats provider invocation as **classifiable** (spend caps, data egress, model access), i.e. as a thing a policy can and may classify rather than a thing outside classification by construction. (ii) That this plane's isolation posture classifies it. `isolation.ts` measures a credential-**REACH** bound — worker and reviewer on the `--internal` network whose only hole is the provider-host allowlist proxy, so governed targets have no route — which is a proof about **what a credential can reach**, not a `NON_EFFECTING` classification of an operation.
4. **The §2.5/§2.3 consequence, plainly, and the named v0.5 IMPLEMENTATION PREREQUISITE.** Under §2.5 an unclassified operation defaults to **effecting**; the reference posture therefore **CANNOT yet claim provider invocation non-effecting**, and under §2.3 a credential able to create an effecting operation belongs **inside the enforcing boundary**. The reach measurement of (1) **bounds the risk** — no governed target is reachable from any surface, which is why the residual exposure is small and why the posture is defensible as an interim — but it does **not substitute** for the classification, and this document claims no non-effecting posture on its strength. Closing it is a named **v0.5 implementation prerequisite**: a **machine-readable, active-policy-bound classification datum** must land before the posture is claimable — entries of the shape `provider-invoke:<provider> → NON_EFFECTING`, carried either as composition/adapter contract data or as a policy key, **its exact home decided by the implementing change and deliberately not invented here.** Until it lands, (2)'s dissolution clause is not merely live — the classification question is simply open, and a deployment that **wants** provider invocation governed introduces it as an operation with a target adapter, at which point §2.5 requires its classification and §2.3 pulls provider credentials inside the PEP boundary in full.
5. **Why this plane's isolation is load-bearing and never delegated.** WP §6 states the measured counter-fact (P0, run `24919dde`, 2026-09-07): a Conductor `working_dir` is **not a sandbox**, and `claude-agent-sdk` loads the working directory's settings as a trust boundary. An orchestrator's working directory, settings, or the word "sandbox" in its documentation therefore establish nothing. The enforceable boundary is this plane's container construction — network, mounts, single-provider auth injection, bounded lifetime (`isolation.ts`) — and it is **never delegated to any orchestrator**. The same fact is why B1's observer is the broker: an orchestrator working directory is not a place a digest can be observed from honestly.

### B3. Optionality and the equal-citizen consequence (Design D1.2)

1. **What is lost: nothing constitutional.** A deployment that runs its workers some other way — its own CI, its own harness, a human clone — keeps K1–K7, admission, PEP-only actuation, reconciliation and Kernel Conformance untouched (Spec v0.5 §9.1). What it loses is exactly the **reference execution-evidence producers**: `backend-scan:codex | grok | claude`, the only producers `adapter_registry` authorizes for `BACKEND_EXECUTION` (`REFERENCE_ADAPTERS`, `referencePolicy.ts`), so no other principal can submit that kind (`EVIDENCE_KIND_FORBIDDEN`).
2. **Which reference-policy predicates then become unsatisfiable, exactly** (`cadp/deployment/referencePolicy.ts`): `backend_model_present` — it requires a `PRESENT` `BACKEND_EXECUTION` with a `surface-role = WORKER` binding and `claim.observed.model.availability == "PRESENT"` — unsatisfiable. `backend_effort_present` — the same shape over `observed.effort` — unsatisfiable, so `effort_requirement_met` holds **only** while `params.require_backend_effort` is `false` (its first clause) and becomes unsatisfiable the moment a deployment arms that param. The **`BACKEND_EXECUTION` clause of `implementer_refs`** contributes nothing; the set is then whatever the `WORK_STEP` clause supplies, and a `WORK_STEP` producer names the **orchestrator, not the model that did the work** (WP §3.2), so a non-empty set from that clause proves no implementer product. Consequently `pr_create_ok` — `verification_ok` ∧ `external_verification_ok` ∧ `review_ok` ∧ `backend_model_present` ∧ `effort_requirement_met` — **DENYs, and no PR is created**.
3. **This is the same honest ingress-only posture the WP TD states for external candidates** (WP §3.2, control 12): **fail-closed at admission, never a defect**. An equal citizen at the effect boundary (Spec v0.5 §4.2) is equally subject to the composition's evidence requirements, and being admissible is not part of any plane's boundary contract. A deployment that wants admission without the reference producers needs a **reference-policy delta** — what establishes the implementer identity of its execution surface, how independence is computed over that evidence, and how model/effort provenance applies when the backend sits outside this plane — the same three questions WP §3.2 defers, composition work, out of scope here.

## C. Conformance controls (falsification additions)

In the Spec v0.5 §9 spirit — proven by attempting the violation. Three controls; the plane's existing product controls (TD v0.4 §13.2, P1–P7) are unchanged.

1. **Symmetric contract shape, with the unified-subject, transport, malformed-result and observer legs.** **What each leg waits on, stated once so no leg overclaims.** The B1(1)–(2) construction path — the `ExecutionRequest`, `output_artifact_subject`, and the broker-side refusals — is **contract-new** (B1's opening; B1(2)'s honest delta: the field does not exist at this checkout), so **no leg of this control passes at this checkout**; the legs differ only in what each needs *beyond* that path. **PURE-CONSTRUCTION** legs need it and **no probe at all**, because both identity components already exist broker-side (`jcsDigest`, `cadp/kernel/canonical.ts`; `RunResult.container`, `isolation.ts`) and nothing new must be observed; **capture** legs additionally wait on B1(4)'s unmeasured digest capture; the scheme leg's ingress half additionally waits on B1(3)'s named gap. **Unified-subject leg — ALL THREE roles, PURE-CONSTRUCTION, asserting BOTH halves of the pin.** *Shape half:* for a `WORKER`, `REVIEWER` or `PLANNER` result the control constructs the envelope and asserts the binding is exactly `{ authority_ref: "cadp-store:k04", namespace: "execution-output", object_id: "<the cadp-jcs-1 digest of that role's ExecutionRequest>/<that execution's broker-minted attempt identity>" }` — **an envelope whose `object_id` LACKS the attempt component (the bare request digest) FAILS the leg**, as does one whose attempt component is anything other than the identity the broker minted for that execution, and as does anything else in the slot: the artifact's own digest, an Ingress-allocated evidence id, a surface-supplied string, a wrong-role request digest — **and, on the `WORKER` result specifically, a `github.com|commit` binding over the `candidate_sha`, which now fails the leg exactly as it does for the other two roles**, because a bundle containing commit C is not commit C's bytes. Each is constructed and each asserted refused **by the broker at construction**. *Distinctness half:* the control runs the **same `ExecutionRequest` twice** through the result path and asserts the two envelopes carry **DISTINCT `execution-output` `object_id`s** — no identity is shared across attempts — each with its own `content_digest`, so a retry can never yield one identity carrying two contents. Both halves are **pure-construction**: they need B1(1)–(2)'s path and **no** capture from B1(4), since the prefix is computed from the request the broker already holds and the attempt identity is `RunResult.container` (`isolation.ts`) — so once that path exists, two stub results bearing distinct container identities exercise the distinctness half in full, with nothing measured. **Surface-input-drift leg:** two requests whose caller arguments are byte-identical but whose `surface-prompt` bytes differ — a reviewer prompt rebuilt after `origin/main` moved under `git merge-base`, or after the prompt template changed — MUST yield **different request digests and therefore different `object_id` prefixes**; a construction that digests caller inputs only fails the leg. **Sealer-transport leg (B1(2)):** the activity must build the binding from `output_artifact_subject` **verbatim**; a path that mutates any component between broker and seal fails, and a path that has the activity *re-derive* the attempt identity fails by construction, since no broker function returns `RunResult.container` across the transport (`surfaceBroker.ts` return types). **Malformed-result leg (B1(2), B1(5)):** a result missing any one of `output_artifact_subject`, `output_artifact_digest`, `output_artifact_locator` is refused by the broker and **seals nothing** — what the control asserts is the **ABSENCE of any `BACKEND_EXECUTION` envelope**, not an envelope carrying an unbound artifact. **Identity/content-placement leg:** the binding must carry the digest in `content_digest` and the subject in `object_id`; the control constructs the misplacement — the digest as `object_id`, `content_digest` absent — and asserts refusal **by the broker at construction** — **pure-construction**, no probe — since a digest-as-name is a subject with no content binding at all. That refusal is asserted at the **two layers that own required-ness** (B1(3)): product construction here, and the composition gate that verifies the relation explicitly. It is deliberately **NOT** asserted at Authority ingress: a generic ingress that knew which product namespaces are digest-required would re-import domain semantics into the kernel. **Scheme leg — what the ingress DOES owe generically, asserted at both layers:** a `content_digest` that **exists** must carry an approved scheme, so a binding whose canonicalization falls outside `data.cadp.approved_digest_schemes` is (a) refused **by the broker at construction** — **pure-construction**, no probe — and (b) refused **independently by the Authority ingress at seal** under the inherited §2.1 rule — leg (b) is the **gap-closing target** of B1(3)'s named implementation gap and does **not** pass at this checkout, where `assertSchemesApproved` runs over K3 digests only. The control asserts (b) as a currently-**failing** leg rather than omitting it, so the gap stays visible instead of being silently satisfied by (a). Negative leg, runnable when the capture lands, and **product-side by construction** since the kernel checks locator presence and not locator shape (B1(3)): a result carrying `output_artifact_digest` without `output_artifact_locator` is refused at Ingress with `OBSERVED_WITHOUT_LOCATOR` (`assertBackendObservedLocators`, already implemented), and a candidate digest whose locator names the surface's own session file or stdout is refused **by the broker**, never sealed as observed. The control falsifies both by feeding a session-scanned digest through the result path and asserting refusal rather than a seal — the artifact digest must be the broker's observation of bytes the broker holds, so a model cannot self-report its way into execution provenance.
2. **Custody.** The **F2** control carries forward unchanged — `cadp/tests/conformance-isolation.test.ts`, "F2: the worker sandbox imports ONLY codex auth material; the profile digest is deterministic": exactly the declared auth files are imported, the host `config.toml` (MCP/config mutation surface) is not, and the probe and production constructions digest equal. Its sibling in the same file carries the reviewer posture (the session bind is the only extra writable bind, `/ws` stays `:ro`, host `HOME` is never mounted). A second provider's auth in one surface container, or any governed-target credential in any surface container, falsifies B2(1).
3. **Optionality.** A deployment with this plane removed — no surface broker, no `backend-scan:*` producers — still passes the Spec v0.5 §9.1 kernel-conformance controls unchanged, while `pr_create_ok` **DENYs** for want of `backend_model_present`. The DENY is asserted as the **correct** outcome, exactly as WP control 12 asserts it for external candidates.
