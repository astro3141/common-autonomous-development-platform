## PART B — NEW NORMATIVE CONTRACTS

Five contracts. Each names the implemented seam it changes, in this checkout, before it states the change. All five are Authority Plane mechanism: **no new constitutional record is created and no K8 exists** (Spec v0.5 §8-1). New storage below is implementation state in the same store, exactly as `effect_allocation` already is (TD v0.4 §3.2).

### B1. Requester-scoped allocation

**Seam today.** `allocate_effect_id` is the only write API that does **not** receive the authenticated principal: `cadp/kernel/api.ts` resolves `principal` for every call but passes it on only to `seal_effect_request` and `submit_evidence` (`sealEffectRequest(draft, { principal })`, `submitEvidence(draft, { principal })`); the allocation branch calls `deps.ingress.allocateEffectId(tuple)` with the tuple alone. `cadp/kernel/ingress.ts` accepts exactly one tuple schema, `cadp.allocation-key.v1` = `{ schema, work_run_ref, step_ordinal, purpose }`, validates `work_run_ref`'s prefix, `step_ordinal ≥ 1` and `purpose ∈ active.config.allocation_purposes`, and derives `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1(tuple))`. **There is no requester scoping in the key.**

1. **The Ingress allocation entry point takes the stamped principal.** `allocateEffectId(tuple, principal)`; the API layer passes the same `principal` it already resolves. As with `requester_ref` (TD v0.4 §9.1 S3), the principal is **stamped, never accepted from the body**: the tuple carries no requester field, and a tuple containing one is rejected `ALLOCATION_TUPLE_INVALID`. The Ingress resolves it through the active `identity_registry` to a `requester_ref` and refuses an unregistered principal (`FORBIDDEN_FOR_PRINCIPAL`).
2. **The derived key is requester-scoped for every tuple schema.** `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1({ requester_ref, tuple }))`. Consequences, both normative: **retry-convergence per principal** — the same principal resubmitting the same tuple receives the same `effect_id`, so an orchestrator that re-runs a step still creates no second logical effect (TD v0.4 §7.4; control P4) — and **distinct effect identities across principals** — two principals submitting an identical tuple receive different `effect_id`s and neither can conflict the other's request (WP control 2).
3. **New tuple schema `cadp.allocation-key.external.v1`** = `{ schema, bindings: [{namespace, object_id}…], purpose }`, **domain-free at the Authority layer**: generic exact-string subject bindings — the K2/K3 vocabulary the Kernel already owns — closed key set, canonical JSON. Validation: `purpose ∈ data.cadp.allocation_purposes` (the existing check), ≥1 binding, no repeated `namespace`, all strings. The namespace strings and the purpose↔`operation_kind` correspondence are **composition-supplied data and composition-owned rules** (WP §§3.3–3.4), cited not restated; the core compares strings it does not interpret (Spec v0.5 §7; Design D7-4). It carries no `work_run_ref` and no `step_ordinal`: it presumes no run-profile enrollment, which is why WP §5 can refuse enrollment and still allocate.
4. `cadp.allocation-key.v1`'s field set, validation and meaning are otherwise unchanged; only the scoping of (2) is added. Because a v0.5 deployment requires a v0.5 genesis in a new store namespace (Spec v0.5 §10; TD v0.4 §10), no existing `effect_allocation` row is re-keyed in place.

### B2. Allocation binding storage and first-seal atomicity

**Seam today.** `effect_allocation (allocation_key PK, effect_id UNIQUE)` (`cadp/kernel/store.ts`), written by `insertAllocation`, read by `allocationByKey` only. `sealEffectRequest` in `cadp/kernel/ingress.ts` **never reads the allocation table**: it stamps `requester_ref`, reads the material CAS object, checks the injected idempotency key, digests, and inserts under `withImmediate`, applying the K3 rule (identical semantic payload → idempotent stored row; different → `REQUEST_DIGEST_CONFLICT` incident + scope hold). An `effect_id` that was never allocated is accepted today.

1. **Storage — one generic shape for every schema.** `effect_allocation` gains exactly `{ requester_ref, allocation_schema, allocation_binding_digest, purpose }`, **all NOT NULL**, plus an index on `effect_id` (already UNIQUE) so a seal resolves the row from the `effect_id` it names. `allocation_binding_digest` = `sha256` over the `cadp-jcs-1` form of the **full allocation tuple, whatever its schema**. **No domain-named column exists and none is ever added per schema** — a new tuple schema changes no DDL (Spec v0.5 §7; Design D7-4). The row stays non-constitutional: in no K-record, no digest, no `ResolvedAdmissionBundle`.
2. **First seal verifies under the schema's registered projection.** The first `seal_effect_request` for an `effect_id` (no `effect_request` row yet) MUST resolve the allocation row by `effect_id`; absent ⇒ `ALLOCATION_NOT_FOUND` (closing caller-invented effect identities — Spec v0.5 K3). It then checks stamped `requester_ref` == row `requester_ref`, and the binding under the **projection registered for `allocation_schema`**: a contract stating how the allocated tuple's binding content is **re-derived or re-presented at seal and compared against the digest**, and **which plane owns it**. Nothing inverts the digest — the caller re-presents the tuple as transport, never a draft field, and the core recomputes its canonical form. An unregistered schema is not allocatable.
3. **The two registered projections.** The core executes the comparison and interprets none of the strings compared.

   | Allocation schema | What the projection compares at seal | Projection owner |
   |---|---|---|
   | `cadp.allocation-key.v1` | sealed work-run binding == allocated `work_run_ref`. Honestly: **`step_ordinal` is allocation-key entropy only** — it names the orchestrator's step slot for key derivation and is **not re-verifiable at seal, because no K3 field carries it**; per-key idempotency and the K3 conflict rule bound it, unchanged | Authority Plane |
   | `cadp.allocation-key.external.v1` | sealed `work_bindings` contain **exactly** the allocated `bindings`: set equality of `{namespace, object_id}` **over the allocated namespaces** (each present with exactly that `object_id`, no second entry in it; other namespaces untouched) | Authority owns the comparison; the composition owns the namespace and purpose data (WP §§3.3–3.4) |

4. **Purpose is not a first-seal check.** It is verified against `data.cadp.allocation_purposes` **at allocation** (already implemented). The purpose↔`operation_kind` correspondence relates a policy-bound vocabulary to an adapter vocabulary and is domain semantics: it is a **composition-level admission predicate over K4-bound facts** — WP §3.3 defines the table and its controls exercise it — and no such table appears here (Spec v0.5 §7; Design D7-4).
5. **Atomicity.** The read of the allocation row, the equality checks and the `effect_request` insert occur **in one store transaction** with the allocation row locked for the duration (`SELECT … FOR UPDATE` on PostgreSQL; `BEGIN IMMEDIATE` single-writer on the SQLite reference, i.e. the existing `withImmediate`). Consequence, which is the point of the contract: a first seal whose principal or projected binding does not equal the immutable allocation row is **REFUSED deterministically before any K3 record exists**, under every interleaving of concurrent first-seal attempts — the check is against the allocation row, never against a race-visible request row, so no ordering makes a mismatching seal land. Concurrent *matching* first seals resolve by the unchanged §3.3 rule: one inserts, the other returns the stored row. Once a `request_digest` exists, the ordinary K3 conflict rule governs everything after it, unchanged.
6. **Refusal shape.** Reason codes `ALLOCATION_NOT_FOUND`, `ALLOCATION_PRINCIPAL_MISMATCH`, and `ALLOCATION_BINDING_MISMATCH` (re-presented tuple digest ≠ `allocation_binding_digest`, or projection inequality). No `EffectRequestV1` is sealed and no effect is performed. **No `KERNEL_INCIDENT` and no scope hold is raised** — deliberately, and this is normative: the allocation is requester-scoped, so a mismatching first seal is a caller error against an effect identity that has no K3/K6/K7 history, and raising a scope hold would let any principal freeze another principal's effect scope by attempting one bad seal. The K3 conflict path (which does raise an incident) is untouched.
7. **Registry drift is fail-closed.** The row stores the `requester_ref` resolved under the policy active at allocation; the first seal compares the `requester_ref` stamped under the policy active at seal time. A policy activation that re-maps the principal makes them unequal, the seal is refused, and the proposer re-allocates under the new registry. This is a refusal, never a fallback to the raw principal string.
8. **Not a K8.** Nothing above is a constitutional record, a new evidence kind, or a new admission state. It is the pre-K3 window's implementation, delegated to this document by WP §3.3.

### B3. Registry uniqueness and closed entry keys

**Seam today.** `validateKernelConfig` (`cadp/kernel/policyBundle.ts`) enforces the closed top-level key set (`ALLOWED_KEYS`), the exact-string/no-pattern rule on `identity_registry.principal` and `adapter_registry.producer_ref`, entry field types, the `produced_at_source` shape, the governed-writer opt-in vocabularies and the invariant-P reserved-constant rule, bounds and bootstrap-scheme retention. It performs **no duplicate detection**, and the closed-key check is `data.cadp` top level only — an unknown key *inside* an entry validates and activates. Resolution is by first match: `identityEntry`/`adapterEntry` in `cadp/kernel/policyState.ts` are `find()`.

1. **Uniqueness (new activation-time rejection).** A bundle is refused at `POLICY_ACTIVATE` recheck #17 / genesis validation if any of the following holds: two `identity_registry` rows share a `principal`; two `identity_registry` rows share a `producer_ref`; two `adapter_registry` rows share a `producer_ref`. Reason `REGISTRY_DUPLICATE_KEY`. Grounding for each: a duplicate `principal` makes `identityEntry`'s `find()` silently order-dependent, so the caller's `process_class` (and therefore its `METHOD_REACH`) and its stamped `producer_ref` are decided by bundle authoring order; a duplicate `producer_ref` in `identity_registry` makes the reference policy's `registry_entry(producer)` a function with two candidate outputs — in Rego that is a conflicting-output evaluation error, i.e. an `EvaluatorFailure` and **no** decision (fail-closed but opaque), while the PEP computing the same derivation in TypeScript takes the first row (fail-open relative to the evaluator, and the two can disagree about `identity_class.product`, which is exactly the value the independence predicate compares); a duplicate `adapter_registry` row makes the allowed `evidence_kinds`, `source_relation` and `produced_at_source` of one producer order-dependent at the ingress. Rejecting at activation makes all three unconstructible.
2. **Unknown keys inside entries are rejected** — decided here, and decided the same way as the top level, for the same fail-closed reason: **an inert key is not a declared binding.** A key the Kernel does not read is either a future binding activated early (so its meaning is unenforced while it appears authoritative to a reader) or a typo silently disabling the binding it was meant to be (`producer-ref` for `producer_ref`, `evidence_kind` for `evidence_kinds`). Spec v0.5 §2.5's rule — a missing or unverifiable required fact never satisfies a requirement — makes silent acceptance the wrong default for the one document that declares who may say what. Reason `REGISTRY_UNKNOWN_ENTRY_KEY`.
3. **Closed entry key sets** (exact; anything else is refused): `approved_digest_schemes` `{algorithm, canonicalization}`; `root_public_keys` `{key_id, alg, public_key, valid_from, valid_to?}`; `attestation_keys` `{key_id, alg, public_key, purpose, valid_from, valid_to?}`; `identity_registry` `{principal, producer_ref, identity_class{vendor, product, account, process_class}}`; `adapter_registry` `{producer_ref, evidence_kinds, source_relation, produced_at_source{kind, claim_pointer?}, replay_idempotency?, governed_edge?}`. The last two optional keys are the governed-writer opt-ins that exist in the checked-out schema and in the reference `adapter_registry` row `governed:reclassification`; omitting them from the closed set would refuse the current reference bundle.
4. **Schema identity.** (1)–(3), together with B4(2) and B5(2), define **`cadp.kernel-config.v2`**, required exactly by `schema` string. Because activation acceptance is narrowed, this is a generation-boundary change: v0.5 genesis bundles carry v2, and no running v0.4 environment is mutated in place (Spec v0.5 §10).

### B4. Assembly completeness

**Seam today.** `assemble_admission_input(effect_id, evidence_refs[])` takes the caller's list verbatim: `cadp/kernel/api.ts` parses `{ effect_id, evidence_refs }` from the body and `Ingress.assembleAdmissionInput` resolves each id, records `{evidence_id, envelope_digest}`, and seals K4. The store already supports the needed read: `evidence_subject(evidence_id, subject_key)` with `subject_key = "<authority_ref>|<namespace>|<object_id>"` and an index, plus an `evidence_kind` index, joined by `evidenceBySubjectKey`. The reference policy's predicates are existential (`some e in input.evidence`), so **a caller can today withhold an unfavourable sealed envelope of a kind the gate consumes** and the evaluator never learns it exists.

1. **Declaration.** `data.cadp.subject_complete_assembly: [{ evidence_kind, subject_namespace, operation_kinds[] }]` — required, may be `[]`, exact strings, closed entry keys (B3), part of `cadp.kernel-config.v2`. Kernel-read, so it lives under `data.cadp` and not in rego-private `policy_params`. All three components are identity strings the Kernel already handles; **no material field is parsed** — domain material vocabulary stays in the composition (Spec v0.5 §7).
2. **Query contract.** For a declared entry and a sealed `EffectRequestV1` whose `operation_kind` the entry lists, the Platform computes, from that request's own `work_bindings`, every subject key `<authority_ref>|<subject_namespace>|<object_id>` it names, and selects **every** sealed envelope of that `evidence_kind` bound to that exact key — the complete set, not a latest-wins pick. This is the existing `(evidence_kind, subject_key)` join over the sealed store. The `latestEvidenceOfKind` helper in `store.ts` MUST NOT be used for assembly: "latest" is not authority in sealed history (Spec v0.5 §2.6; TD v0.4 §6.6). If the sealed `work_bindings` name **no** binding in `subject_namespace`, assembly REFUSES `ASSEMBLY_SUBJECT_UNBOUND` — the rule is never vacuously satisfied by an unbound subject. Composition consequence, stated because it is a real change and not a kernel one: the reference composition binds only `work-run` into `work_bindings` today (`cadp/product/activities.ts` seals `[{namespace: "work-run", …}, ...extra_bindings]` and nothing populates `extra_bindings`), so declaring `{REVIEW, commit, [PR_CREATE, PR_MERGE]}` requires the composition to bind the candidate through that existing hook — exactly what WP §3.4 already mandates for external candidates.
3. **Where it runs.** Inside `assemble_admission_input`, in the Platform (Ingress), in the same transaction that seals K4. The result is the **union** of the caller's `evidence_refs` and the queried set, deduplicated by `evidence_id` and ordered canonically by `evidence_id` so `input_digest` is deterministic. The caller may add; the caller can never subtract. Assembly is never the caller's evidence-selection choice for a declared kind (Spec v0.5 K4: the PEP never back-fills facts the evaluator did not see — the correction is to put them in front of the evaluator, not behind the PEP).
4. **Fail closed.** If the query cannot be executed, or any matched row fails verify-on-read, assembly **refuses** — `ASSEMBLY_QUERY_FAILED` / `DIGEST_CORRUPTION` (incident per TD v0.4 §2.6) — and **no `AdmissionInputV1` row is written**. A partial set is never sealed.
5. **Completeness is as-of a transaction, so it is re-proven at commit.** A new `§4.4` recheck item **#18**: inside the admission transaction, the PEP re-runs (1) over rows read in that transaction and refuses `ASSEMBLY_INCOMPLETE_AT_COMMIT` if the complete set for any declared pair differs from the set the bound `AdmissionInputV1` carries. Without #18 a producer could seal a contrary envelope after assembly and the decision would be silently stale (Spec v0.5 §2.7). Honest cost: a producer that keeps sealing envelopes for a subject can keep admission failing. That is a liveness cost of a safety rule, and it is fail-closed — a fresh assembly and evaluation resolve it.
6. **What this does not do.** It does not make an existential policy predicate sound; it removes the caller's power to decide what the evaluator sees. Whether the complete set satisfies a gate remains the evaluator's decision over K4-bound facts.

### B5. Run membership mechanism

Spec v0.5 §5.3 locks the invariant — *a requester cannot self-select or borrow another valid run scope* — and delegates the mechanism to the TD. **One mechanism is chosen: a Platform-minted run capability.**

**Seam today.** Nothing implements this: `work_bindings` are caller-supplied content on the seal draft, and `sealEffectRequest` reads `work_run_ref` out of them only to index the request row. `METHOD_REACH` in `cadp/kernel/api.ts` is keyed by `process_class`, not by principal.

1. **Minting, only where a delivery channel exists.** When the PEP writes `EffectOutcomeV1(result = COMMITTED)` for a `WORK_START` effect **inside the `admit_and_dispatch` transaction** — K7, never K6, per Spec v0.5 §5.2 and the memo-proof rule of TD v0.4 §6.4 — the Platform mints, in that same transaction, a run capability: ≥256 bits from a CSPRNG. The store keeps only `run_capability(work_run_ref PK, holder_ref, capability_digest, minted_at, revoked_at?)`, a non-constitutional implementation table; the secret itself is never stored, never in any K1–K7 record or digest, never in the `ResolvedAdmissionBundle`, and never in workflow args or effect material. `holder_ref` is the stamped `requester_ref` of that `WORK_START` request. An `UNKNOWN` `WORK_START` mints nothing, and **a later reconciliation to `COMMITTED` mints nothing either** — because there is no result to return it in: `Reconciler.reconcileEffect` writes that outcome with observer `…:reconciler` outside any `admit_and_dispatch` call (`cadp/kernel/reconciler.ts`), reached from the restart scan or from `request_reconcile`, whose reach is not the holder's alone (`cadp/kernel/api.ts`). Minting there would strand a secret nothing can deliver, and only its digest would be stored (B5(6)). Such a run is **never capability-bearing**: its already-sealed effects admit, reconcile and grade normally, but no principal can seal further run-bound requests against it, so the proposer starts a new run. Fail-closed, a liveness cost only. A `NO_EFFECT_CONFIRMED` `WORK_START` mints nothing, ever.
2. **Enrollment.** `data.cadp.run_profile_enrolled_principals: [exact principal]` — required, may be `[]`, part of `cadp.kernel-config.v2`. For an enrolled principal, `seal_effect_request` REFUSES a request without a `work-run` binding (`RUN_BINDING_REQUIRED`) — refused, not merely uncounted (Spec v0.5 §5.1). A **non-enrolled** principal's request carrying a `work_run_ref` is refused `NOT_RUN_ENROLLED`: enrollment cannot be acquired by presenting a binding (WP §5.2; WP control 5).
3. **Presentation and verification.** An enrolled principal presents the capability on `seal_effect_request` over its authenticated channel — as a transport-level header, never as a draft field, never inside any record. The Ingress refuses unless, in the sealing transaction: the capability's digest matches the `run_capability` row for the request's exact `work_run_ref`; that row's `holder_ref` equals the **stamped** `requester_ref` of this request; and `revoked_at` is null. Possession never suffices on its own: the row binds one capability to one `work_run_ref` **and** one holder, so presenting run R2's capability on a request bound to R1 fails the first check and a principal holding another principal's capability fails the second. **Seal-time refusal codes, all distinct from recheck #19's `RUN_MEMBERSHIP_UNPROVEN`** — which is a PEP-time refusal on a missing durable row: `RUN_CAPABILITY_INVALID` (no digest match against the row for this request's `work_run_ref`, including the case where no row exists for it); `RUN_CAPABILITY_HOLDER_MISMATCH` (row `holder_ref` ≠ stamped `requester_ref`); `RUN_CAPABILITY_REVOKED` (`revoked_at` set); `RUN_CAPABILITY_REQUIRED` (an enrolled principal's run-bound request presenting none — distinct from `RUN_BINDING_REQUIRED`, which covers only the missing-`work-run`-binding case of (2)).
4. **Durable proof for the PEP.** The seal inserts `run_membership(effect_id PK, work_run_ref)` in the same transaction as the `effect_request` row. New `§4.4` recheck item **#19**: for a request whose requester is enrolled, the PEP requires that row, with a matching `work_run_ref`, read inside the admission transaction — refusing `RUN_MEMBERSHIP_UNPROVEN` otherwise. Authority after restart is reconstructed from rows, never from process memory (TD v0.4 §4.5); the secret is not needed at admission time.
5. **What it is not.** The run capability is **not** a governed-target credential and confers no effect authority: a compromised one lets its holder propose requests bound to a run, which still need evidence, a decision under the active policy and the PEP's fresh recheck (Spec v0.5 §4.3). Its compromise cannot create an effect; it can only mis-attribute an effect to a run's budget — precisely the invariant it exists to protect, so the residual is stated, not hidden. Custody is no new custody class: the holder already holds a Kernel API bearer/workload credential today (`ApiDeps.tokens`, `cadp/kernel/api.ts`).
6. **No recovery.** The capability is returned **exactly once**, in the `admit_and_dispatch` result of the `COMMITTED` `WORK_START`, to the caller that requested it. That result is the **only** delivery channel this document defines, which is why (1) mints in no other write. There is no re-delivery: only `capability_digest` is stored, and a digest cannot be inverted, so no contract here may promise to hand the secret back. A holder that loses it **cannot seal further run-bound requests for that run** — fail-closed, a liveness cost only, and consistent with the run remaining governable per-effect (its already-sealed effects admit, reconcile and grade normally). Rotation — mint C2, atomically replace the row's digest, invalidate C1, return C2 to the exact holder — is a possible future contract needing its own concurrency and replay rules and would be named `rotate_run_capability`; out of scope here. **This document adds no Kernel API method.**
7. **Unmeasured part, marked exactly** (Spec v0.5 §5.3's marker resolved to the one dependency that is actually unmeasured, with the invariant unweakened):
   - Holder-side custody across an orchestrator restart. `[UNMEASURED — probe required: no probe of any orchestrator's durable secret custody exists. The measured counter-fact bounds it: WP §6 (P0) measured that a Conductor `working_dir` is not a sandbox and that its settings are a trust boundary, which is one reason the reference deployment enrolls no Conductor principal (WP §5.2). The reference run profile's holder is the Temporal-backed `workflow:cadp-work` principal.]`
8. **Not a K8.** Two implementation tables and two recheck items. No new record, no new evidence kind, no orchestrator lifecycle.
