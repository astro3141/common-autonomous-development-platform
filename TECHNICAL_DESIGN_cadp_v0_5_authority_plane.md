## PART B — NEW NORMATIVE CONTRACTS

Six contracts. Each names the implemented seam it changes, in this checkout, before it states the change. All six are Authority Plane mechanism: **no new constitutional record is created and no K8 exists** (Spec v0.5 §8-1). New storage below is implementation state in the same store, exactly as `effect_allocation` already is (TD v0.4 §3.2).

### B1. Requester-scoped allocation

**Seam today.** `allocate_effect_id` is the only write API that does **not** receive the authenticated principal: `cadp/kernel/api.ts` resolves `principal` for every call but passes it on only to `seal_effect_request` and `submit_evidence` (`sealEffectRequest(draft, { principal })`, `submitEvidence(draft, { principal })`); the allocation branch calls `deps.ingress.allocateEffectId(tuple)` with the tuple alone. `cadp/kernel/ingress.ts` accepts exactly one tuple schema, `cadp.allocation-key.v1` = `{ schema, work_run_ref, step_ordinal, purpose }`, validates `work_run_ref`'s prefix, `step_ordinal ≥ 1` and `purpose ∈ active.config.allocation_purposes`, and derives `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1(tuple))`. **There is no requester scoping in the key.**

1. **The Ingress allocation entry point takes the stamped principal.** `allocateEffectId(tuple, principal)`; the API layer passes the same `principal` it already resolves. As with `requester_ref` (TD v0.4 §9.1 S3), the principal is **stamped, never accepted from the body**: the tuple carries no requester field, and a tuple containing one is rejected `ALLOCATION_TUPLE_INVALID`. The Ingress resolves it through the active `identity_registry` to a `requester_ref` and refuses an unregistered principal (`FORBIDDEN_FOR_PRINCIPAL`).
2. **The derived key is requester-scoped AND contract-scoped for every tuple schema.** `allocation_key = "cadp-v04:alloc:" + sha256(cadp-jcs-1({ requester_ref, tuple, allocation_contract_digest }))`, the third component being B2(1)'s `allocation_contract_digest` over the pinned `allocation_contract_payload.v1` preimage — the schema's **descriptor entry AND `allocation_schemas` entry together** — active at **this** allocation — already resolved at this point in the call, because B2(5) refuses `ALLOCATION_SCHEMA_UNREGISTERED` for a schema missing either, so the key is never derivable without both. Consequences, all three normative: **retry-convergence per principal under an unchanged contract** — the same principal resubmitting the same tuple while the schema's contract is byte-identical receives the same `effect_id`, so an orchestrator that re-runs a step still creates no second logical effect (TD v0.4 §7.4; control P4) — **distinct effect identities across principals** — two principals submitting an identical tuple receive different `effect_id`s and neither can conflict the other's request (WP control 2 — an invariant that holds only because B2(10) also keeps a non-owner off the K3 conflict path of an *already sealed* effect; without it the "neither can conflict the other" claim would be true of allocation and false of re-seal) — and **contract drift is RECOVERABLE in one call, not a dead end**. **Cross-document agreement, stated so it is checkable rather than assumed:** WP control 1 **as amended** and this key derivation state the same contract — same principal + same tuple + **unchanged active allocation contract** converge on the same `effect_id`, and after an activation that changes the schema's `allocation_schemas` entry the same call derives a **fresh** `effect_id` under the new contract, by design. **No divergence exists**, and the two wordings are exactly co-extensive rather than merely compatible: the digest's **descriptor** component can never drift after the schema's first activation (B2(2) immutability), so `allocation_schemas` is the only component WP's qualifier need name. WP control 1's distinctness and first-seal-binding legs are unaffected by it. The third is load-bearing and not symmetry: the implemented `allocateEffectId` returns the existing row's `effect_id` on a converging key (`cadp/kernel/ingress.ts`, `store.ts` `allocationByKey`) and the store contract has **no runtime `UPDATE`**, so a re-allocation can never re-stamp a stored row's `allocation_contract_digest` — a key that omitted the digest would converge to the stale row and every later first seal would refuse `ALLOCATION_CONTRACT_CHANGED` **permanently**. Contract-scoping the key is what makes the re-allocation B2(3.3) directs the proposer to actually work: after an activation that changes the schema's entry, the same principal re-presenting the same tuple derives a **different** key, receives a **fresh** `effect_id` on a fresh row stamped with the **new** digest, and its first seal passes B2(3.3). The stranded old `effect_id` is **not** a duplicate effect and creates no second logical effect: it has no K3, K6 or K7 row and can never acquire one, since every first seal against it refuses — it is an unusable identity, which is exactly what that refusal is for.
3. **Tuple schema `cadp.allocation-key.external.v1` — the wire shape is the Workflow Plane's and is not re-shaped here.** The merged WP TD canonically defines it as `{ schema, repo_id, candidate_base_sha, candidate_sha, purpose }` (WP §3.3, which **owns** it); that IS the public wire shape, and this document restates it only to cite it. The Authority Plane treats every field other than `schema` and `purpose` as an **opaque exact string it does not interpret**: allocation-time validation is exactly that the key set is the schema's — **derived from that schema's immutable SCHEMA DESCRIPTOR, never held in kernel code** (B2(2), B2(5)) — that every value conforms to its descriptor field's `value_contract`, which for all three of this schema's fields is `NONEMPTY_STRING` (B2(2)(i)), and that `purpose ∈ data.cadp.allocation_purposes` (the existing check) — no field's meaning is parsed (Spec v0.5 §7; Design D7-4). `allocation_binding_digest` (B2) is computed over the `cadp-jcs-1` canonical form of the wire tuple **as received**; the tuple is an **object**, so JCS canonicalization fully determines the bytes and **no array-ordering problem exists** to be solved here. A future allocation schema is added by the plane or composition that owns its wire shape — which authors its descriptor (B2(2)) — and reaches the Authority core only through that descriptor and B2's bundle-supplied projection; the Authority core never parses its fields. The tuple carries no `work_run_ref` and no `step_ordinal`: it presumes no run-profile enrollment, which is why WP §5 can refuse enrollment and still allocate.
4. **`cadp.allocation-key.v1` is descriptor-defined on exactly the same terms, and `step_ordinal` thereby LEAVES Authority vocabulary entirely.** Its wire shape is no longer kernel code: its descriptor — `work_run_ref` `{PROJECTED, EFFECT_ID}`, `step_ordinal` `{ENTROPY, POSITIVE_INTEGER}` — is **Workflow-Plane-owned** like the external schema's (B2(2)), consistent with this document's own Part A re-homing of the step ordinal to that plane and with Spec v0.5's bisection (Design D3). The Kernel holds **no** v1 field name; it reads the descriptor's strings and compares them generically like any other schema's. `step_ordinal` is therefore not Authority-normative content at all — this document states nothing about what it means, only that a descriptor may mark a field `ENTROPY`, which is a role, not a semantics. **The v0.4 seam, named exactly:** `cadp/kernel/ingress.ts` today hard-codes v1's key set in the `AllocationTuple` type and in `allocateEffectId`'s `schema`/`work_run_ref`/`step_ordinal` checks, the latter two **typed** (`work_run_ref.startsWith("cadp-v04:effect:")`; `Number.isInteger(step_ordinal) && step_ordinal >= 1`); **replacing those with the generic descriptor comparison — key set AND `value_contract`, per B2(2)(i) and B2(5) — is the implementation work this contract mandates**. The typed checks are **MOVED, not dropped**: the field names leave kernel code, the type constraints survive as `EFFECT_ID` and `POSITIVE_INTEGER` in the descriptor, and the v0.4 refusal code `ALLOCATION_TUPLE_INVALID` is unchanged in both name and timing. That distinction is load-bearing rather than tidy: `step_ordinal` is `ENTROPY`, so it is projected nowhere and never re-verified at seal, and a key-set-only migration would let `{step_ordinal: "1"}` and `{step_ordinal: 1.5}` allocate **distinct `effect_id`s from `{step_ordinal: 1}`** — the same logical step minting separate effect identities on serialization drift, which is precisely the retry convergence of (2) and control P4. It is the only place `step_ordinal` appears on the kernel's **allocation** path at this checkout (its other occurrences — the `WORK_STEP` replay check and index — are re-homed Workflow Plane content Part A does not claim; B2's ownership line (iii)). Only the scoping of (2) is added to v1's key derivation. Because a v0.5 deployment requires a v0.5 genesis in a new store namespace (Spec v0.5 §10; TD v0.4 §10), no existing `effect_allocation` row is re-keyed in place.
5. **Tuple schema `cadp.allocation-key.run-origin.v1` — the wire shape is the Workflow Plane's; the immutability of its contract is this document's.** Neither schema above can mint the identity of a run's ORIGIN `WORK_START`: `cadp.allocation-key.v1`'s first field is the `work_run_ref` that IS that `effect_id` (Spec v0.5 §5.2), and the external schema is a candidate-material schema. Spec v0.5 §5.3 makes originating that identity run-profile semantics; B5(9) authenticates the self-origin relation at seal; the tuple that mints the identity is **owned by the Workflow Plane TD** (WP §3.6) exactly as the external schema's is by WP §3.3, and is **quoted verbatim below** so the two documents are checkable against each other rather than paraphrased apart (strip the leading `   > ` and the quoted paragraph is byte-identical to WP §3.6's; the mechanism paragraphs after it are this document's and have no WP twin, WP carrying only the wire shape, the `origin_key` meaning and the Workflow-side caller obligations):

   > **`cadp.allocation-key.run-origin.v1` = `{ schema, origin_key, purpose }`** — exactly these three keys. `schema` and `purpose` are the two reserved kernel fields (AP B2(5)); `origin_key` is the schema's **single non-reserved field**, with descriptor role **`ENTROPY`** and `value_contract` **`NONEMPTY_STRING`**. No field is `PROJECTED`, so this schema's `binding_projection` is **`[]`**: the tuple carries **no `work_run_ref`** and projects nothing onto any subject binding — the origin's self-binding is not an allocation projection at all, and is verified at seal by the Authority Plane's run-origin rule (AP B5(9)). `origin_key` is a **WORKFLOW-OWNED OPAQUE IDEMPOTENCY DISCRIMINATOR**: the Workflow side decides it **once**, when it creates a logical run origin, and preserves it **VERBATIM** across every retry of that origin. It identifies **one logical origin, never the work's content** — two distinct origins carry distinct `origin_key`s even when their work is byte-identical (same repository, same base revision, same work item), and a retry of one origin carries the same `origin_key` and converges on the same `effect_id`. It is **opaque to the Authority core**, compared as a `NONEMPTY_STRING` and never parsed, and it confers **no effect-identity authority**: the Platform still derives `effect_id` from the stamped `requester_ref`, the tuple and the `allocation_contract_digest` (AP B1(2)), so a caller cannot self-select an identity by choosing an `origin_key`. `purpose` is `work-start`, which this schema's one fixed `purpose_relation` pairs with `WORK_START`.

   Everything the Authority core does with that tuple is the generic machinery of B2, unchanged and with no new path: the key set is the descriptor's (B2(5)), `origin_key`'s value is checked against `NONEMPTY_STRING` and **never parsed** (B2(2)(i)), `purpose` is checked for `allocation_purposes` membership and for a registered `purpose_relation` pair, and B2(2)(iii)'s coverage rule is satisfied by an empty `binding_projection` precisely because the schema's only field is `ENTROPY`. **`ENTROPY` is exactly the right role and the residual is the ordinary one (B2(5)):** `origin_key` is projected nowhere and re-verified at no seal, so the tuple binds no material — which is correct here, because the material this identity is for is bound by B5(9)'s self-origin check and by K3, not by a projection. **This schema adds no `data.cadp` key and no DDL:** it rides `allocation_schema_descriptors` and `allocation_schemas` exactly as the other two do, so B3(3)'s closed-key inventory is unchanged. **And the schema is NECESSARY, not merely convenient — that is enforced by the existing rules and needs no new one:** an origin cannot be allocated under `cadp.allocation-key.v1`, whose descriptor marks `work_run_ref` `PROJECTED`, because B2(3.4) would then require exactly one sealed `work-run` binding equal to the **allocated** `work_run_ref` — a value the caller would have to know before allocating the `effect_id` that IS it. The checked-out live path shows the refusal concretely: `startWork` allocates v1 with an all-zero placeholder and seals no `work-run` binding at all (`cadp/live/ops.ts`), which is zero bindings for a projected target ⇒ `ALLOCATION_BINDING_MISMATCH` before any K3 record exists.
   **This schema's allocation contract is IMMUTABLE for the store's lifetime (B2(2)(ii) as extended), and the identity consequence is the point of the whole design.** Its `allocation_contract_digest` therefore never takes a second value, so B1(2)'s derivation yields, for a given stamped `requester_ref` and a given `origin_key`, **exactly ONE allocation key and therefore exactly ONE `effect_id` FOR THE STORE'S LIFETIME** — one logical origin, one run identity, permanently, under **ANY** activation sequence. In particular a `C1 → C2 → C1` contract oscillation cannot fork one origin into two run scopes, and not because a lifecycle rule forbids the second allocation: **there is no `C2` for this schema to reach**, the entry being unable to change in the first place, so no second first-sealable allocation for that `(requester_ref, origin_key)` can ever come to exist (control A5, leg o-v).
   **The asymmetry with the external schema, stated so neither rule is read as the general one.** Contract-scoped **fresh-`effect_id` recovery** — B1(2)'s third consequence, B2(3.3)'s refusal-and-re-allocate, B2(9)'s drift rule, WP control 1's qualifier — is a property of schemas whose allocation contract is legitimately **MUTABLE**: `cadp.allocation-key.external.v1`'s entry carries repointable `binding_projection` targets a composition may re-aim, and contract-scoping its key is what makes that re-aiming recoverable rather than permanently stranding. That text is **untouched and stays exactly as it stands**. The run-origin schema is the opposite case: `binding_projection: []` (nothing to repoint) and a single fixed `purpose_relation` pair (nothing to re-pair) mean it has **no contract content that can meaningfully drift**, so contract-scoping would buy nothing and would instead split one logical origin into two run identities. **No contract-drift recovery, and no allocation-contract versioning boundary, exists for this schema** — there is no drift to recover from.

### B2. Allocation binding storage and first-seal atomicity

**Seam today.** `effect_allocation (allocation_key PK, effect_id UNIQUE)` (`cadp/kernel/store.ts`), written by `insertAllocation`, read by `allocationByKey` only. `sealEffectRequest` in `cadp/kernel/ingress.ts` **never reads the allocation table**: it stamps `requester_ref`, reads the material CAS object, checks the injected idempotency key, digests, and inserts under `withImmediate`, applying the K3 rule (identical semantic payload → idempotent stored row; different → `REQUEST_DIGEST_CONFLICT` incident + scope hold). An `effect_id` that was never allocated is accepted today.

**Three ownership lines, stated as such, because the whole of B1–B2 divides along them and every claim below is checkable against exactly one of them:**

- **(i) SCHEMA SHAPE AND FIELD ROLES — the SCHEMA OWNER**, carried by an immutable **schema descriptor** (2). What fields a versioned schema id has, and whether each is `PROJECTED` or `ENTROPY`, is authored by the plane or composition that owns the wire shape — for `cadp.allocation-key.external.v1` and for `cadp.allocation-key.v1` alike, that is the **Workflow Plane TD**. A bundle **carries** descriptors; it does not author their meaning.
- **(ii) PROJECTION TARGETS AND PURPOSE RELATIONS — POLICY/COMPOSITION**, carried by `allocation_schemas` exactly as it already stands (2): which `(authority_ref, namespace)` target each `PROJECTED` field binds onto, and which `operation_kind` each purpose pairs with. Validated **against the descriptor at activation**, never at runtime allocation.
- **(iii) GENERIC VALIDATION, BINDING AND ATOMICITY — the AUTHORITY PLANE**, unchanged in mechanism (3)–(10): tuple validation against the descriptor-derived key set, first-seal projection equality, the contract digest, the transaction. **The Authority core interprets NO field name**: after the migration (5) mandates, no allocation tuple field name appears anywhere in the allocation, binding or first-seal path — the kernel reads descriptor strings and compares them generically. **Scoped against the checkout rather than overstated:** `step_ordinal` also occurs in `cadp/kernel/ingress.ts`'s `WORK_STEP` replay-idempotency check and its `evidence_envelope (work_run_ref, step_ordinal)` index (`cadp/kernel/store.ts`), and `repo_id` in the GitHub adapter config and adapters (`cadp/kernel/kernelService.ts`, `cadp/kernel/adapters/github.ts`). **Neither occurrence is allocation vocabulary and neither is claimed by this contract:** the first is TD v0.4 §7.4's `WORK_STEP` chaining, which Part A explicitly does **not** claim (Workflow Plane content), and the second is the re-homed §6 target-adapter contract. The claim made here is exact — the allocation contract adds no domain field name, and **removes the one the kernel currently holds**.

1. **Storage — one generic shape for every schema.** `effect_allocation` gains exactly `{ requester_ref, allocation_schema, allocation_binding_digest, allocation_contract_digest, purpose }`, **all NOT NULL**, plus an index on `effect_id` (already UNIQUE) so a seal resolves the row from the `effect_id` it names. `allocation_binding_digest` = `sha256` over the `cadp-jcs-1` form of the **allocated wire tuple as received, whatever its schema** — an object, so canonicalization alone fixes the bytes (B1(3)). **`allocation_contract_digest`'s preimage is PINNED to one canonical JSON shape, not left to the implementer:** `allocation_contract_payload.v1` = `{ "descriptor": <the schema's exact `allocation_schema_descriptors` entry>, "allocation_schema": <the schema's exact `allocation_schemas` entry> }` — an object with exactly those two member names, each member being the registry entry **verbatim as active at allocation time** — and `allocation_contract_digest` = `sha256(cadp-jcs-1(allocation_contract_payload.v1))`. Stated as a definition because "the pair of the two entries" is conceptually clear but is **not** a canonical shape: an array, or the same two entries under different member names, would each digest differently, and this digest is load-bearing in three places (B1(2)'s key derivation, (3.3)'s first-seal contract integrity, (9)'s drift recovery), which cannot agree unless all three compute the identical preimage. Every later use of the name `allocation_contract_digest` in this document means exactly this. Shape and field roles come from (i), `binding_projection` and `purpose_relation` from (ii) — so the row records not only *what tuple* was allocated but *what shape it was declared to have* and *under which projection contract its fields would be read*. Descriptor drift and mapping drift each therefore derive fresh `effect_id`s. **Belt-and-suspenders, stated as such and not as redundancy:** the descriptor component is in practice **stable** for the store's lifetime, because (2)'s cross-activation immutability makes post-first-activation descriptor drift impossible; covering it anyway means the digest is exactly "the contract the tuple was allocated under" with no carve-out a future rule could widen. Deliberately an **entry** digest and not a `policy_ref`: an unrelated policy change (a new principal, a bound edit, another schema's entry) leaves this schema's entry byte-identical and therefore invalidates no allocation. The same digest is also the third component of B1(2)'s key derivation — the row is not merely stamped with the contract, it is **keyed** by it — which is what makes a drifted allocation re-allocatable rather than permanently stranded on an unrefreshable row (B1(2); the store has no runtime `UPDATE`). **No domain-named column exists and none is ever added per schema** — a new tuple schema changes no DDL (Spec v0.5 §7; Design D7-4). The row stays non-constitutional: in no K-record, no digest, no `ResolvedAdmissionBundle`.
2. **Two registries, one per ownership line — and the same-id redefinition hole closed a level up.**

   **(i) The schema descriptor registry — the SCHEMA OWNER's, carried but not authored by the bundle.** `cadp.kernel-config.v2` gains a closed-entry-key registry `data.cadp.allocation_schema_descriptors: [{ schema, fields: [{ field, role, value_contract }] }]` — required, may be `[]`, exact strings, closed entry keys (B3), gate-controlled at activation like every other registry. A field entry has **exactly three members, all required**. `role ∈ {PROJECTED, ENTROPY}` — a **closed two-value vocabulary**, anything else refused. `fields` lists the schema's **non-reserved** fields only: `schema` and `purpose` are reserved kernel vocabulary (5), and a descriptor naming either is refused at activation. B3(1)'s uniqueness rule extends to it: two entries sharing a `schema`, or two `fields` entries of one entry sharing a `field`, are refused `REGISTRY_DUPLICATE_KEY`.

   **`value_contract` — a CLOSED GENERIC vocabulary, so typed canonicity survives the move out of kernel code.** v0.4's allocation tuple was **typed**, not merely key-checked: `cadp/kernel/ingress.ts` requires `work_run_ref` to be a string beginning `cadp-v04:effect:` and `step_ordinal` to satisfy `Number.isInteger(...) && ... >= 1`, refusing `ALLOCATION_TUPLE_INVALID` otherwise. That typing is **part of the replay-identity contract, not incidental validation**, because the key is derived from the tuple's canonical bytes: `{step_ordinal: 1}`, `{step_ordinal: "1"}` and `{step_ordinal: 1.5}` are three distinct `cadp-jcs-1` forms and therefore three distinct `effect_id`s for what a caller means as one logical step — and `step_ordinal` is `ENTROPY`, projected nowhere and **never re-verified at seal**, so nothing downstream would ever catch the drift. Key-set checking alone would therefore have **removed** the v0.4 typing rather than re-homed it, breaking retry convergence on serialization drift. It is re-homed instead: each field entry carries `value_contract` from exactly this closed vocabulary, interpreted by kernel code **with no field-name knowledge whatsoever** —
   - **`POSITIVE_INTEGER`** — a constraint on the **PARSED JSON VALUE**, never on the wire lexeme that produced it: a parsed JSON number `n` such that `Number.isInteger(n) && n >= 1`. That is the implemented v0.4 rule re-homed **as the exact rule it already is** — `cadp/kernel/ingress.ts`'s `allocateEffectId` refuses `ALLOCATION_TUPLE_INVALID` on `!Number.isInteger(tuple.step_ordinal) || tuple.step_ordinal < 1` — and it is stated at the parsed level because that is the **only** level the implemented seam has: `cadp/kernel/api.ts` `JSON.parse()`s the raw request body into the tuple **before any validation runs**, so the original lexeme is already erased by the time any check could read it. A lexical rule here would be unimplementable at this seam, and was never v0.4 behavior. **The convergence this entails is a FEATURE of the identity contract, not a gap in it:** the wire forms `1`, `1.0` and `1e0` parse to the same value, canonicalize to the same `cadp-jcs-1` bytes (`cadp/kernel/canonical.ts` serializes numbers via `JSON.stringify`, so all three render `1`), and therefore mint the **SAME** allocation identity — one logical step, one `effect_id`, which is precisely the retry convergence of (2) and control P4. No lexical distinction survives the parse, and none is needed. What the parsed level still refuses is everything that actually parses differently: `"1"` (a string, not a number), `0` and `-1` (numbers below 1) and `1.5` (a non-integer) — each `ALLOCATION_TUPLE_INVALID`;
   - **`NONEMPTY_STRING`** — a JSON string of length ≥ 1;
   - **`EFFECT_ID`** — a nonempty string in the platform's effect-id shape, i.e. the `cadp-v04:effect:`-prefixed form the kernel already validates on this exact path today (`cadp/kernel/ingress.ts`, `allocateEffectId`'s `work_run_ref.startsWith("cadp-v04:effect:")` check).

   **The plane split, stated exactly, because this is where it could be misread as re-importing domain vocabulary:** the **field name** is schema-owner data (bundle-carried, never in kernel code), and the **value validator** is a **generic Authority vocabulary** naming no field and no schema — the kernel reads a descriptor string, dispatches on it, and never learns that the field it is checking is called `step_ordinal` or means an ordinal. The fence of (iii) is therefore unchanged: `POSITIVE_INTEGER` is exactly as domain-free as `ENTROPY` is. Anything outside the three is refused at activation like any other closed vocabulary. **Honest residual on canonicity, since a value contract bounds types and not every equivalence:** `cadp-jcs-1` fixes member order, string escaping and number serialization, and `POSITIVE_INTEGER` additionally forecloses the string and non-integer values that would otherwise key one logical step separately — number-**form** variance (`1` / `1.0` / `1e0`) needs no contract at all, having already been erased by `JSON.parse` and then by JCS number serialization before any key is derived; what `cadp-jcs-1` does **not** do is normalize Unicode, so two NFC/NFD spellings of one `NONEMPTY_STRING` remain distinct byte sequences and therefore distinct allocations. That is the schema owner's field to spell consistently — `EFFECT_ID` and the WP tuple's sha/id fields are ASCII by their own contracts — and it is a distinctness residual, never a collision: two spellings can never converge onto one `effect_id`.

   The descriptor for `cadp.allocation-key.external.v1` — `repo_id`, `candidate_base_sha` and `candidate_sha`, each `{PROJECTED, NONEMPTY_STRING}` — is **canonically defined by the Workflow Plane TD** (WP §3.3, which owns that wire shape); the descriptor for `cadp.allocation-key.v1` — `work_run_ref` `{PROJECTED, EFFECT_ID}`, `step_ordinal` `{ENTROPY, POSITIVE_INTEGER}` — is **also Workflow-Plane-owned** (B1(4)). Both canonical definitions stay with the schema owner; only the validator vocabulary they draw from is this document's.

   **(ii) CROSS-ACTIVATION DESCRIPTOR IMMUTABILITY — a versioned schema id is a fixed contract for the store's lifetime.** At genesis and at every `POLICY_ACTIVATE` recheck #17: **if any prior activation in the sealed store carried a descriptor for the same `schema` id, the new bundle's descriptor for that id MUST be byte-identical to it** — `cadp-jcs-1` digest equality against the prior — else the bundle is refused **`SCHEMA_DESCRIPTOR_CHANGED`**, no activation. A different wire shape therefore **REQUIRES a different schema id** (a version bump), which is visible in every tuple, every allocation row and every conformance report. This is what makes the WP-defined 5-field `cadp.allocation-key.external.v1` shape a **fixed contract rather than a per-bundle variable**: no two bundles, and no two activations, can make that id mean two shapes. The comparison is against the **sealed store**, not against the currently active bundle, so a descriptor cannot be laundered by withdrawing it in one activation and re-adding a different one in the next. **Honest scope, because the immutability binds shape-drift and not first authorship:** what binds the FIRST activation to carry the *canonical* descriptor is not this rule and not any kernel check — the kernel has no canonical text to compare against, and inventing one would re-import the field names (iii) forbids. It is bound by exactly two things, both stated so the residual is falsifiable rather than implied: the genesis/`POLICY_ACTIVATE` gate itself (a descriptor is Human-approved bundle content like every other registry), and the WP contract binding its **exact schema id** — so a store whose first-ever activation smuggled, say, a 4-field descriptor under that id is a store that **does not implement the WP contract**, detectable by comparing the sealed descriptor against the WP TD's canonical definition, and **unfixable in place**: immutability forbids correcting it under the same id. A weaker allocation contract remains **expressible**, but only under a **visibly different schema id**, gate-controlled, and never under the id WP binds.

   **Extension for `cadp.allocation-key.run-origin.v1` — its MAPPING entry is immutable too, not only its descriptor.** For that one schema id, immutability binds **both** registry entries: once any prior activation in the sealed store carried that `schema` id, a bundle whose `allocation_schema_descriptors` entry for it **or** whose `allocation_schemas` entry for it is not byte-identical to the prior one — **including REMOVING either entry** — is refused **`SCHEMA_DESCRIPTOR_CHANGED`**, no activation. **Justified precisely by what that schema's mapping entry contains, and claimed for no other schema:** its `binding_projection` is `[]` (there is no projection target to repoint) and its `purpose_relation` is the single fixed `work-start`↔`WORK_START` pair (there is nothing to re-pair), so the entry has **no content whose drift a composition could legitimately want** — while leaving it mutable makes its `allocation_contract_digest` a second value that B1(2)'s key can take, which forks one logical run origin into two run identities under a contract oscillation (B1(5); control A5, leg o-v). `cadp.allocation-key.external.v1`'s entry is the opposite case and stays **mutable and contract-scoped exactly as it is** — nothing here touches it. **PRECEDENCE against the generic coverage checks, stated as an ordering rather than left to implementation:** for a `schema` id any prior activation already carried, this immutability comparison runs **BEFORE** B2(5)'s `ALLOCATION_SCHEMA_UNREGISTERED` check and before (iii)'s `ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE` coverage check, so a bundle **deleting** the run-origin mapping entry is refused `SCHEMA_DESCRIPTOR_CHANGED` — the prohibited mutation of an activated contract, which is what it is — and **never** `ALLOCATION_SCHEMA_UNREGISTERED`, which names a schema that was never registered and would misreport a deletion as an absence. **The v0.5 seam, named honestly:** `assertProjectionCoverage` (`cadp/kernel/policyBundle.ts`) today treats a descriptor carried without a mapping as **inert** rather than refused, and no cross-activation comparison exists at all, so both the immutability check and its precedence are the implementation work this contract mandates. The honest-scope note above applies unchanged to first authorship: a store whose first-ever activation carried a non-conforming run-origin entry does not implement this contract, is detectable against WP §3.6's canonical shape, and is **unfixable under the same id**.

   **(iii) The projection registry — POLICY/COMPOSITION data, validated against the descriptor at activation.** `data.cadp.allocation_schemas: [{ schema, binding_projection: [{ tuple_field, authority_ref, namespace }], purpose_relation: [{ purpose, operation_kind }] }]` — exactly as it stands, required, may be `[]`, exact strings, closed entry keys (B3), gate-controlled at activation exactly like `identity_registry` and `adapter_registry`. **Every value in it is supplied by the policy bundle**; the Authority core stores these strings, compares them, and interprets none of them (Spec v0.5 §7; Design D7-4). **Activation now validates each entry AGAINST that schema's descriptor**, at genesis validation and `POLICY_ACTIVATE` recheck #17: **every `PROJECTED` field has exactly one `binding_projection` entry; no `ENTROPY` field has any; and no `binding_projection` names a `tuple_field` outside the descriptor's `fields`** (which disposes of the reserved names too, they not being descriptor fields). Any violation refuses **`ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE` AT `POLICY_ACTIVATE`, never discovered at runtime allocation** — one generic rule over descriptor data, with no schema named in kernel code and no per-schema carve-out. B3(1)'s uniqueness rule extends to it — two rows sharing a `schema`, two `binding_projection` entries of one row sharing a `tuple_field`, two `binding_projection` entries of one row sharing an `(authority_ref, namespace)` **target** pair, or two `purpose_relation` entries of one row sharing a `purpose` are refused `REGISTRY_DUPLICATE_KEY` — for the same reason as the other registries: a first-match lookup would otherwise let bundle authoring order decide what a seal is compared against. The **target**-pair leg is the authoring-side half of (3.4)'s exactly-one rule: an entry projecting two different `tuple_field`s onto the same `(authority_ref, namespace)` demands two bindings on one target pair, which (3.4) then refuses `ALLOCATION_BINDING_AMBIGUOUS` on every conforming seal — an unsatisfiable contract is refused at activation rather than discovered as a permanent seal failure, and the two rules cannot disagree because neither can be authored around the other.
3. **First seal verifies contract, material AND purpose, before any K3 record exists.** The first `seal_effect_request` for an `effect_id` (no `effect_request` row yet) MUST resolve the allocation row by `effect_id`; absent ⇒ `ALLOCATION_NOT_FOUND` (closing caller-invented effect identities — Spec v0.5 K3). It then executes exactly these equalities, all of them generic:

   1. **principal** — stamped `requester_ref` == row `requester_ref`, else `ALLOCATION_PRINCIPAL_MISMATCH`;
   2. **tuple integrity** — the caller re-presents the allocated tuple as **transport, never a draft field**; the core recomputes its `cadp-jcs-1` digest and requires equality with `allocation_binding_digest`, else `ALLOCATION_BINDING_MISMATCH`. **Nothing inverts the digest**; the stored digest only confirms what was re-presented;
   3. **contract integrity** — the core resolves **both** the descriptor entry and the `allocation_schemas` entry for the row's `allocation_schema` **under the policy active at seal time**, reassembles `allocation_contract_payload.v1` from them (1), recomputes `sha256(cadp-jcs-1(·))`, and requires equality with the row's `allocation_contract_digest`, else `ALLOCATION_CONTRACT_CHANGED` (either entry withdrawn between allocation and seal fails this leg too, there being no digest to equal; the descriptor half cannot drift, by (2)(ii)). **This leg runs before (4) and (5) and gates them**: without it, leg 2's digest equality is satisfiable while the *meaning* of the tuple's fields has changed underneath — a policy activation that swaps which `tuple_field` maps to which `(authority_ref, namespace)` target (exchanging, say, the commit and base-commit projections) lets the caller re-present the byte-identical tuple with `work_bindings` arranged to the NEW projection and seal an effect whose material is the inverse of what was allocated, with every other equality passing. Leg 3 makes that a **refusal**: the proposer re-allocates under the new contract — and that re-allocation is a real recovery, not a loop back into the same refusal, because B1(2)'s key is contract-scoped, so the same principal re-presenting the same tuple derives a different key and receives a fresh `effect_id` carrying the new digest. It is exactly the registry-drift discipline (9) already applies to `requester_ref`, now applied to the projection contract itself;
   4. **material** — for each `binding_projection` entry registered for the row's `allocation_schema`, the sealed request's `work_bindings` MUST contain **exactly one** binding whose `authority_ref` and `namespace` equal the entry's, and that binding's `object_id` MUST equal the re-presented tuple's `tuple_field` value. **Zero** such bindings, or a sole binding whose `object_id` differs, is `ALLOCATION_BINDING_MISMATCH`; **two or more** — regardless of their `object_id`s, and including two carrying the same one — is `ALLOCATION_BINDING_AMBIGUOUS`, refused **before any K3 record exists** like every other leg here. The ambiguity leg is load-bearing and not tidiness: `cadp/kernel/records.ts` defines `work_bindings` as `readonly SubjectBinding[]` **with no uniqueness validation of any kind**, so an existence-only check passes on a request carrying `commit=A` (satisfying the projection) *and* `commit=B`, after which the composition — or any later reader selecting by namespace — may choose B, and the exact-candidate binding this whole contract exists to fix is ambiguous with the check already passed. Requiring exactly one is what makes "the allocated tuple field IS the sealed subject" a statement about the sealed record rather than about one witness inside it. **Scope, stated honestly: this is uniqueness for PROJECTED `(authority_ref, namespace)` pairs, checked at first seal only. General `SubjectBinding` uniqueness across all namespaces is NOT this contract's claim** — an unprojected namespace may still carry repeats, and nothing here changes `records.ts`;
   5. **purpose** — the sealed `operation_kind` MUST equal the `operation_kind` that the registered `purpose_relation` pairs with the allocated `purpose`; no pair for that `purpose` is itself a refusal. Else `ALLOCATION_PURPOSE_MISMATCH`. This leg runs **for every allocation schema without exception**, `cadp.allocation-key.v1` included (5).

   This is WP §3.3's contract restored as that document states it: a first seal naming a different **candidate, base, purpose or principal** than the allocation is REFUSED BEFORE ANY K3 RECORD EXISTS, never deferred to a composition-level admission predicate that runs after one. It imports no domain vocabulary to do it — every string compared in (3) and (4) is either bundle-authored data or the caller's own tuple, and the core reads none of them for meaning.
4. **Why a projection entry carries `authority_ref`.** `cadp/kernel/records.ts` defines a `SubjectBinding`'s identity as `{ authority_ref, namespace, object_id, revision_or_version?, content_digest? }` with **`authority_ref` required** — a `namespace`/`object_id` pair is not, by itself, a subject identity. Each entry therefore names the full `(authority_ref, namespace)` pair, so an allocation can never be satisfied by an identically-named subject standing under a **different** authority (`github.com` vs `cadp-store:k04` vs a second forge), which a namespace-only match would accept. The optional `revision_or_version` and `content_digest` are not compared: the tuple field is the object identity, and comparing an optional field would make the check satisfiable by omission.
5. **Schema coverage is closed — no schema is exempt, including the default one.** **Every** allocation schema MUST have **both** a `data.cadp.allocation_schema_descriptors` entry and a `data.cadp.allocation_schemas` entry: `cadp.allocation-key.external.v1` and `cadp.allocation-key.v1` alike. A tuple schema missing **either** **cannot be allocated** — `allocate_effect_id` refuses `ALLOCATION_SCHEMA_UNREGISTERED` — so no allocation can come to exist that a first seal would have to check against nothing, and there is no default path around (3.5). Each entry's `purpose_relation` MUST further be **total over the purposes that schema may allocate**: allocating a `purpose` for which the entry registers no pair is refused `ALLOCATION_PURPOSE_NOT_REGISTERED` **at allocation time** (the existing `allocation_purposes` membership check is unchanged and runs alongside it), and a first seal whose `operation_kind` differs from the registered pair is refused `ALLOCATION_PURPOSE_MISMATCH` **before any K3 record exists** — one rule, one code path, for internal and external schemas identically.
   **The valid tuple key set is the DESCRIPTOR's, and it is THE SAME UNDER EVERY BUNDLE.** For every schema without exception it is **exactly** `{schema, purpose}` ∪ the descriptor's `fields` list. `schema` and `purpose` are the **two reserved fields** and the only kernel vocabulary in any tuple — the Kernel reads `schema` to resolve the descriptor and the entry, and `purpose` for `allocation_purposes` membership and (3.5). At allocation time the presented tuple is validated **on both axes, per field**: its key set is compared against that set, and each non-reserved field's **value is checked against that field's `value_contract`** (2)(i). Any **unknown or missing** key, or any value violating its field's contract, is refused `ALLOCATION_TUPLE_INVALID` — **before any `effect_allocation` row exists**, so a non-conforming tuple never mints an `effect_id` at all. Both axes compare against descriptor strings, so **the Kernel holds no field name for any schema**: `repo_id`, `candidate_base_sha`, `candidate_sha` and `step_ordinal` live only in the WP TD and in bundle data (Spec v0.5 §7; Design D7-4).
   **This is what makes a versioned schema id a fixed wire contract rather than a per-bundle one.** Because the key set comes from the descriptor and **not** from `binding_projection`, a bundle can no longer change a schema's accepted shape by changing what it projects: an omitted mapping is not a narrower tuple, it is an **invalid bundle**, refused `ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE` at `POLICY_ACTIVATE` by (2)(iii). And because (2)(ii) forbids a descriptor for an already-seen `schema` id from changing at all, no second bundle and no later activation can give that id a second shape. **The WP contract is thereby unforgeable on both axes at once:** a bundle can neither *accept the WP tuple while skipping a projection* (activation refusal), nor *redefine the WP wire schema under the same schema id* (`SCHEMA_DESCRIPTOR_CHANGED`) — the stronger of the two claims, and the one the derived-key-set design could not make.
   **`ENTROPY` is a role, not a semantics, and it is where the honest residual sits.** A field marked `ENTROPY` is a valid tuple field that contributes to key derivation and is **not projected, therefore not re-verifiable at seal** — no K3 field carries it; per-key idempotency and the K3 conflict rule bound it. That is the schema owner's declared choice, visible in the sealed descriptor, immutable thereafter, and it is exactly `step_ordinal`'s status under v1's Workflow-Plane-owned descriptor (B1(4)). A schema whose fields are **all** `ENTROPY` — or whose `fields` list is empty — is expressible and binds no material; it is not a weakening of any other schema, because it is a **different, visibly-named schema id** whose tuples are its own contract, and (3.4) is vacuous only over a tuple that projects nothing.
   v1's `purpose_relation` **values** — `work-start` and the other internal purposes paired with their operation kinds — are **composition-authored bundle data exactly as the external schema's are**; the reference composition supplies them and this document cites them as data, never enumerating them normatively (Spec v0.5 §7; Design D7-4). The Kernel names the schema string, never a purpose or an `operation_kind` of it.
   **Migration consequence, stated rather than hidden: for v1 it is caught at genesis, not deferred to a first allocation.** The set of purposes `cadp.allocation-key.v1` may allocate is **statically known to be all of `data.cadp.allocation_purposes`** — the implemented `allocateEffectId` admits a v1 tuple whose `purpose` is any member of that flat, schema-independent list and rejects every non-member (`cadp/kernel/ingress.ts`), and both lists sit in the same closed-schema `data.cadp` object that `validateKernelConfig` already checks whole (`cadp/kernel/policyBundle.ts`). Totality for v1 is therefore a **static property of the bundle**, and validation enforces it as one: a v0.5 genesis bundle carrying no v1 entry, or a v1 entry whose `purpose_relation` omits **any** member of `allocation_purposes`, is **REFUSED at genesis validation / `POLICY_ACTIVATE` recheck #17** (`ALLOCATION_SCHEMA_UNREGISTERED`, `ALLOCATION_PURPOSE_NOT_REGISTERED`) — the deployment never activates, so it cannot allocate internal effects at all. The allocation-time refusal above remains the uniform rule and the backstop for schemas whose allocatable purpose set the Kernel does not statically know; for v1 it is unreachable under any bundle that activated. That is the intended pressure, caught immediately, and it is a refusal, never a fallback to the pre-carve-out behaviour.
6. **Illustrative only — composition data, not a normative table here.** The reference bundle's entry for `cadp.allocation-key.external.v1` — the repository, base-commit and commit namespaces, the GitHub authority, and the three purpose relations — is **composition data, authored where WP §§3.4 (material bindings) and §3.3 (the purpose correspondence) define them**. It is cited, not restated normatively here. One illustrative fragment, marked **composition-supplied data**: `{ schema: "cadp.allocation-key.external.v1", binding_projection: [{ tuple_field: "candidate_sha", authority_ref: "github.com", namespace: "commit" }, …], purpose_relation: [{ purpose: "pr-create", operation_kind: "PR_CREATE" }, …] }`. The test that these are data and not core vocabulary: changing any string in them is a policy change under the ordinary activation gate and requires no Kernel change at all.
7. **Atomicity.** The read of the allocation row, the equality checks of (3) and the `effect_request` insert occur **in one store transaction** with the allocation row locked for the duration (`SELECT … FOR UPDATE` on PostgreSQL; `BEGIN IMMEDIATE` single-writer on the SQLite reference, i.e. the existing `withImmediate`). Consequence, which is the point of the contract: a first seal whose principal, projected material or purpose does not equal the immutable allocation row is **REFUSED deterministically before any K3 record exists**, under every interleaving of concurrent first-seal attempts — the check is against the allocation row, never against a race-visible request row, so no ordering makes a mismatching seal land. Concurrent *matching* first seals resolve by the unchanged §3.3 rule: one inserts, the other returns the stored row. Once a `request_digest` exists, the ordinary K3 conflict rule governs everything after it, unchanged.
8. **Refusal shape.** Reason codes `ALLOCATION_NOT_FOUND`, `ALLOCATION_PRINCIPAL_MISMATCH`, `ALLOCATION_BINDING_MISMATCH` (re-presented tuple digest ≠ `allocation_binding_digest`, or a projection entry unsatisfied by zero bindings or by one mismatching binding), `ALLOCATION_BINDING_AMBIGUOUS` (two or more sealed bindings on one projected target pair — (3.4)), `ALLOCATION_CONTRACT_CHANGED` (the `allocation_contract_payload.v1` assembled from the schema's active descriptor and `allocation_schemas` entries no longer digests to `allocation_contract_digest`, or either entry no longer exists — (1), (3.3)) and `ALLOCATION_PURPOSE_MISMATCH` at first seal; `ALLOCATION_TUPLE_INVALID` (a presented key outside the schema's descriptor-derived key set, a missing one, **or a value violating its field's `value_contract`** — for **every** schema alike, and always before any allocation row exists — B1(1), B2(2)(i), B2(5)), `ALLOCATION_SCHEMA_UNREGISTERED` (no descriptor entry, or no `allocation_schemas` entry) and `ALLOCATION_PURPOSE_NOT_REGISTERED` at allocation; the latter two again at genesis/activation validation against the bundle itself, together with `ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE` (a `PROJECTED` field with no mapping or more than one, an `ENTROPY` field with any, or a mapping naming a field outside the descriptor — B2(2)(iii)) and `SCHEMA_DESCRIPTOR_CHANGED` (a descriptor for a `schema` id any prior activation already carried, not byte-identical to it — B2(2)(ii); **for `cadp.allocation-key.run-origin.v1` this one code covers BOTH that id's descriptor entry AND its `allocation_schemas` mapping entry, and covers REMOVAL of either as well as change to either, and it is evaluated BEFORE `ALLOCATION_SCHEMA_UNREGISTERED` and `ALLOCATION_SCHEMA_PROJECTION_INCOMPLETE` for an already-activated run-origin id — so a mapping deletion is refused as the prohibited mutation it is and never as a never-registered schema**). On any of them no `EffectRequestV1` is sealed and no effect is performed. `ALLOCATION_PRINCIPAL_MISMATCH` is additionally raised on **re-seals**, by the universal gate of (10), and carries the same shape there. **No `KERNEL_INCIDENT` and no scope hold is raised** — deliberately, and this is normative: the allocation is requester-scoped, so a mismatching seal is a caller error against an effect identity the caller does not own, and raising a scope hold would let any principal freeze another principal's effect scope by attempting one bad seal. The K3 conflict path (which does raise an incident) is untouched **and, per (10), is reachable only by the effect's own requester**.
9. **Registry drift is fail-closed, on the principal AND on the contract.** The row stores the `requester_ref` resolved under the policy active at allocation; the first seal compares the `requester_ref` stamped under the policy active at seal time. Symmetrically, the row stores `allocation_contract_digest` over the `allocation_contract_payload.v1` assembled from the schema's descriptor and `allocation_schemas` entries active at allocation; the first seal recomputes it over the payload assembled from those entries active at seal time (1), (3.3). A policy activation that re-maps the principal, or that changes **any byte** of the schema's `allocation_schemas` entry — reordering, retargeting or withdrawing a `binding_projection`, adding or dropping a `purpose_relation` pair — makes one of those equalities fail and the seal is REFUSED; the proposer re-allocates under the new bundle and seals against it. **That re-allocation terminates, on both legs, because B1(2)'s key carries both drifting values**: `requester_ref` and `allocation_contract_digest` are key components, not merely stored columns, so a re-allocation after either drift derives a different `allocation_key` and yields a fresh row stamped under the new bundle instead of converging onto the stale one — which matters precisely because the store has no runtime `UPDATE` to refresh a stale row with (`cadp/kernel/store.ts`), so key-scoping is the only available recovery. (A principal whose `identity_registry` entry was **withdrawn** rather than re-mapped is refused `FORBIDDEN_FOR_PRINCIPAL` at re-allocation; that is loss of authority, not drift, and is correctly not recoverable here.) Both are refusals, never a fallback to the raw principal string and never a silent re-interpretation of an allocation under a projection it was not made under. Note the two are independently necessary: without (3.3) the projection could be swapped under a byte-identical tuple; without the principal leg the tuple could be re-presented by a re-mapped caller. Bounded blast radius, by construction: the digest covers **one entry**, so activations that leave this schema's entry untouched invalidate none of its allocations.
10. **The allocation-principal gate runs on EVERY seal — first seal and re-seal alike — and BEFORE any K3 comparison.** Stated as its own rule because (3)'s legs are first-seal-only and this one is not. **Seam, in this checkout:** `sealEffectRequest` (`cadp/kernel/ingress.ts`) builds the K3 comparison payload from the **stamped** `requester_ref` — `semantic(r)` covers `requester_ref, work_bindings, target_ref, operation_kind, material_schema, material_digest, material_ref, prior_effect_refs`, and the stamp is the caller's own `identity.producer_ref` — so a principal **B** calling `seal_effect_request` on **A's** already-sealed `effect_id`, with *any* material including a byte-identical copy of A's, produces a payload differing from the stored row on that one field: `REQUEST_DIGEST_CONFLICT`, a `KERNEL_INCIDENT`, and a **scope hold on A's effect**. That is exactly the cross-principal freeze (8) refuses to allow at first seal, resurrected **after** K3 exists, and it contradicts B1(2)'s "neither can conflict the other's request". **Therefore, on every `seal_effect_request`, BEFORE the existing-row lookup and before any identical/conflict comparison, the Ingress resolves the `effect_allocation` row for the named `effect_id` and compares its `requester_ref` against the stamped caller's; inequality is refused `ALLOCATION_PRINCIPAL_MISMATCH` with NO `KERNEL_INCIDENT` and NO scope hold** — the same DoS rationale as (8), now uniform rather than first-seal-only. `ALLOCATION_NOT_FOUND` still precedes it for an `effect_id` with no allocation row at all (which, given (3), no sealed effect ever is). Consequence, which is the whole point: only a caller equal to the allocation's `requester_ref` ever reaches the K3 identical/conflict semantics, so `REQUEST_DIGEST_CONFLICT` — which rightly *does* raise an incident and a scope hold — is reachable **only by the effect's own requester re-sealing different material**, the case that rule was written for. The K3 rule itself, its incident and its hold are otherwise unchanged.
11. **Not a K8.** Nothing above is a constitutional record, a new evidence kind, or a new admission state. It is the pre-K3 window's implementation, delegated to this document by WP §3.3.

### B3. Registry uniqueness and closed entry keys

**Seam today.** `validateKernelConfig` (`cadp/kernel/policyBundle.ts`) enforces the closed top-level key set (`ALLOWED_KEYS`), the exact-string/no-pattern rule on `identity_registry.principal` and `adapter_registry.producer_ref`, entry field types, the `produced_at_source` shape, the governed-writer opt-in vocabularies and the invariant-P reserved-constant rule, bounds and bootstrap-scheme retention. It performs **no duplicate detection**, and the closed-key check is `data.cadp` top level only — an unknown key *inside* an entry validates and activates. Resolution is by first match: `identityEntry`/`adapterEntry` in `cadp/kernel/policyState.ts` are `find()`.

1. **Uniqueness (new activation-time rejection).** A bundle is refused at `POLICY_ACTIVATE` recheck #17 / genesis validation if any of the following holds: two `identity_registry` rows share a `principal`; two `identity_registry` rows share a `producer_ref`; two `adapter_registry` rows share a `producer_ref`. Reason `REGISTRY_DUPLICATE_KEY`. Grounding for each: a duplicate `principal` makes `identityEntry`'s `find()` silently order-dependent, so the caller's `process_class` (and therefore its `METHOD_REACH`) and its stamped `producer_ref` are decided by bundle authoring order; a duplicate `producer_ref` in `identity_registry` makes the reference policy's `registry_entry(producer)` a function with two candidate outputs — in Rego that is a conflicting-output evaluation error, i.e. an `EvaluatorFailure` and **no** decision (fail-closed but opaque), while the PEP computing the same derivation in TypeScript takes the first row (fail-open relative to the evaluator, and the two can disagree about `identity_class.product`, which is exactly the value the independence predicate compares); a duplicate `adapter_registry` row makes the allowed `evidence_kinds`, `source_relation` and `produced_at_source` of one producer order-dependent at the ingress. Rejecting at activation makes all three unconstructible.
2. **Unknown keys inside entries are rejected** — decided here, and decided the same way as the top level, for the same fail-closed reason: **an inert key is not a declared binding.** A key the Kernel does not read is either a future binding activated early (so its meaning is unenforced while it appears authoritative to a reader) or a typo silently disabling the binding it was meant to be (`producer-ref` for `producer_ref`, `evidence_kind` for `evidence_kinds`). Spec v0.5 §2.5's rule — a missing or unverifiable required fact never satisfies a requirement — makes silent acceptance the wrong default for the one document that declares who may say what. Reason `REGISTRY_UNKNOWN_ENTRY_KEY`.
3. **Closed entry key sets** (exact; anything else is refused): `approved_digest_schemes` `{algorithm, canonicalization}`; `root_public_keys` `{key_id, alg, public_key, valid_from, valid_to?}`; `attestation_keys` `{key_id, alg, public_key, purpose, valid_from, valid_to?}`; `identity_registry` `{principal, producer_ref, identity_class{vendor, product, account, process_class}}`; `adapter_registry` `{producer_ref, evidence_kinds, source_relation, produced_at_source{kind, claim_pointer?}, replay_idempotency?, governed_edge?}`; `allocation_schema_descriptors` `{schema, fields[{field, role, value_contract}]}` (B2(2)(i)), the nested field entry's **three members all required**, `role` being a **closed two-value vocabulary** `{PROJECTED, ENTROPY}` and `value_contract` a **closed three-value vocabulary** `{POSITIVE_INTEGER, NONEMPTY_STRING, EFFECT_ID}`, both validated exactly like the other closed vocabularies; `allocation_schemas` `{schema, binding_projection[{tuple_field, authority_ref, namespace}], purpose_relation[{purpose, operation_kind}]}` (B2(2)(iii)); `subject_complete_assembly` `{evidence_kind, subject_namespace, operation_kinds}` (B4(1)); `kernel_subject_namespaces` `{namespace, authority_ref}` (4). **Nested entry key sets are closed identically and for the identical reason** — an unknown key inside `binding_projection[]` or `purpose_relation[]` is refused exactly as one inside an `identity_registry` row is, because "inert key ≠ declared binding" (2) does not weaken with nesting depth, and these are precisely the objects a first seal compares against. **Inventory audit of every v2 key this document introduces**, so the list above is checkable as complete rather than assumed so: `allocation_schema_descriptors` (B2(2)(i)) with its one nested shape `{field, role, value_contract}` — all three required, `value_contract` being a closed-vocabulary key like `role` — closed as listed and unique per `schema` and per `field`; The two optional `adapter_registry` keys are the governed-writer opt-ins that exist in the checked-out schema and in the reference `adapter_registry` row `governed:reclassification`; omitting them from the closed set would refuse the current reference bundle.
4. **Exact-subject kernel lookups — `kernel_subject_namespaces`, plus a seal-time ambiguity lock.** B2(3.4) matches a projection on the full `(authority_ref, namespace)` pair, for the reason B2(4) gives — but **every implemented kernel consumer of the work-run scope selects by `namespace` ALONE**: `draft.work_bindings.find((b) => b.namespace === "work-run")?.object_id` in `cadp/kernel/ingress.ts` (the `work_run_ref` the `effect_request` row is indexed by), and the same `find` three times in `cadp/kernel/pep.ts` — recheck #5's `HUMAN_DECISION`/`AGENT_DECISION` scope equality, `REQUIRE_NO_PRIOR_UNKNOWN_IN_SCOPE`, and `MAX_EFFECTS_IN_WORK_RUN`. The values are composition-supplied strings like every other registry's: the reference bundle declares `work-run` under the **constitutional store's** authority (`cadp-store:k04`, as `cadp/product/activities.ts` binds it) — **cited as composition data, hard-coded nowhere in the core**. **(b) A validation lock at seal time.** A request whose `work_bindings` carry **MORE THAN ONE** binding in any declared kernel namespace — **regardless of `authority_ref`** — is refused `KERNEL_NAMESPACE_AMBIGUOUS` **before any K3 record exists** and **before B2(3)'s legs (pre-K3)**, so binding order can never decide what any reader sees, **including a reader not yet migrated to (a)**. **(c) Declaration itself cannot be authored away — a cross-field activation invariant.** `kernel_subject_namespaces` is required-but-**may be empty**, and (a)/(b) bind only **declared** namespaces, so a bundle that enables the run profile (`run_profile_enrolled_requester_refs` non-empty, B5(3)) while declaring no work-run namespace would **activate with the ambiguity lock and the exact-pair lookups silently absent** — the whole safeguard disarmed by an omission rather than by an attack. Therefore, at genesis validation and `POLICY_ACTIVATE` recheck #17: **a bundle whose `run_profile_enrolled_requester_refs` is non-empty MUST declare EXACTLY ONE `kernel_subject_namespaces` entry for the work-run namespace, else it is refused `KERNEL_NAMESPACE_UNDECLARED`** (per-`namespace` uniqueness is already (1)'s). Generally, in one rule: **every namespace the kernel code itself consumes MUST be declared whenever any bundle feature that consumes it is enabled** — and the kernel-consumed namespace list is **code**, not bundle content: today exactly the work-run namespace, which is kernel vocabulary because the kernel itself consumes it (the `effect_request` index, `MAX_EFFECTS_IN_WORK_RUN`, recheck #5's decision scope — `cadp/kernel/ingress.ts`, `cadp/kernel/pep.ts`), never domain vocabulary. A **namespace** the kernel reads is not a tuple **field name**: B2(5) leaves no schema's field set in kernel code. **The v0.4 seam, stated honestly:** the namespace-only `find` in `ingress.ts`/`pep.ts` **is the implemented state at this checkout**; the exact-match migration is the implementation work this contract mandates, and (b) is what makes the contract sound in the interval rather than contingent on the migration landing everywhere at once. Scope: this is uniqueness for **declared kernel namespaces**, additional to and independent of B2(3.4)'s exactly-one rule for **projected target pairs** — neither implies the other, and B2(3.4)'s honest scope note (a namespace that is neither projected nor declared may still carry repeats; `cadp/kernel/records.ts` adds no `SubjectBinding` uniqueness) is unchanged.
5. **Schema identity.** (1)–(4), together with B2(2), B4(1) and B5(3), define **`cadp.kernel-config.v2`**, required exactly by `schema` string. Because activation acceptance is narrowed, this is a generation-boundary change: v0.5 genesis bundles carry v2, and no running v0.4 environment is mutated in place (Spec v0.5 §10).

### B4. Assembly completeness

**Seam today.** `assemble_admission_input(effect_id, evidence_refs[])` takes the caller's list verbatim: `cadp/kernel/api.ts` parses `{ effect_id, evidence_refs }` from the body and `Ingress.assembleAdmissionInput` resolves each id, records `{evidence_id, envelope_digest}`, and seals K4. The store already supports the needed read: `evidence_subject(evidence_id, subject_key)` with `subject_key = "<authority_ref>|<namespace>|<object_id>"` and an index, plus an `evidence_kind` index, joined by `evidenceBySubjectKey`. The reference policy's predicates are existential (`some e in input.evidence`), so **a caller can today withhold an unfavourable sealed envelope of a kind the gate consumes** and the evaluator never learns it exists.

1. **Declaration.** `data.cadp.subject_complete_assembly: [{ evidence_kind, subject_namespace, operation_kinds[] }]` — required, may be `[]`, exact strings, closed entry keys (B3), part of `cadp.kernel-config.v2`. Kernel-read, so it lives under `data.cadp` and not in rego-private `policy_params`. All three components are identity strings the Kernel already handles; **no material field is parsed** — domain material vocabulary stays in the composition (Spec v0.5 §7).
2. **Query contract.** For a declared entry and a sealed `EffectRequestV1` whose `operation_kind` the entry lists, the Platform computes, from that request's own `work_bindings`, every subject key `<authority_ref>|<subject_namespace>|<object_id>` it names, and selects **every** sealed envelope of that `evidence_kind` bound to that exact key — the complete set, not a latest-wins pick. This is the existing `(evidence_kind, subject_key)` join over the sealed store. The `latestEvidenceOfKind` helper in `store.ts` MUST NOT be used for assembly: "latest" is not authority in sealed history (Spec v0.5 §2.6; TD v0.4 §6.6). If the sealed `work_bindings` name **no** binding in `subject_namespace`, assembly REFUSES `ASSEMBLY_SUBJECT_UNBOUND` — the rule is never vacuously satisfied by an unbound subject. Composition consequence, stated because it is a real change and not a kernel one: the reference composition binds only `work-run` into `work_bindings` today (`cadp/product/activities.ts` seals `[{namespace: "work-run", …}, ...extra_bindings]` and nothing populates `extra_bindings`), so declaring `{REVIEW, commit, [PR_CREATE, PR_MERGE]}` requires the composition to bind the candidate through that existing hook — exactly what WP §3.4 already mandates for external candidates.
3. **Where it runs.** Inside `assemble_admission_input`, in the Platform (Ingress), in the same transaction that seals K4. The result is the **union** of the caller's `evidence_refs` and the queried set, deduplicated by `evidence_id` and ordered canonically by `evidence_id` so `input_digest` is deterministic. The caller may add; the caller can never subtract. Assembly is never the caller's evidence-selection choice for a declared kind (Spec v0.5 K4: the PEP never back-fills facts the evaluator did not see — the correction is to put them in front of the evaluator, not behind the PEP).
4. **Fail closed.** If the query cannot be executed, or any matched row fails verify-on-read, assembly **refuses** — `ASSEMBLY_QUERY_FAILED` / `DIGEST_CORRUPTION` (incident per TD v0.4 §2.6) — and **no `AdmissionInputV1` row is written**. A partial set is never sealed.
5. **Completeness is as-of a transaction, so it is re-proven at commit.** A new `§4.4` recheck item **#18**: inside the admission transaction, the PEP re-runs (1) over rows read in that transaction and refuses `ASSEMBLY_INCOMPLETE_AT_COMMIT` if the complete set for any declared pair differs from the set the bound `AdmissionInputV1` carries. Without #18 a producer could seal a contrary envelope after assembly and the decision would be silently stale (Spec v0.5 §2.7). Honest cost: a producer that keeps sealing envelopes for a subject can keep admission failing. That is a liveness cost of a safety rule, and it is fail-closed — a fresh assembly and evaluation resolve it.
6. **What this does not do.** It does not make an existential policy predicate sound; it removes the caller's power to decide what the evaluator sees. Whether the complete set satisfies a gate remains the evaluator's decision over K4-bound facts.

### B5. Run membership mechanism

Spec v0.5 §5.3 locks the invariant — *a requester cannot self-select or borrow another valid run scope* — and delegates the mechanism to the TD. **One mechanism is chosen: a Platform-minted run capability.**

**Seam today.** Nothing implements this: `work_bindings` are caller-supplied content on the seal draft, and `sealEffectRequest` reads `work_run_ref` out of them only to index the request row. `METHOD_REACH` in `cadp/kernel/api.ts` is keyed by `process_class`, not by principal. And `admit_and_dispatch` is the **second** write API that receives no principal: the branch calls `deps.pep.admitAndDispatch(body.effect_id, body.decision_id)` with no caller identity at all (`cadp/kernel/api.ts`), so any principal of the `workflow` class could dispatch any effect.

1. **Minting at dispatch on a DURABLE SEAL-TIME WITNESS, delivered only to the sealed requester.** `admit_and_dispatch` takes the authenticated principal — `admitAndDispatch(effect_id, decision_id, { principal })`, the same pattern the API layer already uses for `seal_effect_request` and `submit_evidence`. **The minting predicate is WITNESSED, not shape-only: `run-capability-minting(E)` holds exactly when BOTH (a) `E`'s sealed request is a `WORK_START` — its sealed `operation_kind` is the run profile's `WORK_START`, the SHAPE leg — AND (b) `E` was ADJUDICATED A RUN ORIGIN AT SEAL, witnessed by a durable `run_membership(E, E)` row**, the self-referential row that (5)'s insert writes inside `E`'s own sealing transaction on (9)'s origin path. The PEP evaluates both legs by reading rows in the dispatch transaction and **mints at initial dispatch ONLY when that witness exists**. `run_membership(E, E)` is **not an incidental row: it IS the DURABLE WITNESS that `E` passed `is_run_origin`'s origin path at seal**, and it is the only witness there is — (5) inserts `run_membership(F, W)` with `W` the request's sealed `work_run_ref`, so `F == W` requires (9)'s leg 3 to have held; an enrolled requester's `WORK_START` is adjudicated origin-or-refused and never falls through (9); a non-enrolled requester's run-bound request is refused `NOT_RUN_ENROLLED` (3); and a non-`WORK_START` self-binding is refused before any row exists (9). **Two consequences, both normative.** **(α) An ordinary `WORK_START` — `operation_kind == WORK_START` but NO `run_membership(E,E)`, because it was not a self-origin at seal — is NEVER minting**, not at its initial dispatch and not at any later one, **and no later `POLICY_ACTIVATE` can retroactively make it one**: the witness is fixed in `E`'s sealing transaction, and a policy change never rewrites a past K3 or a past membership fact — there is no runtime `UPDATE` and no back-dating insert on any path (`cadp/kernel/store.ts`). **The exact cross-boundary lifecycle fork this closes, which is NOT the one recheck #19 catches:** a **non-enrolled** requester `R` seals an ordinary `WORK_START` `E` carrying **no** `work-run` binding — not run-bound, so (3) refuses nothing, (9) never adjudicates it, and **no `run_membership(E,E)` exists**; while `R` is still non-enrolled, `E` is `admit_and_dispatch`ed and, under a shape-only predicate, mints `C(E)`; `E` reaches `COMMITTED`; a later `POLICY_ACTIVATE` enrolls `R`; `R` then seals a follow-up bound to `work_run_ref = E` presenting `C(E)`, and (4)'s ordinary member path passes **every** leg — the `run_capability` row exists for `E`, `holder_ref` matches, `E`'s latest conclusive K7 is `COMMITTED` — **promoting `E` to a run root though it was never an authenticated self-origin at seal**, which is exactly what Spec v0.5 §5.3 forbids. **Recheck #19 is no defence here and never was**: #19 requires the *follow-up request's own* `run_membership(follow_up_effect_id, E)` row, which that seal itself inserts by (5), so #19 finds it and passes while the fork goes through. The witnessed predicate closes it one step earlier, **at the mint**: no witness at dispatch ⇒ **no `run_capability` row is ever written for `E`** ⇒ the later presentation is refused `RUN_CAPABILITY_INVALID` by (4) on its no-row case, permanently — `E` is `COMMITTED`, so recheck #12 admits no further dispatch of it (`EFFECT_ALREADY_COMMITTED`, `cadp/kernel/pep.ts`), and a further ordinal would not be the *initial* dispatch in any case (B6(4)). **(β) A genuine self-origin `WORK_START`, whose witness is durable, mints EXACTLY ONCE at initial dispatch:** the witness is written in its own sealing transaction (9) and is therefore present at that dispatch and at every later one, with once-and-only-once enforced by the `run_capability` primary key below. No legitimate origin loses anything by the narrowing — (9) makes every `WORK_START` an enrolled requester can seal at all an adjudicated origin carrying the witness. **This is the lifecycle discipline already in this document, extended to minting-eligibility:** identity and membership are fixed at seal, a contract oscillation cannot fork one origin (B1(5); A5 leg o-v), the allocation principal and contract are graded against the transaction they were stamped in (B2(9)), and capability revocation is deliberately undefined (4) — so **minting-eligibility is likewise FIXED AT SEAL by the witness and NEVER re-evaluated at dispatch under changed config**. A policy activation changes what may be sealed next; it never re-grades what was sealed. **Honest scope note against the checkout, so the witness is not confused with a shape inference that stays:** `cadp/kernel/pep.ts` also derives a *counting* scope for an unbound `WORK_START` from its own `effect_id` (`request.operation_kind === "WORK_START" ? request.effect_id : undefined`, on recheck #5's decision-scope and the `MAX_EFFECTS_IN_WORK_RUN` path). That is effect counting, not minting; it is not a witness, this contract never reads it as one, and nothing here changes it. For an effect that IS run-capability-minting, the PEP **REFUSES the dispatch** unless the caller's stamped `requester_ref` equals the sealed request's `requester_ref` — reason `WORK_START_DISPATCH_REQUESTER_MISMATCH`. That is a generic stamped-vs-sealed `requester_ref` equality carrying no domain knowledge, and it is what makes the one-shot secret deliverable **only** to its exact holder-to-be. Without it, the checked-out seam would let any `workflow`-class principal dispatch another's `WORK_START`, receive the capability, and — there being no recovery (7) — strand that run permanently. The alternative (let the dispatch proceed and merely withhold the secret from the wrong caller) was **rejected**: it leaves exactly the same permanent stranding, reachable by any authorized caller who simply races the dispatch. On that refusal nothing is minted and no outcome is written.
   At the **initial** `admit_and_dispatch` of a minting `WORK_START` — both legs of the predicate above, **witness included** — and before any outcome exists, the Platform mints a run capability of ≥256 bits from a CSPRNG and returns it in **that** result to the verified caller. `H(C)` is stored **in the same transaction as the admission**, in `run_capability(work_run_ref PK, holder_ref, capability_digest, minted_at)`, a non-constitutional implementation table. **The digest is pinned exactly: `capability_digest` = SHA-256 over the RAW 32 SECRET BYTES, never over the base64url text of B6(3)** — one canonical preimage, so no encoding variant (padding, alternate alphabet, case) can be a second string digesting to the same row, and the transport encoding is decoded before hashing; the secret itself is never stored, never in any K1–K7 record or digest, never in the `ResolvedAdmissionBundle`, and never in workflow args or effect material. `holder_ref` is the stamped `requester_ref` of that `WORK_START` request, which by the paragraph above is also the caller the secret went to. The `work_run_ref` primary key is that `WORK_START`'s own `effect_id` (TD v0.4 §7.4) — which, by leg (b), is also **both** columns of the witness row that authorized the mint — so minting is once-and-only-once by construction: a repeat `admit_and_dispatch` of the same effect finds the row present, mints nothing, and returns no secret — "exactly once" (7) is enforced by the store, not by caller discipline.
2. **Usability is gated at seal time on the `WORK_START`'s LATEST conclusive K7 state — not on when the capability was minted, and not on its first outcome.** Minting is delivery; **grading is Spec v0.5 §5.2's**, which grades the run scope's *current* validity, and it is re-applied on every presentation. The run-membership check of (4) requires, in addition to digest match and holder match, that the `WORK_START` effect's **latest conclusive `EffectOutcomeV1`, read in the sealing transaction, be `COMMITTED`** — K7, never K6, per Spec v0.5 §5.2 and the memo-proof rule of TD v0.4 §6.4. The three states, exactly:
   - **`COMMITTED`** (as the latest conclusive state) ⇒ **usable**. Read existentially — *any* `COMMITTED` outcome for that `effect_id` — which is both the implemented `#latestCommitted` predicate and safe to state as absorbing: recheck #12 refuses `EFFECT_ALREADY_COMMITTED` once one exists (`cadp/kernel/pep.ts`), so no further ordinal is ever admitted after a `COMMITTED` and "latest conclusive" cannot diverge from "present" along the dispatch path. The existential reading additionally survives a late reconciler write against an **earlier** ordinal's still-open admission, which an insertion-order "latest" would let flip a usable scope back to refused. **The flip is one-way: refused/unresolved → usable, never the reverse.**
   - **`UNKNOWN`** — the latest admitted dispatch has no conclusive outcome ⇒ `RUN_SCOPE_UNRESOLVED` (Spec v0.5 §5.2's "unusable until reconciliation resolves it" — no blind retry, no optimistic use). When reconciliation returns `COMMITTED`, the **same already-delivered capability becomes usable**, with **no re-delivery and no reconciler secret-handling** — which matters, because `Reconciler.reconcileEffect` writes that outcome with observer `…:reconciler` outside any `admit_and_dispatch` result (`cadp/kernel/reconciler.ts`), reached from the restart scan or from `request_reconcile`, whose reach is not the holder's alone (`cadp/kernel/api.ts`).
   - **`NO_EFFECT_CONFIRMED` as the latest conclusive state, with no `COMMITTED` anywhere** ⇒ `RUN_SCOPE_REFUSED` — **while that remains the latest state**, which is the whole claim and is deliberately *not* "forever". The checked-out PEP permits the **next admission of the same `effect_id` after a `NO_EFFECT_CONFIRMED`**: recheck #12 admits when `conclusive === "NO_EFFECT_CONFIRMED"`, takes `ordinal = prev.dispatch_ordinal + 1` after a fresh recheck, and that dispatch can reach `COMMITTED` (`cadp/kernel/pep.ts`; Spec v0.5 K6's next-ordinal rule). A rule that called the capability inert forever on the first `NO_EFFECT_CONFIRMED` would therefore contradict the kernel's own retry contract — a `WORK_START` that is genuinely `COMMITTED` at the target would have a scope the Platform refused to recognize — and would also misread Spec v0.5 §5.2, whose grading is of the scope's current conclusive state, not of its first attempt.

   **Minting is unaffected by any of this and stays at the INITIAL `admit_and_dispatch` of a WITNESSED origin only** (1) — K7 grading moves usability, never minting-ness, exactly as a policy activation moves neither: `H(C)` is already stored, so the later ordinals find the `run_capability` row present, mint nothing, deliver nothing, and return no secret (B6(4)). What a later `COMMITTED` changes is **only usability of the one capability already in the holder's hands**. This keeps all four properties at once: no recovery, digest-only storage, Spec v0.5 §5.2's reconciliation semantics and the PEP's retry semantics both honoured rather than contradicted, and **no secret in any reconciler or re-dispatch path**.
3. **Enrollment, in the `requester_ref` domain.** `data.cadp.run_profile_enrolled_requester_refs: [exact requester_ref]` — required, may be `[]`, part of `cadp.kernel-config.v2`. Spec v0.5 §5.1 declares enrollment over exact requester principals **as stamped** (`requester_ref`), so the enrolled set is in that domain and never in the raw authenticated-principal domain. At seal the chain is: authenticated principal → `identity_registry` → **stamped `requester_ref`** → enrollment membership; the PEP's admission-time identity for (5) is `EffectRequestV1.requester_ref`, the **same domain**, read off the sealed record rather than re-derived. For an enrolled `requester_ref`, `seal_effect_request` REFUSES a request without a `work-run` binding (`RUN_BINDING_REQUIRED`) — refused, not merely uncounted (Spec v0.5 §5.1). A **non-enrolled** `requester_ref`'s request carrying a `work_run_ref` is refused `NOT_RUN_ENROLLED`: enrollment cannot be acquired by presenting a binding (WP §5.2; WP control 5).
4. **Presentation and verification.** **Scope: every run-bound request EXCEPT a run origin**, which (9) adjudicates instead — as origin-or-refused — and which therefore never reaches this rule's capability-presentation legs or its pre-existing-K7 usability legs. An enrolled requester presents the capability on `seal_effect_request` over its authenticated channel — as a transport-level header, never as a draft field, never inside any record. The Ingress refuses unless, in the sealing transaction: the capability's digest — SHA-256 over the decoded raw secret bytes (1), and **every seal-time digest comparison MUST be CONSTANT-TIME**, so a refusal leaks no prefix information about the stored digest — matches the `run_capability` row for the request's exact `work_run_ref`; that row's `holder_ref` equals the **stamped** `requester_ref` of this request; and that run's `WORK_START` latest conclusive K7 state is `COMMITTED` (2). Possession never suffices on its own: the row binds one capability to one `work_run_ref` **and** one holder, so presenting run R2's capability on a request bound to R1 fails the first check and a principal holding another's capability fails the second. **Seal-time refusal codes, all distinct from recheck #19's `RUN_MEMBERSHIP_UNPROVEN`** — which is a PEP-time refusal on a missing durable row: `RUN_CAPABILITY_INVALID` (no digest match against the row for this request's `work_run_ref`, including the case where no row exists for it — which is also the **standing, permanent** refusal for any request naming a **never-witnessed** `WORK_START` as its run, no mint having ever been authorized for it (1)); `RUN_CAPABILITY_HOLDER_MISMATCH` (row `holder_ref` ≠ stamped `requester_ref`); `RUN_SCOPE_UNRESOLVED` (the `WORK_START`'s latest admitted dispatch has no conclusive outcome); `RUN_SCOPE_REFUSED` (its latest conclusive state is `NO_EFFECT_CONFIRMED` and no `COMMITTED` exists — a refusal of the presentation *at that moment*, which a later re-admitted dispatch reaching `COMMITTED` lifts for the same capability (2)); `RUN_CAPABILITY_REQUIRED` (an enrolled requester's run-bound request presenting none — distinct from `RUN_BINDING_REQUIRED`, which covers only the missing-`work-run`-binding case of (3)). **There is no revocation state in this generation** and no `revoked_at` column: the store contract forbids runtime `UPDATE`/`DELETE` (`cadp/kernel/store.ts`), so a mutable flag would be a field no append-only path could ever set. Revocation, if it is ever wanted, is a future append-only row (`run_capability_revocation { work_run_ref, revoked_at, … }`) consumed by this seal-time check; out of scope here.
5. **Durable proof for the PEP.** The seal inserts `run_membership(effect_id PK, work_run_ref)` in the same transaction as the `effect_request` row — for a run origin that row is `run_membership(effect_id, effect_id)`, inserted on this same path and not exempted by (9). **That self-referential row is (1)(b)'s durable minting witness**, written here and on no other path — the `work_run_ref` column is the request's sealed one, so only (9)'s leg 3 can make the two columns equal — which is what lets (1) read it at dispatch as proof of a **seal-time** adjudication rather than re-deriving minting-ness from the sealed record's shape under whatever config is active by then. New `§4.4` recheck item **#19**: for a request whose sealed `requester_ref` is enrolled, the PEP requires that row, with a matching `work_run_ref`, read inside the admission transaction — refusing `RUN_MEMBERSHIP_UNPROVEN` otherwise. Authority after restart is reconstructed from rows, never from process memory (TD v0.4 §4.5); the secret is not needed at admission time.
6. **What it is not.** The run capability is **not** a governed-target credential and confers no effect authority: a compromised one lets its holder propose requests bound to a run, which still need evidence, a decision under the active policy and the PEP's fresh recheck (Spec v0.5 §4.3). Its compromise cannot create an effect; it can only mis-attribute an effect to a run's budget — precisely the invariant it exists to protect, so the residual is stated, not hidden. Custody is no new custody class: the holder already holds a Kernel API bearer/workload credential today (`ApiDeps.tokens`, `cadp/kernel/api.ts`).
7. **No recovery.** The capability is returned **exactly once**, in the initial `admit_and_dispatch` result of the minting `WORK_START`, to the caller (1) verified as the sealed requester. That result is the **only** delivery channel this document defines. There is no re-delivery: only `capability_digest` is stored, and a digest cannot be inverted, so no contract here may promise to hand the secret back — and none needs to, because (2) makes a later K7 resolution change only *usability*, never delivery. A holder that loses it **cannot seal further run-bound requests for that run** — fail-closed, a liveness cost only, and consistent with the run remaining governable per-effect (its already-sealed effects admit, reconcile and grade normally). **Accepted fail-closed liveness residual, stated rather than papered over by the phrase "exactly once".** The `run_capability` row commit and the HTTP response delivery are **NOT ATOMIC**: a crash, or a dropped connection, **after the commit but before the caller receives the response, permanently strands that run** — the retry is not the *initial* dispatch, so nothing mints and nothing is delivered (B6(4)); nothing else re-delivers; and the raw secret exists **nowhere durable**, only `capability_digest` (1). "Returned exactly once" is therefore precisely **at-most-once generation with attempted delivery**, not guaranteed delivery. This window is an **ACCEPTED RESIDUAL of the no-recovery model, fail-closed and liveness-only**: the stranded run can seal no further run-bound requests, while its already-sealed effects admit, reconcile and grade normally, and no effect authority is gained by anyone. It is asserted as the documented outcome by the response-loss control in §C, so a future rotation contract has an exact shape to change. Rotation — mint C2, atomically append a superseding row, return C2 to the exact holder — is a possible future contract needing its own concurrency and replay rules and would be named `rotate_run_capability`; out of scope here. **This document adds no Kernel API method.**
8. **Unmeasured part, marked exactly** (Spec v0.5 §5.3's marker resolved to the one dependency that is actually unmeasured, with the invariant unweakened):
   - Holder-side custody across an orchestrator restart. `[UNMEASURED — probe required: no probe of any orchestrator's durable secret custody exists. The measured counter-fact bounds it: WP §6 (P0) measured that a Conductor `working_dir` is not a sandbox and that its settings are a trust boundary, which is one reason the reference deployment enrolls no Conductor principal (WP §5.2). The reference run profile's holder is the Temporal-backed `requester_ref` `workflow:cadp-work` (stamped from principal `cadp-workflow`, `cadp/deployment/referencePolicy.ts`).]`
9. **Run-origin bootstrap — ORIGIN-OR-REFUSED (Spec v0.5 §5.3).** The circularity, in one sentence: §§5.1–5.3 require every enrolled requester's request to carry an authenticated membership proof, and `work_run_ref` IS the `effect_id` of the run's own `WORK_START`, so that `WORK_START` would have to prove membership in a scope only it can establish. Spec v0.5 §5.3 resolves it as run-profile **semantics, not an exemption from them**: the origin `WORK_START` does not join a pre-existing scope, it **ORIGINATES THAT SCOPE'S IDENTITY, and identity only**. This rule authenticates that self-origin relation.

   **`is_run_origin(request)`** holds exactly when all three legs hold, in the sealing transaction:
   1. the request is **`WORK_START`-shaped** — its sealed `operation_kind` is the run profile's `WORK_START`. That is **leg (a) of (1)'s minting predicate and deliberately EXACTLY that leg, never the whole of it**: (1)'s leg (b) is the `run_membership(E,E)` row *this very rule decides whether to write*, so reusing the witnessed predicate here would be **circular** — the origin adjudication would require its own output as its input, and no origin could ever be adjudicated at all. The split IS the resolution of that circularity, not a second predicate with extra domain knowledge: this rule reads, at seal, exactly the one value leg (a) reads, and (1) reads that same value **plus this rule's durable output**, at dispatch. The two are evaluated at different times on purpose, and that is the point of the whole arrangement — shape is a property of the sealed record and cannot drift, whereas the *adjudication* depends on enrollment and self-binding as they were AT SEAL and is therefore the thing that must be pinned durably rather than recomputed later;
   2. its `work_bindings` carry **exactly one** binding in the declared kernel work-run namespace, matched on the **exact `(authority_ref, namespace)` pair** declared by `kernel_subject_namespaces` (B3(4)(a)); and
   3. that binding's `object_id` **equals the request's own `effect_id`**.

   Legs 1 and 2 are discharged by rules that already run before this one, which is why only leg 3 is new: leg 2's "more than one" case is refused `KERNEL_NAMESPACE_AMBIGUOUS` pre-K3 by B3(4)(b) and its "none" case `RUN_BINDING_REQUIRED` by (3), and leg 2 matches on the declared exact pair, so an off-authority `{other, work-run, …}` binding is not a kernel work-run subject at all and cannot stand in for the self-binding.

   **ORIGIN-OR-REFUSED, and this is the whole adjudication rule.** A `WORK_START`-shaped request (leg 1) from an enrolled requester is adjudicated **ONLY** as origin-or-refused and **NEVER falls through to the ordinary member success path of (4)**. Leg 3 holds ⇒ it takes the origin path. Leg 3 fails ⇒ it is **REFUSED `RUN_CAPABILITY_INVALID`** — the existing code of (4), **no new code** — **EVEN WHEN it presents a genuinely valid, holder-matching capability for the run it names, whose `WORK_START` is `COMMITTED`**. That counterexample is the point: possession of a valid capability is exactly what would otherwise carry a `WORK_START`-shaped request down the member path and let one requester originate a second run's identity inside another run's scope. No `effect_request` row, no `run_membership` row and **no membership proof** is created on that refusal — Spec v0.5 §9.2's negative control ("a `WORK_START` whose work-run binding names anything other than its own `effect_id` is refused and creates no run-membership proof"), asserted as control A4 leg **o2**.

   **The exemption's scope, stated exactly so it swallows no rule.** On the origin path, and **only** on it, two things do not apply, both because each names a run that cannot exist yet: (a) (4)'s **capability-presentation** legs — `RUN_CAPABILITY_REQUIRED`, the digest match against a `run_capability` row, and the `holder_ref` match — there being no such row for an `effect_id` not yet dispatched; and (b) (4)'s **pre-existing-K7 usability** legs, `RUN_SCOPE_UNRESOLVED` and `RUN_SCOPE_REFUSED`, which grade a run that is not yet started. **Everything else runs unchanged**: (3)'s enrollment and `work-run`-binding requirements, B3(4)(b)'s ambiguity lock, B2(3)'s complete first-seal legs (allocation row, principal, tuple integrity, contract integrity, projection, purpose), B2(10)'s allocation-principal gate, and (5)'s insert — **`run_membership(effect_id, effect_id)` IS still inserted**, so recheck #19 finds its durable row on the ordinary path and **nothing is exempted at admission**. That same row is **(1)(b)'s minting witness**, which is precisely what makes an adjudicated origin — and **only** an adjudicated origin — minting at its own initial dispatch. An origin acquires no capability by originating either: the capability for that run is minted at its own `admit_and_dispatch` by (1), unchanged.

   **Identity only, never validity.** This provision touches the **membership proof and nothing else**. The originated scope's VALIDITY remains exactly Spec v0.5 §5.2's K7 grading of this same `WORK_START` effect, applied by (2) to **every subsequent** run-bound request: while that `WORK_START` is `UNKNOWN` the scope admits nothing (`RUN_SCOPE_UNRESOLVED`) until reconciliation resolves it, and a `NO_EFFECT_CONFIRMED` one is refused (`RUN_SCOPE_REFUSED`). Originating an identity therefore establishes no validity, and no request other than the origin itself gains anything from this rule.

   **A non-`WORK_START` request binding its own `effect_id` acquires nothing by it** (Spec v0.5 §9.2). `is_run_origin` fails at leg 1, so the request takes (4)'s ordinary path and must present a capability for a `work_run_ref` equal to its own `effect_id` — for which no `run_capability` row can exist, that row being keyed by a **witnessed** origin's `effect_id` (1) — so it is refused `RUN_CAPABILITY_INVALID`; and failing leg 1 it writes no self-referential `run_membership` row either, so it acquires no witness and is never minting at its own dispatch. Self-binding is not a shortcut; it is a refusal. **Why leg 3 is checkable at all, and why the origin tuple carries no `work_run_ref`.** Allocation precedes sealing, so the origin's Platform-issued `effect_id` is already in the caller's hands when it seals (`cadp/live/ops.ts` allocates, then seals) — the caller re-presents it as its own `work-run` binding and the core compares it against the `effect_id` the request names. That is also why B1(5)'s tuple cannot carry `work_run_ref`: a tuple naming the identity would have to contain the value it is being derived to produce.

   **Origin-path material replay is a Workflow-side obligation, cited not restated.** The identity converging is not sufficient for a retry to be a retry: the same `effect_id` re-presented with drifted sealed material is a `REQUEST_DIGEST_CONFLICT` (K3), an incident and a scope hold. WP §3.6 owns that contract normatively — fix the `WORK_START` args at first origin creation, reproduce them verbatim, derive no sealed-material field from the wall clock — and this document consumes it as the caller obligation it is, adding no kernel machinery for it.
10. **Not a K8.** Two implementation tables and two recheck items. No new record, no new evidence kind, no orchestrator lifecycle.

### B6. Wire framing on the §12 surface

B2 and B5 both require the caller to hand the Platform something that is **not** a field of any constitutional record — a re-presented allocation tuple, a run capability — and both said only "as transport, never a draft field". That is a requirement with no exact shape, and the §12 surface is **this document's** to own (Part A, §12 row). It is fixed here, exactly, so that "transport" is checkable rather than aspirational. **No method is added and no method's reach changes** (Part A, §12 row); three payload shapes are pinned.

**Seam today.** `cadp/kernel/api.ts` parses the **whole** `seal_effect_request` body as a `RequestDraft` (`JSON.parse(raw) as RequestDraft` → `sealEffectRequest(draft, { principal })`), and the `admit_and_dispatch` body as exactly `{ effect_id, decision_id }` — no header is read on either beyond `authorization`, and no response of either carries a secret.

1. **`seal_effect_request` — one new optional top-level body field, `allocation_tuple`.** Its value is the **wire tuple object verbatim** as `allocate_effect_id` received it (B1(3)), carried as a sibling of the existing `RequestDraft` keys. **Every existing `RequestDraft` field is unchanged**, and because the API layer parses the body as one object, the Ingress **strips `allocation_tuple` before constructing the draft**: it is never a `RequestDraft` key, never reaches `EffectRequestV1`, and never enters `request_digest` — which is what keeps B2(3.2)'s "transport, never a draft field" true of the implemented parse rather than merely asserted against it. It is **REQUIRED on the first seal** of an `effect_id` (no `effect_request` row yet): absent ⇒ `ALLOCATION_TUPLE_REQUIRED`, refused before any K3 record exists, alongside B2(3)'s other pre-K3 refusals.
2. **On an idempotent re-seal it is ignored-if-identical and refused-if-different.** A re-seal MAY omit it (the request row already exists and B2(3)'s first-seal legs do not re-run — **B2(10)'s allocation-principal gate does, on every seal, before anything else**) and MAY repeat it; if present, its `cadp-jcs-1` digest MUST equal the row's `allocation_binding_digest`, else `ALLOCATION_BINDING_MISMATCH`. Deliberately no new reason code and no new comparison: a differing tuple on a re-seal is the same falsehood about the same allocation that (3.2) refuses on a first seal. The K3 idempotency rule over the semantic payload is untouched — `allocation_tuple` is not part of that payload, so repeating or omitting it can never turn an idempotent re-seal into a `REQUEST_DIGEST_CONFLICT`.
3. **The run capability travels as an HTTP header: `x-cadp-run-capability`.** Value = **base64url (unpadded) of the raw 256-bit (32-byte) secret**, on the caller's authenticated `seal_effect_request` channel; the Ingress **decodes it to those raw bytes before digesting**, because `capability_digest` is over the raw secret and never over this text, and compares constant-time (B5(1), B5(4)). It is **never a body field, never a draft field, never a record field, and never a subject binding** — B5(4)'s "as a transport-level header" resolved to one exact header name and one exact encoding. **Logging prohibition, normative:** the Platform MUST NOT write this header's value — nor the response field of (4) — to any log, trace, metric label, incident detail, error message, or `KERNEL_INCIDENT` claim; refusals name the reason code only (B5(4)), never the presented secret or any prefix of it. A digest of it appears in exactly one place, the `run_capability` row (B5(1)).
4. **`admit_and_dispatch` — one new optional response field, `run_capability`.** Value = base64url (unpadded) of the freshly minted 256-bit secret. It is present **EXACTLY** when all of: the dispatch is the **initial** dispatch of that `effect_id`, the sealed request is run-capability-minting (B5(1)) — **the witnessed predicate, BOTH legs**, so an ordinary `WORK_START` carrying no `run_membership(E,E)` witness returns no field at its initial dispatch either, and no later activation changes that — and the caller passed B5(1)'s stamped-vs-sealed `requester_ref` equality. **Absent in every other case without exception** — non-minting operations, a refused dispatch, and **any non-initial result for the same `effect_id`**, which is what "returned exactly once" (B5(7)) means on the wire: the secret is never re-delivered, and the one-shot/no-recovery model requires exactly this, because only `capability_digest` is stored and a digest cannot be inverted (B5(7)). Stated against the checked-out code rather than around it: `admitAndDispatch` today has **no stored-result replay path** — a repeat call on a `COMMITTED` effect is refused `EFFECT_ALREADY_COMMITTED` and one on an unresolved prior is refused `PRIOR_DISPATCH_UNRESOLVED` (recheck #12, `cadp/kernel/pep.ts`), while a post-`NO_EFFECT_CONFIRMED` retry admits a **further ordinal** (B5(2)). The rule above covers all three uniformly by keying on *initial dispatch*, not on *call outcome*, so it stays exact if a replayed/idempotent result return is ever added: such a result returns the stored result **WITHOUT** the `run_capability` field. The **request** body of `admit_and_dispatch` is unchanged at `{ effect_id, decision_id }`; B5(1)'s principal is the one the API layer already resolves from `authorization`, never a body field.
5. **Not a K8, and not a new method.** Two optional wire fields and one header, all outside every K-record and every digest. `METHOD_REACH` is unchanged.
