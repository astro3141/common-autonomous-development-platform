### A.2 The cross-plane surface — exact pointers

This plane **produces** envelopes; it never decides what an envelope satisfies, and it holds no Kernel API authority beyond submitting evidence as its registered producers. Four contracts cross the boundary, all of them the Authority Plane's under **AP Part A, §9 row** (evidence ingress and provenance: producer stamping, Ingress-set integrity, adapter-registry-checked `source_relation`, untouched `claim`, source-time-authority derivation, non-policy `received_at`, derived `identity_class`, K4 completeness):

1. **Envelope subject bindings.** The `work_run` / `step` / `surface-role` bindings this plane's evidence carries (`cadp/product/backendExecution.ts`) are ordinary `SubjectBinding`s under Spec v0.5 K2/§2.4; their shape, uniqueness and kernel-namespace rules are AP's (AP B3(4) for declared kernel namespaces; AP B2(3.4) for projected pairs). This document adds exactly one binding, in B1, and adds no namespace to any kernel lookup.
2. **`produced_at` sourcing.** Per-producer, from `adapter_registry.produced_at_source`: `{kind: NONE}` for `backend-scan:*`, `{kind: SOURCE, claim_pointer: /completed_at}` for `verifier:github-actions` (`referencePolicy.ts`). A producer here never chooses its own time authority.
3. **Locator rules.** Every `PRESENT` observed field must carry a locator; the Ingress refuses `OBSERVED_WITHOUT_LOCATOR` otherwise (`cadp/kernel/ingress.ts` `assertBackendObservedLocators`; TD v0.4 C13). This plane supplies locators; it does not enforce them.
4. **Producer registration.** Which `producer_ref` may submit which `evidence_kind` under which `source_relation` lives in `adapter_registry` and changes only by `POLICY_ACTIVATE` (TD v0.4 §9.4; WP §3.2). A surface cannot acquire an evidence kind by being an execution surface.

## PART B — NEW v0.5 CONTRACTS

Exactly three. None is a constitutional record; all three are product-service contracts of an **optional** plane.

### B1. The symmetric execution contract (Spec v0.5 §6)

**Seam today.** The broker transport carries per-operation bodies with no digest discipline: `brokerImplement({repo_full_name, base_sha, work_item, worker_product})`, `brokerReview({repo_full_name, candidate_sha, work_item, review_product?})`, `brokerPlan({repo_full_name, base_sha, intent, plan_product?})` (`cadp/product/surfaceBroker.ts`, dispatched through `BROKER_OPERATIONS` / `cadp/product/brokerTransport.ts`). The result side is likewise asymmetric: `brokerImplement` returns `{candidate_sha, bundle_b64, backend_provider, backend_model?, backend_locator?, backend_effort?, …}` — an artifact and observed facts, but **no digest of the artifact**. The contract below is therefore contract-new on both sides; it describes no measured mechanism.

1. **`ExecutionRequest` — a product API contract, not a K-record.** `cadp.execution-request.v1` is **a common header plus a role-specific exact-input block**. It is not one flat shape, because the three implemented entry points are **not handed the same revision**: `brokerReview({repo_full_name, candidate_sha, work_item, review_product?})` receives a `candidate_sha` and **no `base_sha` at all** (`cadp/product/surfaceBroker.ts`), so a common `base_revision` field is one the reviewer role could only fill by re-deriving a value it was never given — which the no-re-derivation rule below forbids. Every field below maps to an argument an implemented broker function **already takes**; that mapping, cited per field, is the whole warrant for the field existing.
   - **COMMON HEADER — `{ schema, surface_role, provider, executor_profile_digest, repo_id }`**, well-defined for all three roles:
     - `surface_role` ∈ `WORKER | REVIEWER | PLANNER` — the existing §19.5 vocabulary, already carried as the `surface-role` binding's `object_id` (`submitBackendExecutionEvidence`, `backendExecution.ts`).
     - `provider` is the closed-union name the resolvers admit — the `worker_product` / `review_product` / `plan_product` argument of `brokerImplement` / `brokerReview` / `brokerPlan` after resolution (`resolveReviewProvider`, `resolvePlanProvider`, `surfaceBroker.ts`); an unknown name fails closed with no filesystem, process, docker or network side effect (§17.1, unchanged).
     - `executor_profile_digest` is a digest over the **resolved provider profile entry** — argv template, auth descriptor, scan fields, `identity_class_product` — i.e. the argv identity of §17.1. It does **not** exist today and is **not** `workerProfileDigest` (`cadp/product/workerProfile.ts`), which digests the constructed auth sandbox; the two are distinct objects and must not be conflated.
     - `repo_id` is exactly the `repo_full_name` argument all three functions already receive.
   - **ROLE-SPECIFIC EXACT INPUTS — `WORKER` and `PLANNER`: `{ base_revision, input_digests: [{ input_role, digest }] }`.** `base_revision` is exactly the **`base_sha` argument `brokerImplement` and `brokerPlan` already receive** and materialize the workspace at (`git checkout --quiet <base_sha>`, both functions) — the same exact base revision the boundary calls `candidate_base_sha` (WP §3.4), carried unchanged. It binds provenance, never target state; this document redefines neither. `input_digests` covers the exact task input the surface is handed: the `work_item` string for `WORKER`, the `intent` string for `PLANNER`. Both arrive as plain strings today and the broker digests neither.
   - **ROLE-SPECIFIC EXACT INPUTS — `REVIEWER`: `{ candidate_revision, input_digests: [{ input_role, digest }] }`.** `candidate_revision` is exactly the **`candidate_sha` argument `brokerReview` already receives** and checks out. The reviewer request carries **no `base_revision`**, because the broker is never handed one — the asymmetry is in the implemented signature and this contract mirrors it rather than papering over it. (`brokerReview` does compute a fork base for its diff — `git merge-base origin/main <candidate_sha>` — but that is a *derived* value built for prompt construction, and it is deliberately **not** promoted into this contract: promoting it would be precisely the re-derivation the next paragraph forbids.) `input_digests` covers the `work_item` string.
   - **Relation to the sealed inputs, for every role.** The Execution Plane digests **what it was handed** and re-derives nothing: the role's revision field MUST equal the revision the sealing composition already pinned for that run, and the work-item / intent digest MUST be over the exact string that run sealed. Whether a sealed effect's material and an execution envelope agree is decided by the evaluator over K4-bound facts (Spec v0.5 §4.3), never here.
2. **`ExecutionResult` — output-bound for EVERY role.** `cadp.execution-result.v1` = `{ schema, surface_role, provider, output_artifact_digest, output_artifact_locator, observed: { model, effort, provider, run_id, version } }`. `observed.*` is the existing scan payload, unchanged (`backendExecution.ts`). **Every** result carries **exactly one** `output_artifact_digest`: there is no "or none" case and never a placeholder. A contract calling itself *symmetric and output-bound* while letting one role return no artifact would be neither, so the per-role artifact is **pinned here, now** — identity, canonical bytes, digest scheme, locator — grounded in what the implemented broker **already holds**, so that the capture probe of (4) measures **MECHANISM only** and decides no design. In all three cases the digest is computed by the **BROKER as observer over bytes the broker already possesses**; it is never read from the surface's session log or from stdout-as-self-description, and never accepted as a value the model states about itself.
   - **`WORKER` — artifact = the candidate `git bundle` bytes the broker itself generates.** Canonical bytes: the bundle file the broker creates and reads back (`git bundle create <path> cadp-candidate` → `readFileSync(bundlePath)`, surfaced as `bundle_b64`, `surfaceBroker.ts`) — a byte stream in the broker's own hands. Identity (`object_id`): the **candidate commit the broker rev-parses** (`git rev-parse HEAD` over the workspace it materialized, `surfaceBroker.ts`), in the `commit` namespace. **The prior draft's bundle-vs-commit ambiguity is RESOLVED here: the digested object is the bundle bytes; the identity `object_id` is the `candidate_sha`.** Why that split and not the reverse: the bundle is the exact byte artifact the broker **holds** and that the broker later verifies reproduces the candidate, so digesting it binds content the broker **possesses** rather than content the target serves — while the candidate sha is the target-canonical *name* the sealed material and every existing `commit` binding already use. Identity names, content verifies; neither field does the other's job.
   - **`REVIEWER` — artifact = the captured verdict stdout bytes.** Canonical bytes: `review.stdout` exactly as the broker captures it from the surface (`brokerReview` returns it), under the **measured** per-provider output contracts already implemented — `parseReviewVerdict`'s exact `APPROVE` / `REQUEST_CHANGES` first line, and the `--json-schema` path for grok's measured glued-narration case (9th pilot). Identity (`object_id`): **the review artifact's own identity** — the evidence id the envelope will carry, or the broker-assigned capture identity — in the review-output identity domain. It is **NOT** the reviewed candidate. This distinction is stated explicitly because the tempting alternative is false: binding `object_id` to the reviewed `candidate_sha` in the `commit` namespace with the verdict bytes as `content_digest` would assert that those bytes **are the content of that commit**, which they are not. The binding of a verdict to the candidate it reviews **already exists and stays exactly where it is** — the REVIEW evidence's own `commit` subject binding (`cadp/product/activities.ts`) — and the artifact binding does not overload it.
   - **`PLANNER` — artifact = the captured proposal stdout bytes**, whose digest the broker **ALREADY measures**: `stdout_digest: sha256(run.stdout)` in `brokerPlan` (`surfaceBroker.ts`). This is **the one measured output-artifact capture that exists at this checkout**, and it is cited as such; worker and reviewer capture mechanics are the remaining **unmeasured** probe scope (4). Identity (`object_id`): the proposal artifact's own identity, in the same output-artifact identity domain as the reviewer case and for the identical reason. Honest delta, since the measured value is not yet the contract value: today `stdout_digest` is a bare hex string, not a typed `Digest`; this contract requires it typed.
   - **All three:** `algorithm` / `canonicalization` come from `data.cadp.approved_digest_schemes` — at this checkout `{sha256, raw-bytes-1}` for all three, each artifact being a raw byte stream and `raw-bytes-1` being an approved scheme in the reference config (`referencePolicy.ts`). `output_artifact_locator` is the **broker-side observation locator** for that digest, of the `broker-response#…` shape the broker already uses for the one field it observes rather than scans (`observed.provider.locator = "broker-response#backend_provider"`, `backendExecution.ts`), satisfying the existing OBSERVED_WITHOUT_LOCATOR rule (§A.2(3)) without any ingress change. Digest and locator are present or absent **together**: a digest without its locator is not a well-formed result.
3. **How it binds into the evidence envelope — two halves, no new kernel field.** `SubjectBinding` at this checkout is `{ authority_ref, namespace, object_id, revision_or_version?, content_digest? }` (`cadp/kernel/records.ts`), where `object_id` is the subject's **identity** (*which* artifact) and `content_digest` is its **content binding** (*which exact bytes*, as a typed `Digest {algorithm, canonicalization, value}`). It carries **no locator slot**, and this document adds none. The digest and its provenance therefore land in the two carriers that already exist:
   - **Subject identity and content, each in its own field.** Exactly one added binding, constructed exactly as the existing `surface-role` binding is (`submitBackendExecutionEvidence`, `backendExecution.ts`). `object_id` is the **artifact's identity exactly as (2) pins it for that role**, never a value the surface states. **WORKER instantiation:** `{ authority_ref: "github.com", namespace: "commit", object_id: <candidate_sha>, content_digest: <digest of the bundle bytes> }` — the same `(authority_ref, namespace)` pair `REVIEW` and `VERIFICATION` evidence already binds (`cadp/product/activities.ts`, `cadp/live/intakeDriver.ts`), with the identity being the broker's own `git rev-parse HEAD` over the workspace it materialized (`surfaceBroker.ts`). **REVIEWER and PLANNER instantiation:** the identity is the output artifact's **own** identity per (2), in the output-artifact identity domain — **not** `github.com|commit`, because the artifact is the verdict/proposal bytes and those bytes are not the content of any commit. Binding either role's stdout digest under a `commit` `object_id` is exactly the overload (2) forbids; the reviewer's tie to the candidate it reviewed remains the REVIEW evidence's existing `commit` binding and is untouched here. `content_digest` is the **`output_artifact_digest` itself**, typed, under a scheme in `data.cadp.approved_digest_schemes` (TD v0.4 §2 — approved schemes govern every new write and must keep verify-on-read computable; AP Part A §2 row, which owns the canonicalization set and the write/read-validation and verify-on-read discipline). **The digest is never an `object_id`**, in this binding or any other this plane produces: a digest carried as a *name* would pass exact-subject equality on a string comparison while engaging neither the approved-scheme discipline nor verify-on-read, so a subject with no content binding at all would satisfy the Spec v0.5 K2/§2.4 rule that a mutable subject without its required digest cannot be claimed exact — the content binding defeated by putting it in the identity field. **Two layers, both obligatory — and an implementation gap NAMED, not absorbed.** (i) The Execution Plane MUST **construct** every `content_digest` it produces under an approved scheme — this plane's own obligation and control C1's falsification target. (ii) The Authority ingress MUST **independently reject** a `SubjectBinding.content_digest` carrying an unapproved scheme, under the **inherited** TD v0.4 §2.1 rule the Authority Plane re-homes verbatim (AP Part A, §2 row): `data.cadp.approved_digest_schemes` in the active policy content **governs every new write**, and *"a digest with an unapproved scheme is invalid input, never a different-but-equal identity."* At this checkout that second layer is **not implemented**: `validSubjectBindings` (`records.ts`) validates `content_digest`'s typed **shape** only (`isDigestShape`), and `assertSchemesApproved` (`cadp/kernel/ingress.ts`) is invoked over **K3 digests alone** — `[sealed.material_digest, sealed.request_digest]` — never over evidence subject bindings. That is an **IMPLEMENTATION GAP in the Authority Plane's own inherited contract**, named here as required implementation work before v0.5 conformance. It is **not re-assigned to this plane**: a product-side construction discipline binds only well-behaved producers, whereas §2.1 governs *every new write by any producer*, so this plane's obligation cannot discharge the kernel-wide rule and does not purport to. **No Authority Plane TD amendment is needed** — the rule already exists there in re-homed §2.1; only its enforcement over this field is missing. Two consequences follow from the identity being the identity, both on the WORKER instantiation where the candidate is the subject: the AP B4(2) assembly key `<authority_ref>|<subject_namespace>|<object_id>` for that pair is one a `PR_CREATE` request's own `work_bindings` already name, which a digest-as-`object_id` binding could never match; and B1(5)(d)'s comparison against the sealed material has an identity to compare on and a digest to verify with, rather than one string doing both jobs and neither well.
   - **Observation provenance.** The same digest also rides as an ordinary observed field — `claim.observed.output_artifact = { availability: "PRESENT", value: <output_artifact_digest>, locator: <output_artifact_locator> }` — so the §A.2(3) locator obligation applies to it under the **already-implemented** rule with no ingress change: `assertBackendObservedLocators` (`cadp/kernel/ingress.ts`) refuses `OBSERVED_WITHOUT_LOCATOR` for any `PRESENT` observed field lacking a locator, this one included. The binding's `content_digest` and the observed field carry the same digest under the same scheme: the binding is the content-verified subject record, the observed field is the provenance-bearing carrier that names where the broker observed it.

   That rule enforces locator **presence** only. It cannot distinguish a broker-side locator from a session-file one — `observed.model`'s locator is legitimately a session file — so *which* locator this field carries is this plane's construction obligation (the broker populates `observed.output_artifact` only from bytes it holds, never from `scanBackendModel` output) and control C1's falsification target, not a kernel guarantee. Everything else about that envelope is unchanged and is the Authority Plane's (§A.2): producer stamping under `backend-scan:<provider>`, `produced_at_source {kind: NONE}`, the locator obligation, and `source_relation` staying `SELF_REPORT` — **no promotion** (Spec v0.5 §4.5). A stronger relation requires a probe establishing it and an `adapter_registry` change under the ordinary activation gate; this document promotes nothing and mints no evidence kind (Design D7-3). Whether any gate consumes the binding is composition policy: the reference policy states no such predicate today, so the binding is **inert until a composition adds one** — and the AP B4 `subject_complete_assembly` declaration set can only name this pair once the binding exists (AP B4(1)–(2): a declared entry whose subject namespace is unbound refuses `ASSEMBLY_SUBJECT_UNBOUND`).
4. **Capture MECHANICS, marked honestly — the WHAT is decided above, not here.** `[UNMEASURED — probe required: the PLANNER artifact digest is measured today (`stdout_digest`, (2)); no probe has captured a WORKER bundle digest or a REVIEWER verdict-stdout digest at the surface boundary, so the capture MECHANICS of those two roles in (2)–(3) are unmeasured. Which object is digested, and under which identity, is settled for all three roles by (2) and is **not the probe's to choose**; the probe measures only that the broker can perform that capture, and it must capture **both** halves of (3)'s binding — the artifact identity destined for `object_id` and the digest destined for `content_digest` — each observed by the broker and neither self-reported.]` This is the capture probe that Spec v0.5 §6's marker, WP §4.2's future K2 candidate-provenance contract (which names this probe as its trigger and mints nothing before it), and the AP B4 declaration-set extension above all wait on. **The contract shape and the artifact identity are defined NOW so the probe has an exact target.**
5. **What the probe must measure**, in order: (a) that the broker can digest the produced artifact from bytes it already holds at the surface boundary, with the surface supplying no digest and no input to it; (b) that the object **already pinned in (2)** digests **stably** — the same worker run's bundle bytes re-digest equal on re-read, and the same reviewer stdout capture re-digests equal; this is a stability measurement over an object this document has fixed, **not** a choice among candidate objects; (c) the observer chain — which principal seals it, and that `output_artifact_locator`, landing in `claim.observed.output_artifact.locator` per (3), names a **broker-side observation** (the `broker-response#…` shape) and never a session-file locator, since a session log is the model's own output and an artifact digest read from it would be self-report promoted to observation; (d) that the digest is comparable to the artifact the sealed material names (`candidate_sha` / `bundle_cas_key`), so the evaluator's Spec v0.5 §4.3 comparison has both sides. Until (a)–(d) are measured, no envelope this plane produces satisfies any execution-provenance requirement, and the reference policy asserts none.

### B2. Provider-credential custody (Spec v0.5 §2.3 and §6; Design D1.2)

1. **The rule, as this plane's internal discipline.** In the reference deployment, provider subscriptions are **not mutation credentials for any current governed domain target**. The measured basis is this plane's own posture: exactly one provider's auth is injected into an isolated container, read-only at its provider path, with the host keychain and every other provider unreachable (TD v0.4 §17.3; `surfaceProviderAuth` → `reviewerAuthArgs`, and `buildWorkerSandbox` on the worker path), inside a container whose only egress is the allowlist proxy to provider hosts so governed targets have no route (`isolation.ts`); and the GitHub read credential stays **host-side on the broker**, never inside any surface container (TD v0.4 §18.2; `fetchExternalVerification` shells the operator's `gh` on the broker host).
2. **This is a deployment-policy fact, and it dissolves on reclassification.** It is never a universal exemption and never a credential-**kind** exemption (Spec v0.5 §2.3, §6; Design D1.2, D7-5). A deployment whose policy classifies **provider invocation itself** as a governed effect — spend caps, data-egress control, model-access governance — thereby brings provider credentials under the **full Authority Plane custody rules**: held by the PEP, absent from every Execution Plane process and every surface container, with the invocation passing admission like any other governed effect. Nothing in this document may be read as carving them out, and Spec v0.5 §2.5's classification rule cuts the same way — an operation with no policy-bound classification defaults to **effecting**, so provider invocation is not non-effecting by default anywhere.
3. **What the reference deployment's classification basis actually is — the closed operation vocabulary plus the isolation measurement.** Stated exactly, because there is **no classification key in `policy_params`**: the reference bundle's params are `{verification_max_age_s, max_effects_cap, max_steps_cap, require_backend_effort, require_external_verification, extra_plain_allow_operations, delegated_merge_producers}` (`cadp/deployment/referencePolicy.ts`), and **`extra_plain_allow_operations` is not an effect classification** — it is a plain-**ALLOW** list over `operation_kind`s that still arrive as `input.effect_request` and still pass through admission and PEP dispatch (`op in params.extra_plain_allow_operations`, `REFERENCE_REGO`; default `[]`, and `FINDING_SEAL` is excluded from it whatever a deployment puts there). Plain-allowed is *governed with a trivial gate*, the opposite of *outside effect admission*; it could not supply the missing declaration and is not cited as if it could. The real basis is narrower and it is measured: **provider invocation is not an `operation_kind` at all.** Spec v0.5 §2.5 requires classification *"per operation against the target adapter's contract"* — so what it demands classification **of** is operations against target adapters, and the operation vocabulary is closed and adapter-declared. The PEP resolves `adapters.byTarget(request.target_ref)` (else `NO_ADAPTER_FOR_TARGET`) and then the operation from `adapter.describe().operations` (else `OPERATION_UNAVAILABLE`) — `cadp/kernel/pep.ts`. The complete declared set at this checkout is `GIT_PUSH`, `PR_CREATE`, `PR_MERGE` (`adapters/github.ts`), `WORK_START` (`temporal.ts`), `POLICY_ACTIVATE` (`storePolicy.ts`), `RECORD_WRITE` (`record.ts`), `DEPLOY` (`deploymentActuation.ts`), `FINDING_PROJECT` (`githubIssues.ts`), `FINDING_SEAL` (`findingSeal.ts`). Provider invocation is **none of them**, has no target adapter and no `target_ref`, and never reaches the PEP: it happens **inside the isolated surface**, reaching no governed target — the MEASURED fact of this plane's isolation posture (`isolation.ts`: worker and reviewer on the `--internal` network whose only hole is the provider-host allowlist proxy, so *"governed targets have no route"* and GitHub / record service / Kernel are unreachable). The policy-bound declaration is therefore **the closed operation vocabulary itself, plus that isolation measurement** — not a classification key, and this document invents no registry to stand in for one. The §2.5 default is not evaded: it applies to operations, and this is not one.
4. **The reclassification path, unchanged and explicit.** A deployment that **wants** provider invocation governed must introduce it **as an operation with a target adapter** — the moment it does, §2.5 requires its classification and §2.3 pulls provider credentials inside the PEP boundary in full. That is exactly the reclassification path §2.3 anticipates, and it is why (2)'s dissolution clause is live rather than rhetorical: the grounding above holds only while the vocabulary stays closed against it.
5. **Why this plane's isolation is load-bearing and never delegated.** WP §6 states the measured counter-fact (P0, run `24919dde`, 2026-09-07): a Conductor `working_dir` is **not a sandbox**, and `claude-agent-sdk` loads the working directory's settings as a trust boundary. An orchestrator's working directory, settings, or the word "sandbox" in its documentation therefore establish nothing. The enforceable boundary is this plane's container construction — network, mounts, single-provider auth injection, bounded lifetime (`isolation.ts`) — and it is **never delegated to any orchestrator**. The same fact is why B1's observer is the broker: an orchestrator working directory is not a place a digest can be observed from honestly.

### B3. Optionality and the equal-citizen consequence (Design D1.2)

1. **What is lost: nothing constitutional.** A deployment that runs its workers some other way — its own CI, its own harness, a human clone — keeps K1–K7, admission, PEP-only actuation, reconciliation and Kernel Conformance untouched (Spec v0.5 §9.1). What it loses is exactly the **reference execution-evidence producers**: `backend-scan:codex | grok | claude`, the only producers `adapter_registry` authorizes for `BACKEND_EXECUTION` (`REFERENCE_ADAPTERS`, `referencePolicy.ts`), so no other principal can submit that kind (`EVIDENCE_KIND_FORBIDDEN`).
2. **Which reference-policy predicates then become unsatisfiable, exactly** (`cadp/deployment/referencePolicy.ts`): `backend_model_present` — it requires a `PRESENT` `BACKEND_EXECUTION` with a `surface-role = WORKER` binding and `claim.observed.model.availability == "PRESENT"` — unsatisfiable. `backend_effort_present` — the same shape over `observed.effort` — unsatisfiable, so `effort_requirement_met` holds **only** while `params.require_backend_effort` is `false` (its first clause) and becomes unsatisfiable the moment a deployment arms that param. The **`BACKEND_EXECUTION` clause of `implementer_refs`** contributes nothing; the set is then whatever the `WORK_STEP` clause supplies, and a `WORK_STEP` producer names the **orchestrator, not the model that did the work** (WP §3.2), so a non-empty set from that clause proves no implementer product. Consequently `pr_create_ok` — `verification_ok` ∧ `external_verification_ok` ∧ `review_ok` ∧ `backend_model_present` ∧ `effort_requirement_met` — **DENYs, and no PR is created**.
3. **This is the same honest ingress-only posture the WP TD states for external candidates** (WP §3.2, control 12): **fail-closed at admission, never a defect**. An equal citizen at the effect boundary (Spec v0.5 §4.2) is equally subject to the composition's evidence requirements, and being admissible is not part of any plane's boundary contract. A deployment that wants admission without the reference producers needs a **reference-policy delta** — what establishes the implementer identity of its execution surface, how independence is computed over that evidence, and how model/effort provenance applies when the backend sits outside this plane — the same three questions WP §3.2 defers, composition work, out of scope here.

## C. Conformance controls (falsification additions)

In the Spec v0.5 §9 spirit — proven by attempting the violation. Three controls; the plane's existing product controls (TD v0.4 §13.2, P1–P7) are unchanged.

1. **Symmetric contract shape, with the identity-domain and observer legs.** **Identity-domain leg, asserted at both layers of B1(3):** the added binding must carry the `output_artifact_digest` in **`content_digest`** and the artifact identity in `object_id` (B1(3)); the control constructs the misplacement — an envelope carrying the digest as `object_id` with `content_digest` absent — and asserts that it is (a) refused **by the broker at construction**, runnable today, and (b) refused **independently by the Authority ingress at seal**, which must reject a subject binding that omits the `content_digest` its subject requires under the inherited Spec v0.5 K2/§2.4 rule (a mutable subject cannot be claimed exact without its content binding). Leg (b) is the same **gap-closing target** as the scheme leg and does **not** pass at this checkout: `content_digest` is optional on `SubjectBinding` and `validSubjectBindings` shape-checks it only when present (`records.ts`), so the kernel today seals the misplacement without complaint. The control asserts (b) as a currently-**failing** leg rather than omitting it. The consequence leg stands alongside both, not in place of them: such an envelope also **satisfies no execution-provenance requirement**, since a digest-as-name is a subject with no content binding, not a content-bound subject. **Scheme leg, likewise asserted at both layers:** a binding whose `content_digest` carries a canonicalization outside `data.cadp.approved_digest_schemes` must be (a) refused **by the broker at construction**, runnable today, and (b) refused **independently by the Authority ingress at seal** under the inherited §2.1 rule — leg (b) is marked as the **gap-closing target** of B1(3)'s named implementation gap and does **not** pass at this checkout, where `assertSchemesApproved` runs over K3 digests only. The control asserts (b) as a currently-**failing** leg rather than omitting it, so the gap stays visible instead of being silently satisfied by (a). An `ExecutionResult` carrying no `output_artifact_digest` produces an envelope with no artifact subject binding and likewise **satisfies no execution-provenance requirement** — *vacuously today*, since the reference policy consumes only presence, `surface-role` and `observed.*` on `BACKEND_EXECUTION` and states no artifact comparison, and *normatively* once B1(5) is measured and a composition adds the predicate. Negative leg, runnable when the capture lands, and **product-side by construction** since the kernel checks locator presence and not locator shape (B1(3)): a result carrying `output_artifact_digest` without `output_artifact_locator` is refused at Ingress with `OBSERVED_WITHOUT_LOCATOR` (`assertBackendObservedLocators`, already implemented), and a candidate digest whose locator names the surface's own session file or stdout is refused **by the broker**, never sealed as observed. The control falsifies both by feeding a session-scanned digest through the result path and asserting refusal rather than a seal — the artifact digest must be the broker's observation of bytes the broker holds, so a model cannot self-report its way into execution provenance.
2. **Custody.** The **F2** control carries forward unchanged — `cadp/tests/conformance-isolation.test.ts`, "F2: the worker sandbox imports ONLY codex auth material; the profile digest is deterministic": exactly the declared auth files are imported, the host `config.toml` (MCP/config mutation surface) is not, and the probe and production constructions digest equal. Its sibling in the same file carries the reviewer posture (the session bind is the only extra writable bind, `/ws` stays `:ro`, host `HOME` is never mounted). A second provider's auth in one surface container, or any governed-target credential in any surface container, falsifies B2(1).
3. **Optionality.** A deployment with this plane removed — no surface broker, no `backend-scan:*` producers — still passes the Spec v0.5 §9.1 kernel-conformance controls unchanged, while `pr_create_ok` **DENYs** for want of `backend_model_present`. The DENY is asserted as the **correct** outcome, exactly as WP control 12 asserts it for external candidates.
